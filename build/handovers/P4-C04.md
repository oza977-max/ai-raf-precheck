## State Threading Fix (found during design, not a late discovery)

`questionnaire`/`contradiction_review` states never carried `corrections`
forward from `graph_review` (a real gap in P4-C03 — corrections made
during graph review were silently dropped once a user moved into the
questionnaire). Fixed by threading `corrections: GraphCorrection[]` and
a new `useCaseId: string` (generated once at questionnaire entry, never
regenerated) through
`questionnaire → contradiction_review → confirmation → evaluation_pending → verdict`.

## Code Review Findings

**Review passes:** [(1, 2), (2, 0)]

**Pass 1 findings, both Critical:**

1. **Audit ordering flake, self-caught before independent review even
   started.** While writing the new TC-UC-6-01 acceptance test, the full
   suite (not the isolated file) failed intermittently — `getAll()`
   returned `['verdict_produced', 'graph_confirmed']` instead of the
   written order. Root cause: `db.getAllFromIndex()` only guarantees
   index-key order; records sharing the same `use_case_id` fall back to
   primary-key (`event_id`, a random UUID) order, not insertion order.
   Fixed by sorting on `occurred_at` in `getAll()`/`getAllForExport()`.
   **Independent review then reproduced a second-order flake in the fix
   itself**: `graph_confirmed` and `verdict_produced` are written close
   enough together that they can share the exact same millisecond
   timestamp, making the `occurred_at` sort a tie that falls back to the
   same undefined ordering the fix was meant to solve. Confirmed via
   direct reproduction (2 of 3 full-suite runs failed). **Fixed** with a
   monotonic tie-breaker in `append()` (module-level `lastOccurredAtMs`,
   bumped by 1ms on collision) — the sole write path, so this guarantees
   strictly increasing `occurred_at` for events in the same tab session,
   exactly where collisions occur. New regression test uses literal
   identical timestamps (not fake timers, which broke the IndexedDB
   polyfill with a 5s timeout) and asserts both correct order and that
   the tie was genuinely broken (`occurred_at` values differ post-write).
2. **BC-P4C04-03 (corrections/useCaseId threading) wasn't verified
   end-to-end** — only single-hop reducer tests existed; nothing drove a
   real correction through the full UI and confirmed it survived to the
   `graph_confirmed` audit event. **Fixed**: new acceptance test clicks
   the real "Edit" button in graph_review, proceeds through the full flow,
   confirms, then asserts `graph_confirmed`'s `payload.corrections_count === 1`.

**Pass 2:** independent reviewer re-verified both fixes against actual
current code, ran the full suite 3 consecutive times (109/109 passing,
zero flakes each run), confirmed the monotonic bump never fires on
uncontested writes (verified against `audit.test.ts`'s first test, which
uses an exact-equality assertion that would break if the bump altered
`occurred_at` unnecessarily), and confirmed Vitest's per-file module
isolation means `lastOccurredAtMs` doesn't leak across test files.
Converged, zero new findings.

## Notes for Downstream Chunks

- **This is the gating chunk for Phase 5+** — P5-C01 (verdict display +
  correction flow), P5-C02 (reasoning trace), and P6-C01 (register view)
  can all now build against a real `graph_confirmed`/`verdict_produced`
  audit trail with guaranteed chronological ordering.
- **The monotonic `lastOccurredAtMs` tie-breaker only guarantees ordering
  within a single browser tab session** — it resets on page reload. This
  is an honest V1 limitation (same class as the append-only "DevTools can
  still delete records" limitation already documented in
  `verdict-audit.md`) — cross-session/cross-tab event ordering still
  relies on `occurred_at` alone, which remains correct for events more
  than 1ms apart (the overwhelming majority) but could theoretically tie
  again if two tabs write within the same millisecond. Flag for the
  eventual V1.5 server-backed audit log.
- **`VERDICT_READY` no longer takes an external payload** — any future
  code dispatching it should not try to pass a `verdictId`; it's derived
  from `state.useCaseId` automatically.
- **P5-C01's correction flow** (spec: `VerdictDisplay.tsx`'s "Correct a
  classification" transitions back to `graph_review`) will need a new
  reducer action distinct from the initial `GRAPH_EXTRACTED` →
  `graph_review` transition, since it must carry `originalVerdictId`
  forward per `verdict-audit.md §6.1` — not addressed in this chunk.

## Retrospective

**Harder than expected:** the audit-ordering bug was genuinely hard to
catch — it only manifested when running the full suite (test-file
composition affected timing enough to sometimes avoid the collision), not
in isolation, and required actually reproducing the flake multiple times
to be confident the fix was real rather than coincidentally passing.

**Easier than expected:** because the reducer was already well-typed and
each state transition explicit, threading `useCaseId`/`corrections`
through the new states was mechanical — TypeScript caught every call site
needing an update.

**What I'd do differently:** this is the second chunk in a row (after
P4-C03's contradiction-resolution gap) where a "must not silently pass"
requirement had a check that looked sufficient on first read but wasn't
verified under real timing/composition conditions. Worth treating any
fix involving timestamps, ordering, or concurrency as requiring an
explicit multi-run stability check before considering it done, not just
a single green test run — codifying this as a standing self-review step
for any future chunk touching audit/ordering logic.
