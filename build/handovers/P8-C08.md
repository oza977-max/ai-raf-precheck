## Code Review Findings

**Review passes:** `[(1, 0)]` — but the substantive finding in this chunk came
from **mutation testing, not from review**, and it was mine.

**A test that could not fail, caught before commit.** TC-R3-NF-2-02 (sign-off
writes exactly one event under double submission) was first written with two
awaited `userEvent.click` calls. Deleting the synchronous `useRef` guard left
it green: an awaited click completes the entire handler before the next
begins, so the guard was never exercised. Rewritten with two synchronous
`fireEvent.click` calls.

**And the rewrite's own claim was also wrong.** The new comment asserted that
the synchronous version exercised the ref guard. Mutation says otherwise: in
jsdom each `fireEvent` flushes React's re-render before the next, so the
button's `disabled={busy}` catches the second click and removing the ref alone
still leaves the test green. Removing **both** layers fails it.

The honest framing, now in the test: it asserts the **requirement** — exactly
one event appended — not any one mechanism. The ref still earns its place,
because in a real browser two clicks can land inside a single tick where a
state update is too late; jsdom cannot reproduce that faithfully. Recorded
rather than papered over, because a comment claiming a test proves something it
does not is worse than no comment.

## Notes for Downstream Chunks
Phase 8 is complete; there is no downstream chunk. Two things a future round
should know:

- `twoloD_reviewed.verdict_id` is now required by the type. Anything
  constructing that payload must supply the id **of the verdict that was
  rendered**. Re-deriving it at write time reopens the race §13.4 closes.
- `verdictStillCurrent()` reads the trail at write time to **detect** a change
  and compares against what was rendered. Reading to detect is not the same as
  deriving to write — that distinction is the whole design.

## Retrospective
The chunk itself was small: a field, a thread, a guard. What took the time was
the last requirement in the phase, and it was the one that had gone untested
for the longest — the double-submission guard that §15.3 called "unchanged and
still required" while nothing checked it.

Two drafts of that test could not fail, and both looked convincing. The first
because an awaited click serialises the handler; the second because jsdom
flushes a re-render between synthetic events. Neither would have been caught by
reading the test — only by deleting the code it claimed to protect and watching
it stay green. That is now three times this round that the pattern has appeared
(P8-C05's null fixture, P8-C07's default parameter, and this), and every time
the test was green and the reasoning in the comment was wrong.

The lesson worth carrying out of Phase 8: **green is not evidence. Deleting the
code the test protects is.** Cheap, mechanical, and it has caught something
every single time it was run this round.
