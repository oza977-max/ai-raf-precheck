## Code Review Findings

**Review passes:** [(1, 2), (2, 0)]

**Pass 1 findings (both fixed):**

1. **`binding_constraint` leak (Important)** — on a clean `approved` verdict
   (nothing tripped), `evaluate.ts` was setting `binding_constraint` to the
   matched track rule's id, misleadingly implying the track rule "bound" an
   outcome that was actually unconstrained. Fixed: `binding_constraint`
   is now `''` when nothing tripped. Regression test added asserting this
   on the approved path.
2. **`tier.ts` unsafe cast (Important)** — `assignTier()` did
   `rule.name as Tier` with zero runtime validation; an unrecognized tier
   name would silently corrupt the `TIER_ORDER` comparison and under-tier a
   use case with no error surfaced anywhere. Fixed two ways: (a)
   `policy.ts`'s `validateTiers()` now fails loud at load time if
   `TierRule.name` isn't one of the four canonical tiers, (b) `tier.ts` adds
   a defense-in-depth skip (`if (!(rule.name in TIER_ORDER)) continue`) so
   even an unvalidated policy can't corrupt the comparison. Regression tests
   added at both layers.

**Pass 2:** Independent reviewer re-verified both fixes against the actual
current code (not the pass-1 report), confirmed the regression tests
genuinely exercise the fix (not tautological), confirmed the untouched
hard-line-rejection and unsatisfiable-invariant `binding_constraint` paths
are still correct, and found zero new issues in the diff. Converged.

**Noted but not blocking (documented deviation, not a defect):**
`resolveActivePacks()`'s computed per-jurisdiction warnings are currently
discarded — `EvaluationResult` has no field to carry them yet, and no
pack-loading chunk exists to populate real packs. Flagged for whichever
future chunk lands jurisdiction packs.

## Deviations from Spec

1. **`resolveActivePacks()`/`applyJurisdictionOverrides()` are pass-through
   stubs** — no pack-loading chunk exists yet (P2-C03 is human-led pack
   authoring, not yet built). `resolveActivePacks()` returns a warning for
   every jurisdiction code (spec-mandated behavior for "no pack registered").
   `applyJurisdictionOverrides()` returns `baseTrack`/`baseTier` unchanged
   with `appliedOverrides: []`. This is a known, spec-acknowledged gap
   flagged in the build prompt, not a chunk defect.
2. **`greedy-solver.ts` is a literal stub** (`{ ok: true, controls: [] }`
   unconditionally) per BC-P3C01-01 — P3-C02's explicit scope.
3. **Hard-line rejection reports `tier: 'Critical'`, `track: 'I'`** as
   ceiling placeholder values, since the spec doesn't assign tier/track on a
   hard-line trip (tier/track assignment is skipped entirely per step
   ordering). Documented inline in `evaluate.ts` — downstream consumers
   should key off `status`/`binding_constraint`, not tier/track, for
   hard-line rejections.
4. **`evaluate()`'s signature changed** from `EvaluationResult` (P1-C01/
   P2-C01 stub shape) to `Result<EvaluationResult, EngineError>` — only
   `no-track-match` produces an `Err`; a `rejected` verdict is a normal `Ok`
   value (rejection is a valid verdict, not an engine error). Upstream fix
   applied to `IntakeFlow.tsx`.

## Retrospective

**Harder than expected:** the `DataFlowGraph`/condition-field drift between
`policy-schema.md`'s example conditions and `intake-flow.md`'s actual graph
schema (`decision_type`, `hitl`, `output_reversibility` missing/mismatched)
required a build-prep spec fix before any code could be written — the same
shared-rule-24 pattern as P2-C01's policy field drift, now three-for-three
across this build.

**Easier than expected:** using the real `policy/appetite.yaml` (already
regenerated correctly in P2-C01) as the primary test fixture for
`evaluate.test.ts` meant the pipeline tests exercise real policy content
from day one, not synthetic fixtures — caught the track-matching
graph-fixture gaps immediately (empty graphs legitimately produce
`no-track-match`, which surfaced a real usability issue in the smoke path
that a synthetic always-passing fixture would have hidden).

**What I'd do differently:** the tier-name-as-cast issue (finding 2) is
exactly the kind of "policy author writes something slightly wrong and
nothing catches it until runtime" risk this project's determinism/audit
principles exist to prevent — worth scanning `tier.ts`/`track.ts` for
similar free-text-to-typed-enum casts before P3-C02 lands, in case the same
pattern recurs in the control library's `id` matching.
