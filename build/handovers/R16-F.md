## Found and fixed while verifying (main loop, after the build agent reported)
Each is inside an approved finding's scope, each now has a test:
1. **F-5 stopped one level short** — nested schemas inside a payload (graph
   correction, verdict caveat, rule rationale, tripped invariant, verdict
   conditions) still stripped unknown keys, so the same false "tampered" could
   happen one level down. Now passthrough too (TC-R16-F-60).
2. **The tick-all editor ticked the wrong box** — it was one `<label>` around all
   four checkboxes, and a label's control is its first input, so clicking any
   option's words ticked "Nothing beyond…". Now a `<fieldset>` with a legend, each
   option its own label (TC-R16-F-61).
3. **Engine jargon on the plain form** — a refused tick-all answer showed the
   engine's reason ("system_access_scope must have at least one value"), and
   unticking every Q13 box raised it as an alert. Now one plain sentence
   (`ACCESS_SCOPE_REFUSAL_TEXT`), and nothing ticked is just "not answered yet"
   (TC-R16-F-38, -39, -62).
4. **An untested path described as tested** — test-cases-022 said the correction
   handler's access-scope check was "exercised indirectly", but those tests used a
   stand-in. The same-set check moved to the engine (`sameAccessScopeSet`) and is
   unit-tested; the real handler is driven end to end (TC-R16-F-63, -64).
5. **"Please double-check" repeated itself** — one warning per affected part of the
   case showed the identical sentence twice; the build's own test had sidestepped
   it by adjusting its fixture. Now each message shows once (TC-R16-F-65).
6. Two stale/garbled comments corrected (`IntakeFlow.tsx` form-submit guard,
   `handoff.ts`).

## Known, carried forward (not fixed here)
- **A form-path correction can dead-end.** During a correction of a form-built case,
  "Change an answer" (and now an evaluation failure) returns to the form without the
  original result's id, so the re-confirm is refused as "already has a result" —
  safe (nothing is written; before F-1 this path wrote duplicates) but a dead end.
  R16-D2 v2 threads the id through the form path (`CORRECT_VERDICT_WITH_FORM`).
- **Register vs intake safeguard counts.** `RegisterDetail` renders `VerdictDisplay`
  without the graph, so evidence scoped to a platform or supplier cannot count as
  "already in place" there (the walkthrough saw 9 vs 10 for one case). Folded into
  R16-D2, which already changes the register's `VerdictDisplay` props.
- **Narrow screens.** The description path's review screen (`GraphView`, three
  columns side by side) squeezes to one letter per line in a narrow window — WCAG
  2.1 AA reflow (1.4.10) fails there. R16-E rewrites that screen and must cover it.
- Plausibility messages name the form's questions ("Where does the AI come from?")
  even on the description path, where those questions are not shown. R16-E's plain
  rewrite of that path must reconcile the wording.
