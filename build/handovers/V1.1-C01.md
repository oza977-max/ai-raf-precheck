# Handover: V1.1-C01 — Verdict Explainability + Intake UX (post-V1 fix chunk)

## Status: Complete
## Branch: main

## Origin

Not part of the original 16-chunk implementation guide. Four real product
gaps found by the user during live acceptance testing, explicitly
commissioned as a fix chunk. Full defect analysis and scope decisions in
`build/prompts/V1.1-C01.md`.

1. Zone A/B/C jargon unexplained anywhere in the UI.
2. "Review extracted graph" showed a flat list, not a graph.
3. The graph-review Edit button was a stub — it appended the literal
   string " (corrected)" to a label and recorded that as a correction.
   Real per-field editing never existed; tests asserted the stub.
4. Regulatory citations (`regulatory_basis` on hard lines/tracks) were
   computed by the engine and dropped at verdict assembly; `Invariant`
   lacked the field entirely; a bare "Approved" had no explanation.

## Key Insight

`assignTier`/`assignTrack`/`evaluateHardLines` already returned the full
rationale (matched rule, field, reason, citation) — `evaluate()` was
discarding it. ~80% of the engine work was carrying existing data
through, which is why determinism (NF-1) was trivially preserved.

## Retrospective

**What made this chunk fast:** the discovery that the rationale data
already existed at every layer — the entire "missing explanation" defect
was one assembly function discarding its inputs' richest fields. The
lesson for review discipline: a field that's computed and never consumed
is as suspicious as one that's consumed and never computed; no test ever
failed because nothing ever asserted the citations reached the user.

**The stub Edit button** survived five chunks because its tests asserted
the stub's own behavior. Acceptance tests written against a placeholder
UI harden the placeholder.
