## Behavior

- **Approve** (2LoD, `pre_checked` only, gated in JSX per BC-V12A-03):
  appends `twoloD_reviewed {action: 'approved', notes?}` (the decision),
  then `updateLifecycleStage(id, 'approved', role)` (the effect, which
  itself appends `lifecycle_stage_changed`) — first-ever use of the
  `twoloD_reviewed` event type. Sequential awaits + audit.ts's monotonic
  timestamps guarantee ordering.
- **Request correction**: appends `twoloD_reviewed
  {action: 'correction_requested', notes?}` only; stage stays
  `pre_checked` (§6's correction loop is submitter-driven; V1 records
  the request, no notification system).
- Timeline reloads after every action — new events appear immediately.

## Code Review Findings

**Review passes:** [(1, 1), (2, 0)]

**Pass 1 — 1 Important finding:**
- **No in-flight guard on the action buttons** — a double-click fired
  the async handler twice before React re-rendered a disabled state,
  writing duplicate `twoloD_reviewed` events (and a spurious
  `approved → approved` stage change) into the append-only trail. For
  this product specifically that's evidence pollution that cannot be
  cleaned afterwards, by design. Secondary: no try/catch, so a
  mid-sequence failure gave no user feedback.
  **Fix**: synchronous `useRef` in-flight guard (a ref, not state — two
  clicks can land before a re-render; same lesson as P7-C01's seed
  guard), `disabled={busy}` for visual feedback, try/catch/finally with
  a `role="alert"` failure message plus an unconditional timeline reload
  so the trail shows exactly what WAS recorded. Regression test added
  (`user.dblClick` → exactly one of each event in the real store).

**Pass 2 — verified the fix, converged, zero findings.** Honest caveat
recorded by the reviewer: under jsdom/act flushing, the regression test
cannot distinguish the ref guard from the disabled attribute alone
(user-event flushes state between the two clicks); it does fail against
the actual pre-fix code, so it guards the finding as reported. A
mechanism-level test (two raw `fireEvent.click`s in one act) was offered
as optional hardening — noted, not taken; the ref is defended by an
explanatory comment.

## Retrospective

The recurring theme of this whole build showed up twice more: (a) the
`twoloD_reviewed` event type sat unused for fourteen chunks — schema
without a consumer is a gap detector when you finally audit against a
design; (b) the double-click finding is P7-C01's StrictMode lesson in
user-interaction form — for an append-only evidence store, *any* path
that can fire a write twice is a data-integrity bug, not a UX nit.
