## What was built (one line per contract item)

- **§1 — one assumption shape, carrying its own fields (D-95).**
  `AssumptionRef`/`Assumption` gain `fields: string[]`; `assume()` in
  `plain-intake.ts` takes a third argument at all 13 call sites plus the
  `3platformZone` direct push; `Assumption` gains `shortLabel` (new
  `ASSUMPTION_SHORT_LABEL` map, `plain-copy.ts`). The guard test
  (`TC-R16-D2-19`) rebuilds the graph from each "Not sure"/"dont-know"
  answer and from every one of the question's other answers and asserts
  the union of differing graph fields equals the mapping's own reported
  `fields`, for all 14 questions.
- **§2 — the "No" screen (VD-10).** `buildVerdictView` gains a trailing
  options object (`assumptions`, `packs`, `evidenceScope`) and computes
  `VerdictView.no: NoScreenView` for every rejected verdict — `kind`
  (`hard_line` | `pack_hard_line` | `unsatisfiable` | `other`), `reason`,
  `change`, `contributingAssumptions`, `otherAssumptionCount`. All four
  "why"/"what would change" text variants, the contributing-assumption
  line with its pointer clause, the reworded single correction control,
  and the unconditional "who to talk to" line are rendered by `FirstScreen`
  (`VerdictDisplay.tsx`). The reviewer section's own, second correction
  control does not render on a "No". Pack hard lines gain optional
  `plain_reason`/`plain_change` (engine type, `packs.ts` zod schema,
  `policy-references.ts` placeholder scan) — no shipped pack uses pack
  hard lines; tests use fixture packs.
- **§2 item 7 — the reviewer section lists every assumption.** A new fold,
  "Answers the submitter wasn't sure about", renders whenever
  `assumptions` is non-empty — for ANY verdict, not only a rejected one
  (a case fact; see "Decisions the contract left to me" below).
- **§3 — assumptions reach the result screen (D-96, DR7-15).**
  `IntakeFlow.tsx` reads `assumptions`/`plainAnswers` out of the
  confirmation state before the `CONFIRMED` dispatch (beside the existing
  `resolutions`/`answerContexts` reads) and keeps them in a new
  `lastConfirmed` state, set beside `lastGraph` in `runConfirmAndEvaluate`
  — covering both a fresh confirm and a correction. `VerdictDisplay` gains
  `assumptions?`/`packs?`/`evidenceScope?` props; the intake verdict screen
  passes `lastConfirmed.assumptions` and `loadedPacks`.
- **§4 — saving assumptions with the case (D-81, DR7-16/19).**
  `graph_confirmed` gains optional `assumptions` (written only when
  non-empty); a correction writes them on `verdict_corrected` instead —
  `graph_confirmed` is never written on a correction. `RegisterDetail`
  reads them through `currentVerdictAttestationFields`, extended with this
  field (both directions tested: uncorrected vs. corrected). `eventDetail`
  adds "N answer(s) was/were 'Not sure'." to both the `graph_confirmed`
  and `verdict_corrected` lines when present (singular/plural handled).
  Hand-off import validates each element (`questionId`, `fields`, the
  three bounded strings) — valid, missing, and malformed all tested.
  Every lookup tolerates an unknown `questionId`/field.
- **§4b — register/result "already in place" parity (D-97, W-7).**
  `verdict_produced`/`verdict_corrected` gain optional `evidence_scope:
  { platform?; vendor? }`, written spread-if-present from the processing
  node at evaluation. `evidenceApplies`/`safeguardStatus` take an optional
  fallback scope, consulted only when `graph` is absent. `RegisterDetail`
  reads `evidence_scope` via `findLatestVerdictEvent` and now also loads
  packs itself (`loadPacks(getPackSources())`, mirroring `IntakeFlow.tsx`'s
  own independent load — see "Decisions" below). Same case, same "already
  in place" text proven on both the intake screen and the register
  (`TC-R16-D2-36` / `TC-R16-D2-46`).
- **§5 — correcting a form-path verdict through the form (D-82,
  DR7-17/22).** New reducer action `CORRECT_VERDICT_WITH_FORM`;
  `handleCorrectVerdict` dispatches it when `lastConfirmed.plainAnswers`
  exists for a form-built graph, else falls back to `CORRECT_VERDICT`.
  `originalVerdictId`/`originalGraph` (both new, optional) thread through
  `graph_extraction`/`questionnaire`/`contradiction_review`/`confirmation`/
  `evaluation_pending` in parallel with `originalVerdictId`'s own existing
  path — `CHANGE_ANSWER`, a genuine `EVALUATION_FAILED`, and the
  questionnaire's own `STEP_BACK` all keep the correction (the last one is
  a deliberate extension beyond the contract's own v2.1 list — see
  "Decisions"). The one-line correction-mode note renders above the form.
  New pure module `src/components/form-corrections.ts`: diffs the
  original and resubmitted graphs by node ROLE (never by id), over the
  union of each node's own keys (bar `id`), with inputs/jurisdictions each
  one synthetic correction on sentinel node ids `inputs`/`graph` compared
  as sorted sets. Every correction carries the new optional
  `correction_source: 'form' | 'review' | 'question'` (`GraphView`'s
  editor and the jurisdictions panel set `'review'`; a questionnaire
  write-back sets `'question'`). A zero-change resubmission writes
  `verdict_corrected` with no `graph_corrected` events and
  `corrections_count: 0`. Proven end-to-end against the real App: a real
  correction (two `graph_corrected`, `correction_source: 'form'`, against
  the original node ids), a zero-change resubmission, "Change an answer"
  mid-correction, and a double-click during a correction's confirm all
  write exactly what they should (`TC-R16-D2-48..51`).
- **§6 — "Corrected N times" (DR7-09, D2 part).** `RegisterDetail` adds
  the line when `correctionCount > 0`, counting `verdict_corrected`
  events.
- **§7 — evidence claims name their tool (DR7-34).** `VerdictView` gains
  `inPlaceScopeName?: string` (`resolveInPlaceScopeName`); the existing
  "Already in place" note is extended — never duplicated — to "…(your
  firm's records show this for {plain name})" when at least one in-place
  safeguard's evidence is scoped and matches; the platform's name wins
  when both a platform and a vendor match.
- **§8 — tests, test cases, specs.** `test-cases/test-cases-023.md` (+
  `.html`, generated via `scripts/test-cases-html.py`), `TC-R16-D2-01`
  through `-58`. Both twins edited for `specs/verdict-audit.md` (§4.3,
  §5.5, new §5.9, new §6.5), `specs/intake-flow.md` (new §24),
  `specs/policy-schema.md` (§10d amendment).

## Deviations from the contract, and decisions the contract left to me

- **The reviewer section's new assumptions fold renders for every
  verdict with assumptions, not only a rejected one.** §2 item 7 is
  written inside the "No" screen's own numbered list, but nothing in it
  (or elsewhere) says the fold itself is "No"-specific, and the data it
  needs (`assumptions`) now flows generically through `buildVerdictView`
  for every verdict. I read "the reviewer section... lists EVERY
  assumption the case has" as a case fact worth showing regardless of
  outcome, and implemented it that way (`TC-R16-D2-37/38/39` cover both).
- **`RegisterDetail` now loads jurisdiction packs itself.** Not explicitly
  asked for — the contract's §4b text is about `evidence_scope`, and
  never mentions packs for the register path. But the "No" screen's
  pack-hard-line branch needs `options.packs` to resolve correctly, and
  without this a 2LoD reviewer opening a pack-hard-line rejection from the
  register would see the WORSE, generic "an id found nowhere loaded"
  fallback instead of the real reason and jurisdiction — a visible
  disagreement with what the submitter saw, which is exactly the kind of
  gap §4b's own principle ("the register and the result screen agree")
  exists to close. Added `loadPacks(getPackSources())` in
  `RegisterDetail.tsx`, the same independent-load pattern `IntakeFlow.tsx`
  already uses for the identical data.
- **`STEP_BACK` from the questionnaire, during a correction, now also
  carries `originalVerdictId`/`originalGraph` back to the form.** The
  contract's v2.1 "every way back into the form keeps the correction" item
  names `CHANGE_ANSWER` and a form-path `EVALUATION_FAILED` explicitly,
  and separately confirms `STEP_BACK` FROM the form is already a no-op.
  It does not mention `STEP_BACK` FROM THE QUESTIONNAIRE back to the form
  — but before this fix, that transition (verified at intake-state.ts's
  `STEP_BACK` questionnaire case, the `graph_extraction` destination
  branch) carried `plainAnswers`/`assumptions` but neither
  `originalVerdictId` nor `originalGraph`, which is the IDENTICAL
  "orphaned correction" dead end the contract closes for the other two
  controls, just reached by a different one. Fixed it for consistency
  (`TC-R16-D2-53`), on the reasoning that leaving it would reintroduce the
  exact bug class this chunk exists to close.
- **`verdict_corrected` gains a new optional `corrections_count: number`
  field** — not named anywhere in the contract, which only says
  `eventDetail` should render a zero-correction resubmission as a
  re-check. I considered having `eventDetail` infer this from context
  (the surrounding events) but that would need its signature to take the
  whole trail, a bigger and riskier change to an already heavily-tested,
  single-event function; a field mirroring `graph_confirmed`'s own
  pre-existing `corrections_count` (same concept, same place) is minimal,
  consistent, and keeps `eventDetail`'s signature untouched.
- **The lower-right apostrophe-grammar bug I found and fixed while
  writing tests, not specified by the contract.** My first implementation
  of the hard-line/CS-2 "Why" composition produced a double period
  ("...for you.. That's a line...") or a period directly followed by a
  comma ("...for you., and your firm...") whenever the §4.4 fallback (no
  `plain_reason`) was used, because the fallback's own text already ends
  in a full stop (the shared pointer sentence) and my template
  unconditionally appended more punctuation after it. Caught by my own
  test (`TC-R16-D2-02`) failing on the exact string, not by inspection —
  fixed with a `withoutTrailingPeriod()` helper applied at both
  composition sites, rather than loosening the test to match the bug.

## Found and fixed while verifying (main loop, after the build reported)

Each is inside the approved contract's scope; each now has a test.

1. **The "never to an empty form" guard was not built** — though this
   handover's "What was built" and "Not built" sections said nothing was
   skipped. The contract's §5 v2.1 says a correction without its form answers
   (the `CORRECT_VERDICT` fallback) must return to the review screen, "never
   to an empty form". The build sent all three routes back to the form
   unconditionally; on that path the form opens empty, and a resubmission
   would rebuild the case from blank answers and, with no original graph to
   diff against, record "Re-checked — no answers changed" — a false record on
   the append-only trail. Now one rule, `returnsToForm` in `intake-state.ts`,
   decides all three routes (TC-R16-D2-59 to -61).
2. **Pack countries were printed as codes.** The "No" screen used the pack's
   `jurisdiction` value directly ("EU"), where the contract asks for the plain
   name. The tests passed only because their sample packs spelled the code
   out as words ("the European Union") — the same bent-sample-data pattern
   R16-F's verification caught. Now the policy's own name, with "the" where
   English needs it; an unlisted code reads "the countries it involves"
   (TC-R16-D2-62; sample packs now use real codes).
3. **Garbled fallback sentences.** "Caught by my own test" above was half
   right: the fix left "…for this exposure Ask your AI risk team what this
   means for you, and your firm has no safeguard that resolves it." — and the
   test pinned that sentence. Now the description is closed as a sentence and
   the pointer follows the whole "Why" sentence. The same missing full stop in
   D1's older fallbacks is fixed too (`invariantPlainReason`, the safeguard
   fallback), updating TC-R16-D1-02e/02f, which had pinned the run-on text.
4. **An internal id could reach the first screen.** The evidence note fell
   back to a platform's or supplier's id when it had no plain name; it now
   stays generic (TC-R16-D2-63).
5. **"v1 → v1".** A correction through the form rebuilt the graph at version
   1, so its correction records read v1 → v1. The rebuilt graph is now
   numbered one above the original (TC-R16-D2-48 strengthened).
6. **My own regression, caught by the ritual.** The first version of fix 3
   crashed the whole sign-off page for a stored control with no description
   (37 tests failed, every run). The full-stop helper now tolerates a missing
   description and degrades to "{name}. {pointer}" (TC-R16-D2-64).
