# Handover: V1.3 — Proof-Carrying Controls

## Status: Complete — CLOSES THE V1.x DESIGN-GAP PLAN
## Branch: main

## Origin

Fourth and final V1.x chunk of the design-gap plan
(`build/design-gap-audit.md` item A7; design-vision decision #3: "a
required control is not a checkbox — VERIFIED or UNVERIFIED, with a
`verification_evidence` field from the start even where V1 attests
manually").

## What shipped

- **Schema (additive)**: `Control.verification_evidence?:
  { status: 'verified' | 'unverified'; detail?; attested_by?;
  attested_at? }` in types + Zod. **Absent = UNVERIFIED** — the honest
  default (BC-V13-02); a stale verdict-vs-policy control id also renders
  UNVERIFIED (fail-safe direction, review-traced).
- **Zero engine changes** — status is policy data resolved at display
  time by id (the `findRuleDescription` pattern); the verdict's
  `controls: string[]` contract and determinism untouched.
- **Starter YAML**: one worked example on CTRL-ENC-01 (`verified`,
  platform TLS attestation) with `[FIRM]`/`[DATE]` markers — mechanism
  demonstrated inside the template's adoption-required convention; the
  NF-10 banner correctly stays up since the attestation is unfilled.
- **UI**: the bare "Controls required:" line becomes the design's
  **MINIMAL CONTROL SET (CS-1)** panel — per control: id, name,
  "Patches: {invariants}", VERIFIED/UNVERIFIED chip, evidence +
  attestation line when verified. Subtitle states the V1 reality
  plainly: "statuses are attested in the policy file; machine-checked
  evidence binding is V1.5" (BC-V13-01). Legacy render paths without a
  policy prop degrade to the plain id list, zero chips (BC-V13-03).
- Spec sync in both `policy-schema.md` and `.html` (BC-V13-04).
