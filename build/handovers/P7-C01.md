## Code Review Findings

**Review passes:** [(1, 1), (2, 0)]

**Pass 1 — 1 Critical finding:**
- A TOCTOU race in `seedAigateSelfAssessment()`: React StrictMode
  (confirmed present in `src/main.tsx`) double-invokes mount effects in
  dev, so `App.tsx`'s `useEffect` could call the seed twice concurrently.
  The read-then-write existence check (`getUseCase()` then later writes)
  had no synchronization — both concurrent calls could pass the
  existence check before either had written anything, producing
  duplicate `graph_confirmed`/`verdict_produced` audit events (a real,
  silent audit-trail duplication) before a later `addNode()` call threw
  a caught-but-messy `ConstraintError`.
  **Fix**: a module-level in-flight promise cache — concurrent calls
  collapse onto the same in-progress promise, with the actual seed logic
  moved into a private `runSeed()` function. A regression test using
  `Promise.all([...])` (true concurrent dispatch, not sequential awaits)
  was added, asserting exactly one register node and exactly one
  `verdict_produced` event survive two racing calls.

**Pass 2 — verified the fix, 0 findings:**
- Confirmed the synchronous check-and-set has no `await` between the
  `if (!inFlight)` check and the `inFlight = runSeed(...)` assignment,
  so JS's single-threaded execution model closes the window entirely —
  a second synchronous call always observes the already-set `inFlight`.
- Confirmed `.finally()` correctly resets the cache on both success and
  failure, so a genuinely later/separate seed attempt isn't permanently
  blocked.
- General sanity pass on `App.tsx` and `RegisterView.tsx` — no further
  issues.

## Retrospective

**Harder than expected:** the concurrency race wasn't visible from
sequential test execution or code read-through alone — it only surfaced
because the independent review agent traced `main.tsx`'s actual
`<StrictMode>` wrapper and reasoned about dev-mode double-invocation
semantics specifically. A useful reminder that "idempotent" needs to
mean "safe under concurrent calls," not just "safe when called twice in
sequence."

**Easier than expected:** everything else — the seed logic itself
reused `evaluate()`/`routeToWorkflow()`/`register.ts`/`audit.ts` exactly
as `IntakeFlow.tsx` already does, so there was very little genuinely new
logic to get wrong.

**What I'd do differently:** write the concurrent-call test as part of
the initial TDD pass, not just after a review finding — the race was
foreseeable given React StrictMode is a known, standing fact about this
codebase's entry point.
