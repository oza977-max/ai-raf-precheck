## Notes for Downstream Chunks

- **`.md` and `.html` spec files are maintained as parallel duplicates
  with no generation link between them** — a real, standing risk that
  future spec edits will only touch one format and silently drift from
  the other again. `spec-parity-check.py` only checks `.md` files by
  design (that's the format read by build tooling and specs consumed by
  `/gvm-build`); if `.html` files are meant to stay in sync, a future
  chunk should either add `.html` to the parity script's scope or
  establish a generation step so `.html` is derived from `.md`
  automatically rather than hand-maintained.
- **P7-C03** (final chunk) — no specific carry-over from this chunk;
  `exportAll()`'s consumer call site (this chunk's whole point) is now
  live, closing that item off implementation-guide.md's wiring matrix.

## Retrospective

**Harder than expected:** getting `spec-parity-check.py`'s R1/R3/R5
regexes correct on the first pass — an early bug (requiring `|` to
immediately follow `=\s*` with no allowance for leading whitespace on
subsequent union-member lines) silently truncated multi-line union
extraction to just the first member, which would have made the script
look like it was checking something it wasn't. Caught by deliberately
injecting known defects and confirming they were flagged, not just by
observing a clean baseline run (a clean run alone proves nothing about
whether the checker actually checks anything).

**Easier than expected:** the export button itself — reusing the
existing `exportAll()` store function meant there was no new business
logic to get wrong, just browser-API plumbing.

**What I'd do differently:** when fixing spec drift found by a new
automated checker, immediately grep across BOTH `.md` and `.html`
formats in the same pass, rather than discovering the `.html` half in a
second review round. The parity script's own scope boundary (`.md`
only) should have been a prompt to explicitly check the unchecked format
too, not just the checked one.
