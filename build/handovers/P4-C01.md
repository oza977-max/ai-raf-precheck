## Code Review Findings

**Review passes:** [(1, 3), (2, 0)]

**Pass 1 findings:**

1. **CRITICAL — weak response validation.** `parseDataFlowGraph()`
   originally only checked that top-level arrays existed, never validating
   individual node fields against the canonical enum vocabulary. A
   malformed or near-miss LLM response (e.g. `data_class: "PII"` instead
   of the canonical `"Client PII"`) could silently pass through into
   `evaluate()` and produce a wrong verdict — a severe correctness bug for
   a compliance product whose value proposition is deterministic
   correctness. **Fixed**: replaced with a real Zod schema
   (`ExtractedGraphSchema`, built from per-node-type sub-schemas) that
   validates every field against the canonical vocabulary via
   `.safeParse()`; failure returns `parse-error`, never a malformed graph.
   Two regression tests added (near-miss enum value, missing required
   fields) — both confirmed genuinely exercising the fix, not tautological.
2. **IMPORTANT — hardcoded enum duplication (drift risk).**
   `graph-extractor.ts` redeclared its own copies of the canonical
   vocabulary arrays instead of sharing a single source with
   `policy.ts`'s `CANONICAL_VOCABULARY` — no compiler-enforced link between
   them. **Fixed**: extracted `src/engine/canonical-vocabulary.ts` as the
   shared source; both `policy.ts` and `graph-extractor.ts` now import
   from it. Confirmed `policy.test.ts` still passes unmodified (pure
   refactor, no behavior change).
3. **IMPORTANT — dropped `policyPermittedValues` parameter.** `extractGraph()`
   doesn't accept a policy-scoped permitted-values argument per
   `intake-flow.md §4.1`'s literal signature — the canonical vocabulary is
   fixed and baked in directly instead. **Accepted as a documented
   deviation**, not fixed — flagged explicitly below as requiring product
   sign-off, since it means a bank can't restrict vocabulary narrower than
   the canonical set via policy today (e.g. disallow `agentic` model types
   firm-wide).

**Pass 2:** independent reviewer re-verified both fixes against actual
current code, traced the full `extractGraph()` → `parseDataFlowGraph()` →
`ExtractedGraphSchema.safeParse()` call path to confirm the Zod gate is
live (not dead code), confirmed the regression tests inject real bad SDK
responses via `mockResolvedValueOnce` rather than asserting tautologically,
and confirmed `policy.ts`'s extraction diff is a clean, behavior-preserving
subtraction. Zero new findings. Converged.

## Deviations from Spec

1. **`extractGraph()` doesn't accept `policyPermittedValues`** — see Code
   Review Findings #3 above. **Requires product/CRO sign-off** before a
   bank can rely on this for anything beyond the canonical vocabulary as
   currently baked in.
2. **`questionnaire`/`contradiction_review`/`confirmation` states exist in
   the type union but have no UI** — this is the documented P4-C01/P4-C04
   boundary from the build prompt, not a defect. `graph_review` proceeds
   directly to `evaluation_pending` via `PROCEED_TO_EVALUATION_PASSTHROUGH`.
3. **No `graph_confirmed` audit event is written in this chunk** — that's
   P4-C04's attestation semantics, not yet specified precisely enough to
   guess at safely. Confirmed via grep: the event type exists only in
   `store/types.ts`, never called from `IntakeFlow.tsx`.
4. **No structured-form fallback UI** — a no-API-key extraction failure
   shows a plain message ("structured-form fallback is not available yet
   in this build") rather than routing to a form, since `StructuredForm.tsx`
   is P4-C02's scope.

## Retrospective

**Harder than expected:** getting Zod's `z.enum()` to work cleanly with
runtime-shared (not `as const`) vocabulary arrays required a documented
type-cast at the end of `parseDataFlowGraph()` — Zod widens enum output to
`string` unless the input array is a literal tuple type, and making the
shared vocabulary module `as const` would have required touching
`policy.ts`'s existing `satisfies DataClass[]` pattern too. Kept the cast
narrow and commented rather than reshaping the shared module's typing
under review-fix time pressure.

**Easier than expected:** the reducer's separation from `IntakeFlow.tsx`
(TDD-driven, one file for pure state logic, one for rendering) made the
transition tests trivial to write and made the eventual review very fast
to verify — Dan Vanderkam's discriminated-union approach paid for itself
immediately.

**What I'd do differently:** the Critical validation gap (finding #1)
should have been caught during self-review before independent review, not
after — the build prompt itself flagged spec §4.4's Zod-schema requirement
and the LLM's tool_choice forcing was a plausible-sounding excuse for
skipping it. Worth treating "the API enforces the schema" as a claim to
verify, not assume, on every future LLM-boundary chunk.
