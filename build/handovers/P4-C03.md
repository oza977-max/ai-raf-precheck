## Code Review Findings

**Review passes:** [(1, 1), (2, 0)]

**Pass 1 finding (Critical, fixed):** `CONTRADICTION_RESOLVED` had no
reducer-level guard against an empty resolution — only a UI
disabled-button check in `ContradictionReview.tsx`. The explanation text
typed by the user was captured by the component then silently discarded
(never dispatched), and the reducer would transition
`contradiction_review → questionnaire` unconditionally regardless of
payload. **Fixed**: `CONTRADICTION_RESOLVED` now requires an
`explanation: string`, the reducer rejects empty/whitespace-only input at
the state-machine layer (not just the UI), and successful resolutions are
recorded in a new `resolutionNotes: string[]` field carried on the
`questionnaire` state — defense in depth, and the data is no longer thrown
away even though nothing reads it yet (see Notes for Downstream Chunks).

**Pass 2:** independent reviewer re-verified the fix against actual
current code — confirmed the reducer rejection returns the exact same
state object by reference (proving the early-return branch, not a
same-shape reconstruction), confirmed `IntakeFlow.tsx` no longer discards
the explanation, confirmed both `QUESTIONS_GENERATED` dispatch sites
produce the correct new shape with no `as any` casts anywhere, and traced
that `resolutionNotes` has no destination yet but nothing breaks from the
shape addition (grep confirmed only the reducer and its own test reference
it). Zero new findings. Converged.

## Deviations from Spec / Documented Judgment Calls

1. **"Worst-case" provisional tier** (§6) — uses the graph's
   already-extracted values directly rather than building a separate
   per-field worst-case substitution engine, since `extractGraph()`
   already instructs the LLM to fill uncertain fields with a concrete
   best-guess value, not leave them empty.
2. **`activePacks: JurisdictionPack[]` always `[]`** — no pack-loading
   chunk exists yet (same unresolved P3-C01 deviation). Pack-triggered
   questions (§6 selection logic step 3) never fire.
3. **`detectContradictions()` scoped to description-vs-graph only** — the
   spec's signature (`description, answers, graph`) doesn't give access to
   which graph field each `QuestionAnswer` targeted, so true
   answer-vs-answer contradiction detection isn't derivable from this
   signature. Implemented as a fixed table of 2 known signal pairs
   (client-data negation, autonomy negation), matching `intake-flow.md §5`'s
   own listed Pattern 1 example — not a general NLP solution.
4. **`resolutionNotes` is accumulated but not yet persisted anywhere**
   (audit trail, etc.) — genuinely out of scope for this chunk (no audit
   write chunk exists at this granularity yet), but no longer silently
   discarded either.

## Retrospective

**Harder than expected:** the field-linkage gap in
`detectContradictions()`'s spec signature required a genuine scoping
decision rather than a mechanical implementation — worth flagging that
this pattern (a spec citing a function signature that doesn't carry enough
context for its own stated purpose) has now shown up twice this build
(also P4-C01's `extractGraph()` permitted-values parameter).

**Easier than expected:** because the reducer was already
well-factored from P4-C01, adding four new transitions and two new state
shapes required no changes to unrelated states — the type system caught
every call site that needed updating.

**What I'd do differently:** the empty-resolution gap (pass-1 Critical)
is exactly the kind of "UI check without reducer-level enforcement" defect
this project's own BC-pattern naming convention is meant to catch before
review, not during it — worth explicitly checking "does every
user-blocking validation exist at the state-machine layer, not just the
component layer" as a standing self-review item for any future chunk with
a "must not silently pass" requirement.
