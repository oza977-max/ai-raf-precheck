# Build Prompt: P7-C02 — Export + Spec Parity Check Script

## Chunk Summary

Two independent deliverables: (1) an "Export JSON" button in
`RegisterView.tsx`'s 2LoD view (deferred from P6-C01, confirmed in scope
here per the wiring matrix), and (2) `scripts/spec-parity-check.py` — a
standalone Python script checking five cross-spec invariants (R1-R5).
The export button is user-facing (**TDD-1 applies**); the parity script
is a CI/review tool with no runtime consumer (wiring matrix's own
documented exemption: "internal helper, no consumer demanded").

## Spec Drift Found and Resolved Before Implementation

Building the parity checker required grounding each rule (R1-R5) against
the real spec text, which surfaced several genuine, pre-existing
spec-documentation bugs — fixed as small, safe doc corrections (not
touching any built code):

1. **`evaluation-engine.md`/`cross-cutting.md` referenced
   `src/engine/evaluator.ts` and `src/engine/control-solver.ts`** —
   aspirational filenames from before the code was built; the real files
   are `src/engine/evaluate.ts` and `src/engine/greedy-solver.ts`.
   Corrected.
2. **`implementation-guide.md §7`'s test co-location example** claimed
   engine/store tests live under a `__tests__/` subfolder
   (`src/engine/__tests__/evaluate.test.ts`), but the actual convention
   adopted since P1-C01 is sibling `.test.ts` files for `engine/`/`store/`
   — only `src/components/*` uses a `__tests__/` subfolder. Corrected to
   match the real, already-built convention.
3. **`policy-schema.md`** referenced `src/engine/policy-loader.ts`
   (never built under that name — the real loader is
   `src/store/policy.ts`, built in P2-C01). Corrected.
4. **`intake-flow.md §4.1`'s `extractGraph()` example signature** was
   stale relative to what P4-C01 actually built: the spec showed
   `extractGraph(description, apiKey, policyPermittedValues):
   Promise<Result<DataFlowGraph, LlmError>>`, but the real function
   (`src/llm/graph-extractor.ts` line 169) is
   `extractGraph(description: string): Promise<LlmResult<DataFlowGraph>>`
   — the API key is read internally via `getApiKey()`, and permitted
   values come from `canonical-vocabulary.ts`'s shared runtime constants
   (a P4-C01 review fix), not a caller-supplied parameter. Corrected the
   spec example to match the real, already-shipped signature. Also fixed
   a bare typo in the same section: `exposure: ExposureLevel` →
   `exposure: Exposure` (the real type name in `src/engine/types.ts`).

## Design Notes for `scripts/spec-parity-check.py`

- **Scope boundary**: only TypeScript identifiers/literals inside fenced
  ` ```typescript ` code blocks are checked (plus inline `` `src/...` ``
  path references for R4). Prose — including the ASCII lifecycle-stage
  transition diagram in `register-lifecycle.md §6` (which uses the
  display name "Rejected" for a terminal outcome, conflating the
  verdict's `status: 'rejected'` with a lifecycle stage in human-readable
  text) — is documentation, not a machine-checked contract, and is
  intentionally out of scope. Flagging prose diagrams would produce
  noise without real signal.
- **R2 is relaxed** (documented in the script's own docstring) to accept
  a type as "defined" if it exists either in a spec's fenced code block
  OR in the actual `src/` implementation — the literal spec wording ("in
  at least one spec") is too strict for implementation-only helper types
  that were never worth re-litigating back into prose after the chunk
  that introduced them shipped.
- **Verified against real defects, not just the clean baseline**: each
  of R1/R3/R4/R5 was sanity-checked by temporarily injecting a known
  defect (a bogus field claim, a bogus lifecycle stage in a literal
  array, a bogus file path, a bogus `AuditEventType` variant) and
  confirming the script actually flags it before reverting — not just
  that it passes on the unmodified spec suite.

## Deliverables

1. **`scripts/spec-parity-check.py`** (new) — `check_r1()` through
   `check_r5()`, `main()` returns 0 (clean) / 1 (findings) / 2 (script
   error). Executable (`chmod +x`).
2. Five small spec-doc corrections (see drift #1-4 above) — no code
   changes, no test changes required for these.
3. **`src/components/RegisterView.tsx`** — "Export JSON" button, 2LoD
   view only, per `register-lifecycle.md §10.3`: calls
   `register.exportAll()`, wraps the result as `{exported_at, nodes,
   edges}`, triggers a browser download via a `Blob` + temporary anchor
   element.

## API Boundary Contracts

- `scripts/spec-parity-check.py` reads `specs/*.md` and `src/**/*.ts` —
  no runtime consumer, matches the wiring matrix's own documented
  exemption for this exact module.
- `RegisterView.tsx`'s export handler stays presentation-only: it calls
  `register.exportAll()` (existing store function, unchanged) and does
  browser-API DOM manipulation (Blob/anchor) inline, the same class of
  operation already used nowhere else in this codebase but permitted
  under Rule 4 (UI is presentation-only, no *business* logic — a file
  download trigger is a browser-API concern, not business logic).

## TDD Approach

**TDD-1 applies to the export button** (user-facing). Acceptance test:
`RegisterView.test.tsx` — in the 2LoD view, clicking "Export JSON"
triggers a download whose Blob content, when parsed as JSON, contains
`exported_at` (a valid ISO 8601 string) and `nodes`/`edges` arrays
matching what `register.exportAll()` returns. Since jsdom doesn't
support real file downloads, the test intercepts the anchor click via a
mocked `URL.createObjectURL`/`revokeObjectURL` and reads the `Blob`
passed to `createObjectURL` directly (TDD-2 mock budget: 1 — jsdom's
missing browser-download API, not test-writer convenience).

The parity script has no test framework of its own (Python, no
Vitest) — Hard Gate 8's smoke command IS the script's own exit code,
per the chunk's own stated acceptance criterion ("Parity script:
`python3 scripts/spec-parity-check.py` exits 0 on the current spec
suite").

## Review Criteria

**Experts loaded:** Kent Beck (TDD), Fowler (parser correctness — regex
edge cases around comments/whitespace), McConnell (defensive script
design — exit codes as a real contract other tooling might depend on).

**Known Patterns to Avoid:**
- BC-P7C02-01: the export button must be 2LoD-only, matching §10.3 and
  the button's own confirmed-out-of-scope status in P6-C01's handover.
- BC-P7C02-02: `spec-parity-check.py`'s exit codes must be exactly
  0/1/2 as specified — not a truthy/falsy Python convention mismatch
  (Python's own `sys.exit(True)` would be exit code 1, which happens to
  align, but the script uses explicit integer returns to avoid relying
  on that coincidence).
- BC-P7C02-03: do not flag register-lifecycle.md §6's prose ASCII
  transition diagram — it is intentionally out of the parity checker's
  scope (see Design Notes above).
