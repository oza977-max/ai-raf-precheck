## 1. The "No" screen (VD-10, §4.3)

When `verdict.status === 'rejected'` the first screen is, in order:

1. Headline **"No — not as described."** (already built in D1).
2. **Why.** Which rule said no:
   - `binding_constraint` is a firm hard line (`policy.hard_lines`): *Why:
     {plain_reason}. That's a line your firm never crosses, and no
     safeguard can make up for it.* — `{plain_reason}` resolved with the
     same `{audience}`/`{destination}` rules as D1; no `plain_reason` → the
     hard line's description + the §4.4 pointer line.
   - `binding_constraint` is a firm invariant (`policy.invariants`) — the
     unsatisfiable case (CS-2, no control in the library resolves it):
     *Why: {the invariant's plain_reason}, and your firm has no safeguard
     that resolves it.* (D-66)
   - anything else (a pack rule id, or an id not in the loaded policy):
     *Why: one of the rules your firm has adopted for the countries
     involved rules this out.* + the §4.4 pointer line. Never the bare id
     on the first screen (the reviewer section shows it).
3. **Answers you weren't sure about — only those that contributed (D-80).**
   R16 §4.3 says "when an assumed answer contributed". An assumption
   contributed when its question sets a graph field that appears in the
   binding rule's condition. Export from `plain-intake.ts` one table,
   `QUESTION_FIELDS: Record<QuestionId, string[]>` (the graph fields each
   question can set — Q3 data_zone + vendor, Q3a data_zone + vendor, Q4
   model_type, Q5 data_class, Q6 action_type + autonomy_level +
   decision_bindingness + hitl, Q7 exposure, Q9 output_reversibility,
   3platformZone data_zone, … — derive it from the mapping code itself and
   test it against `plainAnswersToFormValues` so it cannot drift). The
   binding rule's condition fields come from the hard line or invariant
   condition (`Object.keys(condition)`). When at least one assumption
   contributed: *This is based on answers you weren't sure about: {list of
   those questions' short text}. If any of them is wrong, change it and
   check again.* When none contributed, the line is absent (the other
   assumptions are still listed in the reviewer section — see §2).
4. **What would change the answer.**
   - hard line with `plain_change`: *What would change the answer:
     {plain_change} Then check again.*
   - hard line without `plain_change`, or a pack/unknown rule: *What would
     change the answer: change how it would be used, then check again. Ask
     your AI risk team what this means for you.*
   - CS-2: *What would change the answer: change how it would be used, or
     ask your AI risk team whether the firm can add a safeguard for this.*
5. A button: *If we've misunderstood how you'd use it, correct your answers
   and check again.* — the correction flow (§3).
6. *Who to talk to: your AI risk team — the independent team that checks
   how the firm uses AI — if you think this is wrong or want to discuss
   another way to do this.*
7. No safeguards list, no next-steps list, no "checks other teams run", no
   "who signs off". The reviewer section (collapsed, unchanged) follows.

The view-model computes all of this (one computation, as D1): add a `no`
block to `buildVerdictView`'s result (`reason`, `assumptionsThatContributed`,
`change`, kind `hard_line | unsatisfiable | other`) — `undefined` unless
rejected. `buildVerdictView` gains an optional `assumptions` argument
(last, so existing callers compile unchanged).

## 2. Saving the assumptions with the case (D-81)

Today assumptions live only in the intake session, so a case reopened from
the register cannot say which answers were guesses.
- `graph_confirmed` payload gains optional `assumptions: Array<{
  questionId: string; question: string; assumption: string }>` — written
  only when non-empty (spread-if-present, like `submitter_note`). On a
  correction pass (§3) the same field goes on `verdict_corrected` if that
  is where the correction's record lives; check which event the register
  reads for the current verdict and put it where the reader looks. Also
  record `description` on that event when the description differs from
  the one `use_case_created` holds (R16-W made question 2 editable — close
  that gap here).
- Types: `src/store/types.ts` payload union; the hand-off bundle's import
  schema (`src/store/handoff.ts`) accepts the new optional fields and
  rejects malformed ones (array of objects with three strings each);
  an older bundle without them still imports and verifies.
- `RegisterDetail` reads the assumptions from the current verdict's
  confirming event and passes them to `VerdictDisplay`, which passes them
  to the view-model. The intake verdict screen passes the session's.
- The reviewer section lists every assumption the case has (contributing
  or not) under *Answers the submitter wasn't sure about*.
- `RegisterDetail`'s event list renders the new fields in plain words
  (`eventDetail`): e.g. *Attested. Graph v1, 0 corrections. 2 answers were
  "Not sure".*
- Specs: `specs/verdict-audit.md` §4.3/§5 (payload + rendering) — both
  twins; the hand-off spec section that lists the import schema.

## 3. Correcting a form-path verdict through the form (D-82)

"Correct your answers and check again" (every verdict, D1 item 8, and the
"No" screen's button) dispatches `CORRECT_VERDICT`, which opens the old
field-card screen (`graph_review`). For a case that came from the guided
form, open the guided form instead, filled in with the answers it was
confirmed with:
- Keep the confirmed `plainAnswers` and `assumptions` available at the
  verdict step for the session (the reducer's `evaluation_pending` and
  `verdict` states, or the same `useState` that holds `lastGraph` — pick
  one and say why). If they are not available (e.g. after a reload, when
  the intake draft is cleared at the verdict), fall back to today's
  `graph_review` correction path unchanged.
- New action `CORRECT_VERDICT_WITH_FORM { originalGraph, useCaseId,
  originalVerdictId, plainAnswers, assumptions }` → `graph_extraction`
  (`method: 'form'`) carrying a correction context. The form opens filled
  in, with a one-line note above it: *You're correcting your earlier
  answers. Change what was wrong, then continue — the result will be
  worked out again and both versions are kept.*
- On Continue in correction mode: same `useCaseId`; **no**
  `use_case_created`; `FORM_SUBMITTED` (R16-W) carries `originalVerdictId`
  and the corrections; the flow continues to confirmation and, on Confirm,
  through the existing correction write path (`graph_corrected` per
  correction, then `verdict_corrected` — never `graph_confirmed` /
  `verdict_produced`).
- Corrections are field-level so the register's existing renderer stays
  readable: a pure helper `formCorrections(originalGraph, correctedGraph,
  { by, at, newId })` (in `src/components/`, ids and time injected —
  never generated inside) emits one `GraphCorrection` per changed field:
  processing-node fields and output-node fields against the corrected
  graph's node ids; the inputs' kinds as one correction on node id
  `inputs`, field `data_classes` (sorted arrays); jurisdictions on node id
  `graph`, field `jurisdictions` (the existing `JURISDICTIONS_SET`
  precedent). Unchanged fields emit nothing. Test every field kind, a
  no-change resubmission (zero corrections), and that `String(value)` of
  every emitted value renders readably in `RegisterDetail`'s event list.
- The in-flight guard: re-entering for a correction releases the confirm
  guard exactly as `handleCorrectVerdict` does today.
