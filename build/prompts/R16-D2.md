## 1. One assumption shape, carrying its own fields (D-95; DR7-19, DR7-24)

v1 keyed the "contributing" check on a form-only `QuestionId` table; the
description path's questionnaire answers could never match it, and a table
kept beside the mapping can drift. Instead, every assumption carries the graph
fields it set:

```ts
interface Assumption {
  questionId: string;        // a form QuestionId, or 'field:<graph field>' for a questionnaire answer (E)
  question: string;          // the full question, for the reviewer section
  shortLabel: string;        // e.g. "whether a mistake can be put right" — used in sentences
  assumption: string;        // what we assumed
  fields: string[];          // the graph fields this answer set
}
```

- **How `fields` is produced (new work — R16-F's `AssumptionRef` has no
  `fields` today, verified: src/engine/plain-questions.ts:35-37).** Each place
  the form mapping records a "Not sure" names the graph fields that branch
  sets: the local helper `assume(id, optionKey)` (verified:
  src/engine/plain-intake.ts:110-112) becomes `assume(id, optionKey, fields)`,
  and every call site passes the graph field names it sets on that branch
  (13 calls, verified: plain-intake.ts:138-543; plus the direct
  `3platformZone` push at :233). `AssumptionRef` gains `fields: string[]`;
  `describeAssumptions` copies it onto the worded `Assumption`. Field names are
  the GRAPH's (`data_zone`, `vendor`, `platform`, `model_type`,
  `autonomy_level`, `data_class`, `action_type`, `exposure`,
  `decision_bindingness`, `output_reversibility`, `replaces_prior_model`,
  `system_access_scope`, `multi_instance_coordination`, …), because the
  binding rule's condition keys are graph field names.
- The guard test (no hand-kept table survives unchecked): for every question
  that offers "Not sure", build the graph from the "Not sure" answer and from
  each of the question's other options (`plainAnswersToFormValues` then
  `buildGraphFromForm`, all other answers fixed); the union of graph fields
  whose value differs from the "Not sure" graph must EQUAL that assumption's
  reported `fields`.
- `shortLabel` lives in `plain-copy.ts` per question that offers "Not sure":
  3 *where the AI comes from* · 3supplier *which supplier it is* · 3a *which
  account you use* · 3aWhich *which company assistant it is* · 3platformZone
  *whether your information stays on your firm's systems* · 4 *what kind of AI
  it is* · 5 *what information it uses* · 6 *what it does with what it
  produces* · 6a *how much weight what it produces carries* · 7 *who sees what
  it produces* · 9 *whether a mistake can be put right* · 12 *whether it
  replaces something you use* · 13 *what it can get into by itself* · 14
  *whether copies of it work together*. (DR7-18: the full question text made a
  run-on sentence.)
- Existing `Assumption` readers (UnderstoodSummary, StructuredForm, the
  reducer states R16-W added) adopt the new fields; the summary keeps showing
  `question` + `assumption` as today.

## 2. The "No" screen (VD-10, R16.md §4.3)

When `verdict.status === 'rejected'` the first screen is, in order:

1. Headline **"No — not as described."** (built in D1).
2. **Why**, by the kind of rule that said no:
   - a firm hard line (`policy.hard_lines`): *Why: {plain_reason}. That's a
     line your firm never crosses, and no safeguard can make up for it.*
     (`{audience}`/`{destination}` resolved as D1 does; no `plain_reason` →
     the hard line's description + the §4.4 pointer line).
   - a firm invariant with no resolving control (CS-2): *Why: {the
     invariant's plain_reason}, and your firm has no safeguard that resolves
     it.*
   - **a pack hard line (DR7-20 — the owner did NOT accept a generic
     fallback):** pack `hard_line` effects gain optional `plain_reason` and
     `plain_change` (schema `specs/policy-schema.md`, loader zod in
     `src/store/policy.ts`, placeholder/token checks in
     `checkPolicyReferences` exactly as for firm hard lines). With them: *Why:
     {plain_reason}. It's one of the rules your firm has adopted for
     {country}, and no safeguard can make up for it.* Without them: *Why: one
     of the rules your firm has adopted for {country} rules this out.* + the
     pointer line. `{country}` = the pack's jurisdiction plain name. No
     shipped pack uses pack hard lines today; tests use a fixture pack.
   - an id found nowhere loaded: *Why: one of your firm's rules rules this
     out.* + the pointer line. Never the bare id on the first screen.
3. **Answers you weren't sure about that contributed (D-80):** an assumption
   contributed when any of its `fields` appears in the binding rule's
   condition keys (`Object.keys(condition)`; for a pack rule, the pack rule's
   own condition — so `buildVerdictView` needs the loaded `packs` and the
   case's `assumptions`, both passed in the ONE trailing options object §4b
   defines; DR7-20, DR7-15). When at least
   one contributed: *This is based on answers you weren't sure about:
   {shortLabels joined "a", "a and b", "a, b and c"}. If any of them is wrong,
   change it and check again.* — and when the case has OTHER assumptions too,
   add: *(You weren't sure about other answers too — they're listed in the full
   reasoning below.)* (DR7-18).
4. **What would change the answer:** firm or pack hard line with
   `plain_change` → *What would change the answer: {plain_change} Then check
   again.*; without → *What would change the answer: change how it would be
   used, then check again. Ask your AI risk team what this means for you.*;
   CS-2 → *What would change the answer: change how it would be used, or ask
   your AI risk team whether the firm can add a safeguard for this.*
5. **One correction control (DR7-21):** on a "No", the button *If we've
   misunderstood how you'd use it, correct your answers and check again.*
   REPLACES the first screen's existing *Think we got something wrong? Correct
   your answers and check again.* (verified: src/components/VerdictDisplay.tsx
   1198-1201), and the lower *Correct this classification?* control (verified:
   VerdictDisplay.tsx:2144-2148) is not rendered on a "No". Both stay as they
   are on every other verdict.
6. *Who to talk to: your AI risk team — the independent team that checks how
   the firm uses AI — if you think this is wrong or want to discuss another way
   to do this.*
7. No safeguards list, no next steps, no "checks other teams run", no "who
   signs off". The reviewer section (collapsed, unchanged) follows, and lists
   EVERY assumption the case has under *Answers the submitter wasn't sure
   about* (contributing or not).

The view-model computes all of it (D1's one computation): a `no` block on
`buildVerdictView`'s result — `kind: 'hard_line' | 'pack_hard_line' |
'unsatisfiable' | 'other'`, `reason`, `change`, `contributingAssumptions`,
`otherAssumptionCount` — `undefined` unless rejected.

## 3. Where the assumptions come from at the result step (DR7-15, D-96)

The reducer's `verdict` state is bare (verified:
src/components/intake-state.ts:167 `| { step: 'verdict'; verdictId: string }`)
and the current carrier (verified: src/components/IntakeFlow.tsx:189
`formAssumptions = 'assumptions' in state ? … : []`) is empty there — so v1's
line would always have been empty on a first result.
- In `handleConfirmAndEvaluate`, read `assumptions` and `plainAnswers` out of
  the confirmation state BEFORE `dispatch({ type: 'CONFIRMED' })` — the same
  way `resolutions` and `answerContexts` already are (verified:
  IntakeFlow.tsx:861-868) — and keep them in one `useState`,
  `lastConfirmed: { assumptions: Assumption[]; plainAnswers?: PlainAnswers } |
  null`, set beside `setLastGraph` in `runConfirmAndEvaluate`.
- `VerdictDisplay` gains `assumptions?: Assumption[]` and `packs?:
  JurisdictionPack[]` props, passed through to `buildVerdictView`'s options
  object (§4b). The intake
  verdict screen passes `lastConfirmed.assumptions` and the loaded packs
  (verified call site: IntakeFlow.tsx:1776-1786).
- This lasts for the life of the page: after a reload the intake draft is
  cleared at the verdict (verified: IntakeFlow.tsx:785-790) and the register
  path (§4) supplies them from the trail instead. Say so in the spec.

## 4. Saving the assumptions with the case (D-81; DR7-16, DR7-19)

- `graph_confirmed` gains optional `assumptions: Assumption[]` (the §1 shape),
  written only when non-empty. A correction writes them on `verdict_corrected`
  (same field) — `graph_confirmed` is never written on a correction (verified:
  IntakeFlow.tsx:932-947 writes only `graph_corrected` there).
- Types: `src/store/types.ts` payload union; hand-off import schema
  (`src/store/handoff.ts`) accepts the field on both events and validates each
  element: `questionId` matches a known form `QuestionId` or
  `/^field:[a-z_]+$/`, `fields` is an array of known graph field names, the
  three strings non-empty and at most 500 characters (DR7-19, EB-2/EC-5). R16-F
  made the schemas pass unknown fields through; this validates the known one.
- `RegisterDetail` reads assumptions through R16-F's current-verdict event
  helper (latest `verdict_corrected` for a corrected case, else the
  `graph_confirmed`) and passes them and the loaded packs to `VerdictDisplay`
  (DR7-16 — both directions tested: an uncorrected case shows its confirmation's
  assumptions; a corrected case shows the correction's, not the original's).
- `eventDetail` adds *N answers were "Not sure".* to BOTH lines when present:
  the confirmation case (verified: RegisterDetail.tsx:46-51) and the
  correction case (verified: RegisterDetail.tsx:58-62).
- Every lookup into `assumptions` tolerates an unknown `questionId` or field
  (`?? []`), never throws (DR7-19).

## 4b. The register shows the same "already in place" lines as the result (D-97)

Found in the R16-F walkthrough: one case showed a different safeguard count on
the register page than on its own result screen. `RegisterDetail` renders
`VerdictDisplay` without a graph — deliberately, the graph is not persisted on
the register entry (verified at 52b2edf: src/components/RegisterDetail.tsx
943-948 comment, 1028-1035 call) — so `evidenceApplies` returns
`'cannot-check'` for evidence scoped to a platform or supplier (verified:
src/components/verdict-view-model.ts:264-274) and an "already in place"
safeguard falls back to "to do" for the reviewer who signs off.
- Follow the knowledge-lens precedent (verified: RegisterDetail.tsx:231-242 —
  computed at evaluation time, carried beside the verdict): `verdict_produced`
  and `verdict_corrected` gain optional `evidence_scope: { platform?: string;
  vendor?: string }`, the processing node's `platform`/`vendor` at evaluation.
  It sits beside the verdict exactly where `knowledge_lens_matched_entry_ids`
  does (verified: IntakeFlow.tsx:1096, 1117 — that field is written
  unconditionally), but is written spread-if-present like `submitter_note`
  (verified: IntakeFlow.tsx:997-999 and 1101-1103): absent when the processing
  node has neither.
- `buildVerdictView`'s evidence check uses the graph when it has one, else the
  persisted `evidence_scope`, else `'cannot-check'` (legacy events — honest, as
  today). Its new optional inputs (`assumptions`, `packs` from §2-§3, and
  `evidenceScope`) arrive in ONE trailing options object, not three more
  positional arguments (verified signature: verdict-view-model.ts:500-507).
  This is the only shape: §2 and §3 refer to this object.
- The two internal helpers change with it: `evidenceApplies(appliesTo, graph)`
  (verified: verdict-view-model.ts:264-274 — today `if (!graph) return
  'cannot-check'`) and its caller `safeguardStatus` (verified: :294-307) both
  take the optional fallback scope; `evidenceApplies` matches the scope's
  `platform`/`vendor` exactly as it matches the graph's processing node.
- `RegisterDetail` reads `evidence_scope` from the event that recorded the
  current verdict (the same `findLatestVerdictEvent` precedence) and passes it.
- Hand-off import schema: optional, each string non-empty and at most 200
  characters.
- Test: the same case shows the same "already in place" lines on the intake
  result and on the register page; a legacy event without the field still
  renders, with the existing "we couldn't check" note.

## 5. Correcting a form-path verdict through the form (D-82; DR7-17, DR7-22)

- `CORRECT_VERDICT_WITH_FORM { originalGraph, useCaseId, originalVerdictId,
  description, plainAnswers, assumptions }` → `graph_extraction` (`method:
  'form'`). The `graph_extraction` form state gains `originalVerdictId?` and
  `originalGraph?`; `FORM_SUBMITTED` (verified: intake-state.ts:399-445)
  carries `originalVerdictId` into the next states so `runConfirmAndEvaluate`'s
  `isCorrection` is true (verified: IntakeFlow.tsx:932) and the correction write
  path runs — the node is updated (verified: IntakeFlow.tsx:1127-1131), never
  `addNode` on the reused id (the fresh-only call, verified: IntakeFlow.tsx:1151).
  `description` comes from the confirmed state (DR7-17).
- `handleCorrectVerdict` (verified: IntakeFlow.tsx:1191-1204) dispatches
  `CORRECT_VERDICT_WITH_FORM` when `lastConfirmed.plainAnswers` exists and the
  graph is form-built; otherwise today's `CORRECT_VERDICT` (the `graph_review`
  path, whose words E makes plain).
- A one-line note above the form: *You're correcting your earlier answers.
  Change what was wrong, then continue — the result will be worked out again
  and both versions are kept.*
- `formCorrections(originalGraph, correctedGraph, { by, at, newId })` (pure,
  ids and time injected) emits one `GraphCorrection` per changed field. It
  lives in `src/components/` beside `verdict-view-model.ts` — the precedent
  for a pure derivation that serves one screen flow (no React, no store, no
  clock) — rather than in the engine, which evaluates graphs and never records
  how a person changed one:
  - against the ORIGINAL graph's node ids, matching nodes by role (the
    processing node, the output node) — the rebuilt graph mints new ids
    (verified: src/engine/build-graph-from-form.ts:73-74, 86, 130) (DR7-22);
  - over the UNION of both nodes' keys, so a cleared optional field
    (`declared_model_id`, `platform`, `decision_type_other` — absent, not
    undefined, when cleared: verified build-graph-from-form.ts:106-110) is
    recorded with `corrected_value: null`;
  - inputs as one correction on node id `inputs`, field `data_classes`
    (sorted arrays); jurisdictions on node id `graph`, field `jurisdictions`;
  - every correction carries the new optional `correction_source: 'form'`;
    GraphView edits set `'review'` and questionnaire write-backs `'question'`
    (`GraphCorrection` type + hand-off `graphCorrectionSchema`) (CB-4).
  A test enumerates `ProcessingNode` and `OutputNode` keys and asserts the
  helper diffs every one.
- A zero-correction resubmission writes `verdict_corrected` with no
  `graph_corrected` events; `eventDetail` renders it *Re-checked — no answers
  changed.* (F2C-6).
- The confirm guard is released on entry exactly as `handleCorrectVerdict`
  does today; the R16-F case lock refuses a correction whose case was corrected
  elsewhere.
- **Every way back into the form keeps the correction (v2.1).** Today a
  correction of a form-built case loses `originalVerdictId` on the way back to
  the form — `CHANGE_ANSWER` (verified at 52b2edf: src/components/intake-state.ts
  631-639) and, since R16-F, a form-path `EVALUATION_FAILED` (verified:
  intake-state.ts:679-687) — so the re-confirm runs as a FRESH confirm and the
  R16-F precondition refuses it as "already has a result". Safe (nothing is
  written) but a dead end. In correction mode (`originalVerdictId` set):
  - `CHANGE_ANSWER` and `EVALUATION_FAILED` return to the form carrying
    `originalVerdictId` and `originalGraph` when `plainAnswers` exist; when they
    do not (the `CORRECT_VERDICT` fallback), they return to `graph_review` with
    `originalVerdictId`, never to an empty form;
  - `STEP_BACK` from the correction-mode form already returns the state
    unchanged and Back is already hidden — true today for EVERY
    `graph_extraction` state (verified: the `STEP_BACK` switch at
    intake-state.ts:306-355 has no `graph_extraction` case; `canStepBack`,
    IntakeFlow.tsx:114-127, excludes it). No production change: add a test
    that pins it for the correction-mode form;
  - test each, ending in a successful correction: `verdict_corrected` written,
    no "already has a result" refusal.

## 6. What a reviewer sees about re-tries (DR7-09, D2 part)

The sign-off page (`RegisterDetail`) adds one line when the case has been
corrected: *Corrected {n} time(s) by the submitter — each version is in the
record below.* So repeated re-answering is visible to the person who signs off.

## 7. Evidence claims name what they rely on (DR7-34)

The first screen already ends its in-place line with a generic note —
*Already in place: {safeguards} (your firm's records show this)* (verified:
src/components/VerdictDisplay.tsx:1156-1161). EXTEND that note; never add a
second one. When at least one in-place safeguard's evidence carries an
`applies_to` scope (R16-W W-7), the note becomes *(your firm's records show
this for {plain name})*, where {plain name} is the registered name of the
platform or supplier this case uses that the scope matched (the platform's
name when both match). One case has one platform and one supplier, so one name
covers the line, and it stays true for unscoped safeguards, whose evidence
covers every tool. No scoped safeguard → the note is unchanged. The view-model
computes the name (`inPlaceScopeName?: string`); the screen only renders it.
