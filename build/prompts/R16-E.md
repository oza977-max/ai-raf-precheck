# R16-E — the description-first path speaks the form's words (UC-12)

Built against `build/prompts/R16.md` v2.1 §5, on top of R16-W (which added
`SUMMARY_VALUES` — graph value → plain sentence — to `plain-copy.ts`) and
alongside or after R16-D2. Principles §0 apply unchanged, principle 1
above all: no engine vocabulary (field codes, zone letters, model-type
names, autonomy levels, "binding", "graph", "model proposed") on any
screen a submitter sees. Reviewer-only grids (collapsed "details the rules
use") keep their codes. Decision ids continue at D-90.

The description-first path runs when a model is configured: the submitter
describes the tool, the model extracts a draft, the submitter checks it on
the review screen (`GraphView` inside `graph_review`), answers follow-up
questions (`QuestionnaireStep`), resolves contradictions
(`ContradictionReview`), then sees the R16-C summary and confirms. The
same review screen is also where every path lands after a failed
evaluation, and where a verdict correction goes when the form's answers
are not available (R16-W/D2 fallbacks) — so it must be plain for everyone.

House rules (CLAUDE.md) as usual: `npm test` only; `.md` + `.html` twins;
no rendered "approved"/"rejected"; `src/engine/*` pure; `src/llm/*` is the
only place the model SDK is imported.

## 1. Extraction can carry the agent fields (D-90)

`src/llm/graph-extractor.ts`: add `system_access_scope` (array of the four
values; validated through `normaliseAccessScope`, the single helper — R16
§1.1, D-65) and `multi_instance_coordination` (`no | yes | unknown`) to the

`none` with another value (rejected), duplicate (rejected), unknown value
(rejected), absent (accepted).

## 2. Follow-up questions in the form's words (D-91)

`src/engine/question-generator.ts` keeps its ids, fields, budget and
ordering. Only the words change, plus one new answer type:
- Move every question text and option label into `plain-copy.ts`
  (`QUESTIONNAIRE_COPY`), imported by `QuestionnaireStep` — the engine
  file keeps field/option VALUES only (it must not import from
  `src/components/`; if the generator needs text, the component looks it
  up by field).
- Per field, exact text (question; then options value → label). Where a
  form question sets the same field, the labels are the form's own option
  text (R16 §2.2), and "Not sure" maps exactly as the form maps it:
  - `data_class`: *What's the most sensitive information it will see or
    use?* — Client PII / MNPI / Confidential / Internal / Public with
    R16-W's summary wording; **Not sure → Confidential** (assumed).
  - `data_zone`: *Where will your information go?* — Zone A *An outside
    website or service, outside your firm's control* · Zone B *A
    supplier's systems, outside your firm's own* · Zone C *Your firm's own
    systems* · **Not sure → Zone A** (assumed).
  - `model_type`: Q4's question and options (score option expands to the
    three score kinds with Q4a's wording: statistical / traditional-ml /
    ml) · **Not sure → agentic** (assumed).
  - `action_type`: *What happens with what it produces?* — read *It finds
    or summarises things for people to read* · inform *It answers people's
    questions directly* · draft *It creates drafts* · recommend *It
    suggests, ranks or flags things* · execute *It carries out actions —
    sends, books, updates records or deploys changes* · trade *It places or
    changes trades* · approve *It makes yes-or-no decisions, like accepting
    an application* · **Not sure → execute** (assumed).
  - `autonomy_level`: *How much does it do without a person?* — 0 *Nothing
    by itself — people decide what to do with what it produces* · 1 *A
    person checks or approves each thing before it happens* · 2 *It decides
    or acts by itself, and a person reviews afterwards* · 3 *It acts by
    itself within limits someone set, with no routine review* · 4 *It acts
    entirely by itself, with no person involved at any point* · **Not sure
    → 4** (assumed).
  - `hitl`: *Does a person check what it produces before anything
    happens?* — Yes · No · **Not sure → No** (assumed).
  - `decision_bindingness`: Q6a's question and options + binding *It's
    acted on without a person deciding* · **Not sure → material**
    (assumed) — as the form.
  - `exposure`: Q7's question, help and options · **Not sure →
    market-facing** (assumed).
  - `decision_type`: Q8's question and options (credit-decision and
    lending-decision share the lending option's text; keep both values
    selectable only if the generator offers both — check) · no "Not sure"
    (the form has none) but keep the free-text "Something else" only if
    the questionnaire can record `decision_type_other`; otherwise omit it.
  - `output_reversibility`: Q9's question and options · **Not sure →
    irreversible** (assumed).
  - `scale`: Q10's question, help and options (limited / at_scale; the two
    at-scale options both map to at_scale).
  - `replaces_prior_model`: Q12's question and options · **Not sure →
    yes** (assumed).
  - `system_access_scope`: Q13's question and options, **tick all**
    (`answer_type: 'multi_select'`) · **Not sure → all three** (assumed).
  - `multi_instance_coordination`: Q14's question and options.
  - Any other field: *Please check this detail: {plain field name}* with
    the R16-W summary wording for its values — never the bare field id.
- "Not sure" answers in the questionnaire are recorded like any answer
  (they set the stricter value) AND carried as assumptions, so the R16-C
  summary lists them under "Things we couldn't tell from your description"
  together with the uncertain nodes — one list, same wording as the form
  path's assumptions.
- `answer_type: 'multi_select'` (types + generator for
  `system_access_scope`); `coerceAnswerValue` accepts an array for it:
  every value from the closed set, non-empty, canonical order, through
  `normaliseAccessScope` (the single helper — no second implementation).

## 3. `QuestionnaireStep` (D-92)

- Progress line *Question {x} of {y}* — no budget, no "provisional tier".
- Multi-select: tick-all checkboxes with a *Done* button (disabled until
  one box is ticked; "Nothing beyond what it's given for the task" clears
  the others and vice versa, exactly as the form's Q13).
- The "why we ask" line: the triggering rule's plain reason (CF-6
  `plain_reason`, resolved like D1) instead of its formal description;
  the rule id stays quiet (existing R15-C3 idiom). No rule → no line.
- Guessed-field questions (R6) introduce themselves as *We couldn't tell
  this from your description:* rather than any "guessed"/"verified basis"
  vocabulary.
- Undo, the double-click guard and the context field stay as they are;
  their labels in plain words (context: *Anything we should know about
  this answer? (optional)*).

## 4. The review screen — `GraphView` and its surroundings (D-93)

`graph_review` in `IntakeFlow` + `GraphView`: same mechanics (R5 confirm
cards, R6 guessed fields and provenance quotes, R7 jurisdictions gate, R9
checklist), plain words:
- Card titles: input *What it uses* · processing *The AI* · output *What
  comes out*. Field labels without the code beside them (the code stays
  only in the collapsed reviewer grid and in the edit control's
  `aria-describedby` if a test needs it — prefer not).
- Field values: R16-W's summary wording (`SUMMARY_VALUES`), the same
  sentence the summary will show. Edit controls offer the same wordings as
  options (values unchanged); `system_access_scope` edits with tick-all
  (D-22) through `normaliseAccessScope`.
- Provenance: a verified quote shows as *From your description: "{quote}"*;
  a value with no basis shows *Not in your description — please check
  this* (replaces "not found in your text — worth a second look").
- Confirm-card button: *This is right*; confirmed note: *Checked by you.*
- Checklist header: *{n} thing(s) to check before you continue:*; items
  *Check "{label}"*, *Fix {n} detail(s) we couldn't tell on "{label}"*,
  *Check the countries*; done: *All checked — continue when you're ready.*
- Gate messages: unconfirmed cards → *{n} card(s) still need checking. We
  read these from your description — nothing is decided until a person
  has checked or corrected each one.*; jurisdictions → *Check the
  countries before continuing — they decide which countries' rules
  apply.*
- Jurisdictions panel: heading *Which countries does it involve?*; help
  with countries read: *We read these from your description. Check them —
  they decide which countries' rules apply.*; none read: *We couldn't tell
  from your description which countries it involves. Tick the ones it
  does — if none of these, only your firm's own rules apply.*; option
  labels by country name only (no code); confirm button *These are right*
  / *None of these — continue*.
- Plausibility warnings (R5-GR-4, advisory): plain words, no zone letters
  — e.g. *Your description sounds like it stays on your firm's own
  systems, but this says it goes outside the firm. Check it — where your
  information goes affects several rules.* Rewrite every warning message
  in `src/engine/plausibility.ts` the same way (engine file: plain strings
  are fine there, they are data).
- Ignored jurisdictions note (R5-GX-1): *We ignored "{x}" — it isn't one of
  the countries your firm's rules cover.*
- The "Why these values matter" toggle: *Why we ask* (consequence lines
  already plain in `field-copy.ts` — check each for codes and fix any).
- The heading *Confirm what we understood* becomes *Check what we read
  from your description* and the "WHAT YOU TOLD US" label *What you
  wrote*. The Proceed button: *Continue*.
- `EVALUATION_FAILED` re-entry message: *Something went wrong working out
  the result: {error}. Check the details below and try again.*

## 5. `ContradictionReview` (D-94)

Plain words for its heading, explanation, the "your description says / your
answer says" pair and the required explanation field: heading *Your
description and an answer don't match*; per item *Your description says:
"{quote}"* / *Your answer says: {plain value}*; field *Which is right, and
why?* (required, unchanged guard); button *Continue*. Contradiction
messages generated in `src/engine/contradiction.ts` get the same plain
rewrite as the plausibility warnings.
