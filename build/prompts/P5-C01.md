# Build Prompt: P5-C01 — Verdict Display + Correction Flow

## Chunk Summary

Replaces `IntakeFlow.tsx`'s inline 2-line verdict card with a real
`VerdictDisplay.tsx` (`verdict-audit.md §5`): status above the fold,
binding constraint with graph path, confidence-caveat warnings (RA-11),
controls/downstream-reviews lists, and a "Correct this classification?"
button that re-enters `graph_review` (§6, VD-3) — writing
`graph_corrected`/`verdict_corrected` audit events instead of
`graph_confirmed`/`verdict_produced`, with the original verdict event
never modified. User-facing — **TDD-1 applies.**

## Spec Gaps Found and Resolved Before Implementation

1. **`ConfidenceCaveat` has no `confidence` field.** §5.3 requires
   checking `caveat.confidence === 'low' | 'medium'`, but
   `src/engine/types.ts`'s `ConfidenceCaveat` (landed P3-C01) only has
   `{ruleId, field, reason}`. **Fixed**: added `confidence: 'low' | 'medium' | 'high'`
   to the type. Note: `evaluate()` never actually populates
   `confidence_caveats` with real data yet (always `[]`) — RA-11 rendering
   is built and tested against synthetic `Verdict` objects, not
   engine-produced ones. Flagged, not silently assumed away — a future
   engine chunk owns populating this for real.
2. **§5.2 says "Plain-language explanation from `Verdict.reasoning_trace`"**
   but `Verdict` (src/types/verdict.ts) has no such field — reasoning
   trace actually lives on the `verdict_produced` audit event's
   `payload.reasoning_trace` per §5.4/§7, which is correct and consistent.
   §5.2's wording is the drift, not the data model. `VerdictDisplay.tsx`
   reads it from the matching audit event, not from `Verdict` itself.
3. **`reasoning-trace.ts` (P5-C02) doesn't exist yet** — the `<details>`
   reasoning-trace section always falls back to the structured summary
   (rule ID + policy `description` field) per §5.4's documented fallback
   behavior. This is not a gap, it's the spec's own designed degradation
   path — P5-C02 fills in the real LLM-generated prose later.

## State Machine Changes

`useCaseId` generation moves from `QUESTIONS_GENERATED` to
`GRAPH_EXTRACTED` (carried on `graph_review` state from the start) so a
correction flow can **reuse** the original `useCaseId` (same use case
being re-evaluated) instead of generating a new one. New optional
`originalVerdictId?: string` threaded through
`graph_review → questionnaire → contradiction_review → confirmation → evaluation_pending`
— present only on a correction pass, undefined on a fresh submission.
New action `CORRECT_VERDICT` (verdict → graph_review, carrying the
existing graph/useCaseId/originalVerdictId). `IntakeFlow.tsx` tracks the
last-evaluated `DataFlowGraph` and the full `Verdict` envelope in
component state (not just `EvaluationResult`) so a correction has
something to re-enter `graph_review` with and something to cite as
`original_verdict_id`.

## Deliverables

1. **`src/engine/types.ts`** — add `confidence` to `ConfidenceCaveat`.
2. **`src/components/intake-state.ts`** — `useCaseId` moved to
   `GRAPH_EXTRACTED`; `originalVerdictId?` threaded through the chain;
   new `CORRECT_VERDICT` action.
3. **`src/components/VerdictDisplay.tsx`** (new) — full display per
   §5.1-5.4: status `<h2>` above the fold, tier/track, confidence-caveat
   banners (full-page "Provisional" for Low, inline box for Medium),
   binding constraint `<code>` + graph path, controls list, downstream
   reviews, `<details>` reasoning-trace fallback, "Correct this
   classification?" button.
4. **`src/components/IntakeFlow.tsx`** — render `VerdictDisplay` instead
   of the inline card; `handleConfirmAndEvaluate()` branches on
   `originalVerdictId` presence: fresh submission writes
   `graph_confirmed`/`verdict_produced` (unchanged), a correction writes
   one `graph_corrected` event per `GraphCorrection` in
   `state.corrections` plus one `verdict_corrected` event citing
   `original_verdict_id`. `handleCorrectVerdict()` dispatches
   `CORRECT_VERDICT` with the last graph/useCaseId/the displayed
   verdict's own `id`.

## API Boundary Contracts

- The original `verdict_produced` audit event is never modified —
  verified by a test asserting `getAll(useCaseId)` still contains the
  original event, byte-identical, after a correction.
- `db.add()` (not `db.put()`) on `audit_events` already throws on
  duplicate `event_id` (P2-C02) — correction events get fresh UUIDs, so
  this is naturally respected, not something this chunk needs to enforce
  separately.

## Review Criteria

**Experts loaded:** Alan Cooper (correction must feel safe, not
punitive — the original verdict is preserved, not erased), Kent Beck (TDD).

**Known Patterns to Avoid:**
- BC-P5C01-01: a correction must reuse the ORIGINAL `useCaseId`, never
  generate a new one — verify with a test asserting the register's
  `use_case_id` is identical before and after correction.
- BC-P5C01-02: `graph_corrected` audit events must be written per
  individual `GraphCorrection`, not one event summarizing multiple
  corrections — matches the spec's singular `correction: GraphCorrection`
  payload shape.
- BC-P5C01-03: Low-confidence caveats must show "Provisional — legal
  review required" status text exactly, not just a generic warning —
  this is a specific compliance-facing string, not decorative copy.
