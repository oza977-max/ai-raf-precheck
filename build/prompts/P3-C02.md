# Build Prompt: P3-C02 — Greedy Set-Cover Control Solver

## Chunk Summary

Replace `src/engine/greedy-solver.ts`'s P3-C01 stub (`solvControls()` always
returning `{ ok: true, controls: [] }`) with the real greedy set-cover
algorithm (`evaluation-engine.md §4.2`, ADR-004). This is the last piece of
the P3-C01 pipeline that was intentionally deferred.

**TDD-1 exempted: pure internal engine module, no new user-facing surface —
same exemption class as P3-C01.** The function signature is already locked
(`evaluate.ts` calls it correctly today with the stub); this chunk only
changes the function body plus one small `evaluate.ts` wiring addition for
`boundary_proximity` (see Deliverable 2).

## Dependencies

- P3-C01 (evaluation engine pipeline) — complete, `c2b95db`. Locked contract:
  `solvControls(trippedInvariants: string[], controlLibrary: Control[], inheritedControls: string[], margin: number): SolverResult`
  where `SolverResult = { ok: true; controls: string[] } | { ok: false; unsatisfiableInvariant: string }`.

## Deliverables

1. **`src/engine/greedy-solver.ts`** — real algorithm per §4.2 pseudocode:
   - Remove invariants already satisfied by `inheritedControls` before the
     greedy loop starts (controls "already inherited from approved
     platforms" cover their invariant at zero burden cost).
   - Greedy loop: at each step, pick the control from `controlLibrary` that
     resolves the most remaining unsatisfied invariants. Tie-break: lowest
     `burden` wins; if still tied, lowest control `id` alphabetically wins
     (determinism guarantee, §7 point 4 — "lowest burden, then alphabetical
     by control ID").
   - A control that resolves zero remaining unsatisfied invariants is never
     a candidate (avoids reselecting an already-fully-covering control).
   - If at any iteration no candidate resolves any remaining unsatisfied
     invariant, return `{ ok: false, unsatisfiableInvariant: <first remaining invariant id> }`
     (CS-2 — name the first unsatisfiable one deterministically, don't pick
     arbitrarily from a Set).
   - If `trippedInvariants` is empty, return `{ ok: true, controls: [] }`
     immediately (nothing to solve).
2. **`src/engine/evaluate.ts`** (small addition) — wire `boundary_proximity`
   (VD-6/CS-4) into the `approved_with_controls` verdict path. **Judgment
   call, since §4.2's MVP description is a one-line flag with an ambiguous
   precise definition** — this chunk's interpretation: `boundary_proximity: true`
   if the solution is satisfiable, at least one invariant tripped, AND at
   least one tripped invariant is resolved by exactly one control in
   `selected ∪ inherited` (zero redundant coverage — the minimum possible
   margin). Document this interpretation explicitly in the handover as a
   deviation, not a silent guess. `greedy-solver.ts`'s exported `SolverResult`
   type gains no new fields for this — `evaluate.ts` computes
   `boundary_proximity` itself from the already-returned `controls` array
   and the tripped-invariant list (both already in scope at the call site),
   not from a new solver return field. This avoids widening the locked
   `SolverResult` contract.
3. **`src/engine/greedy-solver.test.ts`** (new) — comprehensive coverage:
   - TC-CS-1-01: basic greedy pick — one control resolving 2 invariants
     beats two controls each resolving 1
   - TC-CS-1-02: burden tie-break — two controls resolve the same count,
     lower burden wins
   - Alphabetical tie-break — two controls same count AND same burden,
     lower id wins (determinism guarantee — this exact scenario isn't
     independently spec-test-ID'd but the determinism guarantee in §7
     requires it, so cover it directly)
   - TC-CS-2-01: unsatisfiable invariant — no control in the library
     resolves it, returns the correct `unsatisfiableInvariant` id
     deterministically (not whichever happens to iterate first in a Set)
   - Inherited-controls: an invariant already covered by
     `inheritedControls` is removed before the greedy loop runs (assert the
     solver returns `controls: []` when inheritance covers everything)
   - Empty trippedInvariants → `{ ok: true, controls: [] }` immediately, no
     library scan needed

## API Boundary Contracts

**Known Patterns to Avoid:**
- BC-P3C02-01: Do NOT use `Set`/`Map` iteration order or object key order
  for tie-breaking — always sort explicitly (burden, then id) before
  picking, so behavior doesn't silently depend on V8 implementation details.
- BC-P3C02-02: Do NOT widen the locked `SolverResult` type to smuggle
  `boundary_proximity` through the solver — compute it in `evaluate.ts`
  from already-available data, per Deliverable 2.
- BC-P3C02-03: An already-selected control must not be reselected in a
  later greedy iteration even if it happens to still "resolve" an
  invariant that's already been removed from `unsatisfied` — verify the
  loop terminates and doesn't infinite-loop if a control's `resolves` list
  overlaps with itself in unexpected ways.
- BC-P3C02-04: The unsatisfiable invariant returned on failure must be
  deterministic (e.g., first in the original `trippedInvariants` order),
  not whichever the language's default Set/object iteration happens to
  produce first.
