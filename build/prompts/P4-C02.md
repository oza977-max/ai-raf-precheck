# Build Prompt: P4-C02 — Structured Form Fallback (UC-3a)

## Chunk Summary

Build the actual form UI for when there's no Anthropic API key configured,
replacing `IntakeFlow.tsx`'s current plain "no key" message (a documented
P4-C01 gap). This is a **user-facing chunk — TDD-1 applies**, outside-in
acceptance test first.

## Spec Drift Found Before Implementation (documented here, not a separate
## build-prep commit — small enough to fold into this chunk's own handover)

`intake-flow.md §5.2` says form select options come from "policy
`data_classes`/`model_types`/`action_types`/`exposure_levels`" — these
field names **do not exist anywhere in `policy-schema.md` or `PolicyFile`**
(confirmed via grep, zero matches). This is the same class of drift caught
in P4-C01 (`extractGraph()`'s permitted-values deviation): the canonical
vocabulary is a fixed closed enum set (`policy-schema.md §3.0`), not a
per-policy field. **Resolution**: source all enum select options from
`src/engine/canonical-vocabulary.ts` (P4-C01's shared module), consistent
with `extractGraph()`'s existing documented deviation. `jurisdictions` IS a
real `PolicyFile` field (`JurisdictionEntry[]`) — that one genuinely comes
from the loaded policy, no drift there.

## Dependencies

P4-C01 (complete, `121446b` + `887d217` SettingsPanel + `6e0e886` styling).

## Deliverables

1. **`src/components/StructuredForm.tsx`** (new) — all 13 fields from
   `intake-flow.md §5.2` (use case name, brief description, input data
   class/zone, AI model type, autonomy level 0-4 with plain-language
   descriptions, processing data zone, output action type/exposure/
   decision-bindingness/reversibility/scale, replaces-prior-model boolean,
   jurisdictions multi-select). Enum options from
   `canonical-vocabulary.ts`; jurisdictions from the loaded `PolicyFile`.
2. **`src/engine/build-graph-from-form.ts`** (new) — `buildGraphFromForm(formValues): DataFlowGraph`
   per `intake-flow.md §5.3`. Pure function (belongs in `src/engine/*`, zero
   React/I/O), constructs one input node, one processing node, one output
   node, no edges (the form doesn't collect edge topology — same
   single-node-per-category shape the LLM path effectively produces for
   simple cases). `intake_method: 'structured_form'`.
3. **`src/components/IntakeFlow.tsx`** (modify) — `graph_extraction` state
   now checks `getApiKey()` (already imported); if absent, render
   `StructuredForm.tsx` with the spec's exact banner text ("Structured
   intake mode — LLM graph extraction is not configured. Answer the fields
   below to describe your use case.") instead of the current plain error
   message. Form submission calls `buildGraphFromForm()` and dispatches
   `GRAPH_EXTRACTED` (same action the LLM path already uses — no reducer
   changes needed, `DataFlowGraph` is method-agnostic by design).

## API Boundary Contracts

- `build-graph-from-form.ts` has zero I/O, zero LLM — same purity rule as
  the rest of `src/engine/*`.
- `StructuredForm.tsx` is presentation-only (rule 4, cross-cutting.md §7) —
  calls `buildGraphFromForm()`, no inline business logic.

**Known Patterns to Avoid:**
- BC-P4C02-01: Do NOT hardcode enum option lists inside `StructuredForm.tsx`
  — import from `canonical-vocabulary.ts` (same drift-risk lesson from
  P4-C01's review finding #2).
- BC-P4C02-02: Do NOT call `buildGraphFromForm()` from inside
  `IntakeFlow.tsx` inline — it's an `src/engine/*` pure function, imported
  and called, not reimplemented.
- BC-P4C02-03: `usePolicy()` hook mentioned in the spec (§5.1) is NOT built
  in this chunk — `IntakeFlow.tsx` already has `loadPolicy()`/`getApiKey()`
  available directly; introducing a new hook is unnecessary indirection
  for what's already a simple boolean check. Document as a deviation, not
  a silent scope-narrowing.
