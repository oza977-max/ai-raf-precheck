### `src/store/register.ts` — real `RegisterStore` implementation
```typescript
export async function addNode(node: RegisterNode): Promise<void>
export async function addEdge(edge: RegisterEdge): Promise<void>
export async function updateUseCaseVerdictSummary(useCaseId: string, summary: Partial<UseCaseSummary>): Promise<void>
export async function updateLifecycleStage(useCaseId: string, stage: LifecycleStage, actor: string): Promise<void>
export async function getUseCases(role: 'all' | string): Promise<UseCaseSummary[]>
export async function getUseCase(useCaseId: string): Promise<UseCaseSummary | undefined>
export async function getGraph(useCaseId: string): Promise<{ nodes: RegisterNode[]; edges: RegisterEdge[] }>
export async function getBlastRadius(componentNodeId: string): Promise<RegisterNode[]>
export async function exportAll(): Promise<{ nodes: RegisterNode[]; edges: RegisterEdge[] }>
```
- `getUseCases(role)`: role `'all'` returns every `use_case`-type node (2LoD view) via the `by_type`
  index; role = an actor ID filters by `metadata.submitted_by` via the `by_submitted_by` index —
  **filter at the query layer, not by loading everything and filtering in-memory** (per
  `register-lifecycle.md` ADR-009 — ties to RG-2 role-based access).
- `UseCaseSummary` is a **derived/computed view**, not a separately-stored record (Fowler — avoid
  dual-write inconsistency). Compute it from the `RegisterNode`'s `metadata` fields at read time
  in `getUseCases`/`getUseCase`, not from a separate object store.
- `updateLifecycleStage` MUST call `audit.append()` with a `lifecycle_stage_changed` event in the
  same function call, per `register-lifecycle.md §6`: "Both writes happen in the same async call;
  they are not wrapped in a transaction — partial write risk is an acknowledged V1 limitation."
  Import `append` from `./audit.ts` for this.
- `getBlastRadius(componentNodeId)`: query the `by_to_node` index on `register_edges`, map matching
  edges to `from_node_id`, fetch each `register_nodes` row. O(edges referencing this component),
  not a full table scan.

## Framework Reference

**`idb` typed schema, second database (pattern already established in P1-C01's `db.ts` for
`aigate-audit` — mirror it for `aigate-register`):**
```typescript
import { openDB, type DBSchema, type IDBPDatabase } from 'idb';
import type { RegisterNode, RegisterEdge } from './types';

interface RegisterDbSchema extends DBSchema {
  register_nodes: {
    key: string;
    value: RegisterNode;
    indexes: { by_type: string; by_submitted_by: string };
  };
  register_edges: {
    key: string;
    value: RegisterEdge;
    indexes: { by_from_node: string; by_to_node: string };
  };
}

let registerDbPromise: Promise<IDBPDatabase<RegisterDbSchema>> | undefined;

export function openRegisterDb(): Promise<IDBPDatabase<RegisterDbSchema>> {
  if (!registerDbPromise) {
    registerDbPromise = openDB<RegisterDbSchema>('aigate-register', 1, {
      upgrade(db) {
        const nodeStore = db.createObjectStore('register_nodes', { keyPath: 'node_id' });
        nodeStore.createIndex('by_type', 'node_type');
        nodeStore.createIndex('by_submitted_by', 'metadata.submitted_by');

        const edgeStore = db.createObjectStore('register_edges', { keyPath: 'edge_id' });
        edgeStore.createIndex('by_from_node', 'from_node_id');
        edgeStore.createIndex('by_to_node', 'to_node_id');
      },
    });
  }
  return registerDbPromise;
}
```
**Note on nested-key index (`by_submitted_by` on `metadata.submitted_by`):** `idb`/IndexedDB
supports dot-path keys for `createIndex` — this indexes the nested field directly, no
denormalization needed. Verify with a real `fake-indexeddb` round-trip test (write a `use_case`
node with `metadata.submitted_by`, query `by_submitted_by` index, confirm it's found) — don't
assume the dot-path syntax works without testing it, since not all IndexedDB polyfills handle
nested keyPaths identically.
