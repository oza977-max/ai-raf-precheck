# Build Prompt: V1.1-C01 — Verdict Explainability + Intake UX (post-V1 fix chunk)

## Origin

Not part of the original 16-chunk implementation guide. Four real product
gaps found by the user during live acceptance testing of the completed
V1 build, confirmed by code inspection, explicitly commissioned by the
user ("fix this and review everything"):

1. **Zone A/B/C is unexplained jargon.** The structured form's two zone
   dropdowns offer bare "Zone A/B/C" options with no help text anywhere
   in the UI. The definitions exist only in `policy-schema.md` (Zone A =
   external/public internet, Zone B = cloud/managed third-party, Zone C =
   internal only / MNPI boundary). The input-zone vs processing-zone
   distinction (where the data lives vs where the model runs) is also
   never explained.
2. **"Review extracted graph" shows no graph.** It's a flat `<ul>` of
   node labels — no visual flow, no node attributes, nothing showing the
   structure the engine actually evaluates.
3. **The Edit button is a stub.** `IntakeFlow.tsx` line ~418: clicking
   Edit appends the literal string `" (corrected)"` to the label and
   records that as a correction. No real field editing exists anywhere —
   the correction machinery (reducer, `GraphCorrection` records, audit
   events) is real, but the UI feeding it is fake. This survived every
   chunk since P4-C01 because tests asserted the stub's behavior instead
   of real editing.
4. **Regulatory grounding is computed and then dropped.** Every hard
   line and track rule in `appetite.yaml` carries real citations
   (`"MAR Article 8; MiFID II"`, `"EU AI Act Annex III §5(b)"` …).
   `hard-lines.ts` reads `regulatory_basis` into its result;
   `assignTier`/`assignTrack` return the full matched-rule rationale —
   and `evaluate()` discards all of it at verdict assembly. `Invariant`
   lacks the field entirely. A bare "Approved" with no explanation is
   the visible symptom.

## Key Discovery

The engine already computes everything needed: `TierAssignment`
(`triggeringRuleId/Field/Value`), `TrackAssignment` (`ruleId/ruleName`),
`HardLineResult` (`reason`, `regulatoryBasis`), `TrippedInvariant[]`.
This chunk is 80% *wiring existing data through to the verdict*, not new
computation. That also means determinism (NF-1) is trivially preserved —
every new field is a pure function of the same sorted inputs.

## Deliverables

### D1 — Engine: `explanation` on `EvaluationResult`

- `src/engine/types.ts`: new `RuleRationale`, `TrippedInvariantDetail`,
  `VerdictExplanation` interfaces; `EvaluationResult` gains a REQUIRED
  `explanation: VerdictExplanation`; `Invariant` gains OPTIONAL
  `regulatory_basis?: string`.
- `src/engine/tier.ts`: `TierAssignment` gains
  `triggeringRegulatoryBasis?` (from the matched trigger's optional
  `regulatory_basis`).
- `src/engine/track.ts`: `TrackAssignment` gains `regulatoryBasis`
  (from `TrackRule.regulatory_basis`, already required on the type).
- `src/engine/invariants.ts`: `TrippedInvariant` gains `severity`,
  `requiredControls`, `regulatoryBasis?`.
- `src/engine/evaluate.ts`: all four return paths assemble a real
  `explanation`: tier/track rationale (null on hard-line rejection,
  where assignment is skipped by design), `hard_lines_checked` /
  `invariants_checked` counts, full `tripped_invariants` detail list
  (closing P5-C02's documented "one-element approximation" limitation),
  `binding_reason` (hard line's `reason`) and
  `binding_regulatory_basis` (binding rule's citation).
- `src/store/policy.ts`: Zod invariant schema accepts optional
  `regulatory_basis`.
- `policy/appetite.yaml`: `INV-ZONE-01` gets
  `regulatory_basis: "MAR Article 8; MiFID II"` (identical citation to
  `HL-002`, the same MNPI/Zone rule family in the same file);
  `INV-DATA-01` gets `regulatory_basis: "GDPR Art. 32(1)(a)"` (the
  canonical encryption-of-personal-data-in-transit citation). Both are
  starter-template content subject to the file's existing header caveat
  (CRO review required before adoption) — same standing as every other
  citation in the file.
- `src/llm/reasoning-trace.ts`: `buildTraceData()` upgraded to use the
  full `explanation.tripped_invariants` set instead of the one-element
  binding-constraint approximation (P5-C02 handover explicitly reserved
  this follow-up for "a future engine chunk extending EvaluationResult").
- Spec sync: `evaluation-engine.md` (+ `.html` mirror per P7-C02's
  drift lesson) EvaluationResult block gains the new interfaces;
  `policy-schema.md` (+ `.html`) invariant schema notes the optional
  field.

### D2 — VerdictDisplay: render the explanation

- "Why this verdict" section, always present:
  - Rejected: binding rule's `reason` + regulatory citation, prominent.
  - Tier/track rationale lines with rule ids + citations (or the honest
    "not assigned — hard-line rejection" note).
  - Tripped invariants: description, severity, citation, required
    controls per entry — the real multi-invariant breakdown.
  - Clean Approved: "Evaluated against N hard lines and M invariants —
    none triggered", plus the tier/track rationale. No more bare word.
- Defensive `verdict.explanation` access (old persisted verdicts predate
  the field).

### D3 — GraphView: real visual data-flow on graph review

- New `src/components/GraphView.tsx` (presentation-only): three-column
  flow (Inputs → Model → Outputs) with arrow connectors, node cards
  showing the actual attributes the engine evaluates (data class, zone,
  model type, autonomy, vendor, action, exposure, bindingness,
  reversibility, scale), uncertain-flag marker. Plain CSS per the
  no-component-library decision. Graphs with empty input columns (LLM
  extraction can produce them) render gracefully.

### D4 — Real correction editor (replaces the stub)

- Each node card's "Edit" toggles an inline editor: per-field `<select>`s
  sourced from `canonical-vocabulary.ts` (+ autonomy 0–4, reversibility,
  scale literals) and a label text input with Apply. Every field change
  dispatches a real `GraphCorrection` via the existing
  `handleCorrectNode(nodeId, field, value)` — the reducer/audit machinery
  is untouched; only the fake UI in front of it is replaced.
- `WalkingSkeleton.test.tsx`'s two correction tests are updated from
  asserting the stub's `" (corrected)"` label mutation to performing a
  real field edit (select change) and asserting the same audit-trail
  outcomes (corrections_count, event sequence, original-event
  immutability).

### D5 — StructuredForm field help

- Inline help under both zone selects: Zone A/B/C definitions + the
  input-zone vs processing-zone distinction, one line each.
- Terse one-line help for data class, exposure, decision bindingness,
  and output scale.

## Known Patterns to Avoid

- BC-V11C01-01: `explanation` must be deterministic — pure function of
  sorted policy + graph, no formatting that depends on iteration order
  of anything unsorted. TC-PE-1-01 (10-run byte-identical) must pass
  unmodified.
- BC-V11C01-02: do NOT fabricate regulatory citations. Only the two
  invariant citations named above (one copied from the same rule family
  in the same file, one canonical GDPR encryption cite), both under the
  template's existing review-required caveat. Rules without a citation
  show nothing rather than something invented.
- BC-V11C01-03: the correction editor must dispatch through the existing
  `CORRECTION_APPLIED` reducer path — no parallel state, no direct graph
  mutation.
- BC-V11C01-04: old persisted verdicts (audit events written before this
  chunk) lack `explanation` — every UI read must be defensive.

## TDD Approach

TDD-1 applies (user-facing). Acceptance tests first where behavior
changes are observable: updated correction-flow tests (real field edit →
same audit outcomes), verdict-explanation rendering (citation visible on
a rejection; "what was checked" on clean approval), zone help visible.
Engine unit tests: explanation contents per status path; determinism
unchanged.
