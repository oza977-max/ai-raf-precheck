# Build Prompt: P8-C04 — `Verdict.provisional_reasons`

## Chunk Summary

The engine determines Provisional and names its causes. `EvaluationResult`
gains `provisional_reasons` — an ordered collection, empty when the verdict is
not provisional. Two reasons in round 3:

| Reason | Raised when |
|---|---|
| `unsigned_pack_rules` | Any fired pack rule is unsigned (a low-confidence caveat exists) |
| `no_regulatory_basis` | No jurisdiction pack activated at all |

Both existing derivations become reads. Verified derivation sites:
- `src/components/VerdictDisplay.tsx:161` — `const isProvisional = lowCaveats.length > 0;`
- `src/store/register.ts:55` — `verdict.confidence_caveats.some((c) => c.confidence === 'low')`

Two copies of one rule in two layers. Round 3 adds a second cause, so leaving
them would mean editing the same rule twice and hoping neither drifted.

## Spec Excerpt

`evaluation-engine.md` §13, ADR-EE-R3-1 (chosen option 3):

> The `Verdict` gains `provisional_reasons` — an ordered collection of named
> reasons, empty when the verdict is not provisional. […] A verdict is
> Provisional if and only if `provisional_reasons` is non-empty. Both consumers
> read that; neither re-derives it.

§13.1a (design review I-3):

> A fired unsigned pack rule continues to emit its `ConfidenceCaveat` at low
> confidence — that is the per-rule detail, and it keeps its existing RA-11
> rendering. […] The caveat says *which rule* is unadopted; the reason says
> *why the verdict as a whole* is provisional. `provisional_reasons` is the
> single determinant of Provisional status. No consumer may re-derive it from
> `confidence_caveats`.

§13.1 — the reasons are not interchangeable: `unsigned_pack_rules` means a
basis exists and is not yet adopted; `no_regulatory_basis` means there is no
basis. Presenting the second as the first claims more than the engine can
support. The engine states the conditions; it does not rank them.

§13.2 — determinism: fixed declaration order, not discovery order. §13.3 — the
`status` enum is untouched; Provisional is a qualifier carried alongside it.

Cross-cutting §7 rule 1: `src/engine/*` imports only engine types and stdlib —
no React, no idb, no SDK, no `Date.now()`, no `Math.random()`.

## Framework Reference

- TypeScript 5 — a string-literal union plus a `const` array for fixed
  iteration order; `readonly` tuples keep the declaration order authoritative.
- Existing engine idiom: every return path builds through `emptyResult(overrides)`
  (`src/engine/evaluate.ts:437`), which spreads `...overrides` last. Deriving
  the new field AFTER that spread is what makes omission impossible.

## TDD Approach

Engine chunk with no direct user-facing surface of its own — the visible change
lands in P8-C05. The outside-in test here is the register-row agreement test
(TC-R3-JU-2-03), which crosses the engine→store seam a user can observe.

1. Write the failing engine test for the four condition pairs. Confirm Red.
2. Add the type, the module, the derivation at the choke point.
3. Replace both consumer derivations with reads.
4. **Realistic-fixture variant (TDD-3):** a verdict persisted *before* this
   chunk, with no `provisional_reasons` field at all. The happy path never
   produces it, and treating absent-as-empty would silently downgrade a
   historical Provisional verdict to plain — a false claim about a record.
5. Confirm Green.

## Review Criteria (self-review loop)

- **Metz:** grep for any surviving `confidence === 'low'` outside the engine
  module. One determination, or the chunk failed.
- **Copeland:** are the two causes distinguishable in the output, and does a
  test fail if they are swapped?
- **Determinism (NF-1):** fixed order, no clock, no randomness. Run the suite
  three times.
- **Honesty:** a legacy verdict lacking the field must not silently lose its
  Provisional status; and the two reasons must not be flattened into one badge.
- **HR3-08:** no new rendered string contains "approved" or "rejected".
