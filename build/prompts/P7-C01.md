# Build Prompt: P7-C01 — AIGate Self-Assessment Seed (LC-6)

## Chunk Summary

`src/seeds/aigate-self-assessment.ts` — AIGate evaluates itself through
its own engine on first launch and appears in its own register with a
real verdict, not a fixture. Wired into `App.tsx` (mount-time seed).
User-observable via the register view — **TDD-1 applies.**

## Spec Drift Found and Resolved Before Implementation

1. **`register-lifecycle.md §9`'s `AIGATE_USE_CASE_GRAPH` example uses a
   field name `reversibility` on the output node.** The real
   `OutputNode` interface (`src/engine/types.ts` line 86) has
   `output_reversibility`, not `reversibility` — same class of
   field-name drift already fixed once in this graph type (see line 47's
   "post build-prep field-drift fix" comment on `DataFlowGraph` itself).
   **Resolution**: the seed graph uses `output_reversibility`, matching
   the real, locked `OutputNode` contract.
2. **"On first launch (when the register is empty)" is checked more
   defensively than a literal empty-register test.** A literal
   `getUseCases('all').length === 0` check is fragile: if the seed
   effect somehow re-fires after a real user has already submitted their
   own first use case (e.g. a fast page reload racing the effect), an
   empty-register check would wrongly skip seeding forever. **Resolution**:
   the seed checks specifically whether AIGate's own use case node
   (fixed id `'aigate-self-assessment'`) already exists via
   `getUseCase(AIGATE_USE_CASE_ID)`, and is a no-op if so — idempotent
   regardless of what else is in the register or how many times the
   mount effect fires.
3. **Vendor node's `approval_status`** — the spec doesn't specify a
   value. Set to `'pending'`, not `'approved'`: this codebase has no
   real vendor-approval workflow (no chunk builds one), so honestly
   representing "not yet formally approved through any real process"
   beats fabricating an approved status.
4. **No `use_case_created` audit event is emitted** — that
   `AuditEventType` variant exists in the union but is never actually
   written anywhere else in this codebase (checked via grep — only
   `graph_confirmed`/`verdict_produced` are used on the real intake
   path). The seed follows the SAME real pattern as
   `IntakeFlow.tsx`'s fresh-path (`graph_confirmed` then
   `verdict_produced`), not the spec's unused literal event type.

## Deliverables

1. **`src/seeds/aigate-self-assessment.ts`** (new) —
   - `AIGATE_USE_CASE_ID = 'aigate-self-assessment'` (also the
     `DataFlowGraph.id` and `RegisterNode.node_id`).
   - `AIGATE_USE_CASE_GRAPH: DataFlowGraph` per §9's example, using
     `output_reversibility` (drift fix #1).
   - `seedAigateSelfAssessment(policy: PolicyFile): Promise<void>` —
     idempotent (drift fix #2): no-op if `getUseCase(AIGATE_USE_CASE_ID)`
     already exists. Otherwise:
     a. `evaluate(AIGATE_USE_CASE_GRAPH, policy)` — a REAL call, not a
        stub.
     b. Writes `graph_confirmed` then `verdict_produced` audit events
        (matching `IntakeFlow.tsx`'s real pattern, drift fix #4).
     c. `routeToWorkflow(verdict.tier, policy)` — AIGate gets **no
        auto-approve special-casing**; it goes through the identical
        routing every other use case does (§9 step 5's explicit "no
        auto-approve" instruction is naturally satisfied by reusing the
        same function, not by adding a bypass).
     d. `addNode()` for the AIGate use_case node, with `lifecycle_stage`
        from the routed workflow, `submitted_by: 'system'`.
     e. `addNode()` for an Anthropic vendor node (`approval_status:
        'pending'`, drift fix #3) and `addEdge()` a `provided_by_vendor`
        edge from the use case to the vendor node.
2. **`src/App.tsx`** — a mount-time `useEffect` calls
   `seedAigateSelfAssessment(policy)` once (empty deps array) when the
   loaded policy is valid. Errors are caught and surfaced the same way
   other best-effort operations in this codebase are (console warning,
   never blocks the UI — matches VD-8's reasoning-trace
   best-effort pattern).
3. **`src/components/RegisterView.tsx`** — two governance banners, both
   scoped to AIGate's own row (found by `use_case_id ===
   AIGATE_USE_CASE_ID` among the fetched rows), shown regardless of
   1LoD/2LoD role since both are firm-wide governance concerns:
   - If AIGate's `current_verdict_status === 'rejected'`: "AIGate does
     not satisfy its own controls — policy review required" (per
     `implementation-guide.md`'s P7-C01 deliverable list).
   - Else if AIGate's `lifecycle_stage === 'pre_checked'` (not yet
     2LoD-cleared): "AIGate self-assessment pending 2LoD approval —
     verdicts are provisional until cleared." (§9 step 5's exact
     wording).

## API Boundary Contracts

- `src/seeds/aigate-self-assessment.ts` may import `src/engine/evaluate.ts`,
  `src/engine/workflow-router.ts`, `src/store/register.ts`,
  `src/store/audit.ts` — a store-adjacent orchestration module, same
  shape as `IntakeFlow.tsx`'s `runConfirmAndEvaluate()` but with no React

  function call in a `useEffect`, no business logic inlined.

## Review Criteria

**Experts loaded:** Kent Beck (TDD), Fowler (idempotent seed operation —
no partial-write risk on re-run), McConnell (defensive first-launch
guard).

**Known Patterns to Avoid:**
- BC-P7C01-01: do NOT special-case AIGate's own lifecycle-stage routing
  to auto-approve — must go through the exact same `routeToWorkflow()`
  call as every other use case (§9's explicit "no auto-approve").
- BC-P7C01-02: the seed must be idempotent — re-running it (e.g. on a
  second app mount within the same session) must not throw or create a
  duplicate register entry.
- BC-P7C01-03: use `output_reversibility`, not the spec's incorrect
  `reversibility` field name.
