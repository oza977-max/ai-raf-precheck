## 0. Principles

1. **Situation, not categories.** No question, option, summary line or first-screen sentence shows engine vocabulary: data class, data zone or zone letters, autonomy level, bindingness, model-type names (LLM, ML, deep learning, generative AI, agentic), tier, track, MNPI, PII, 2LoD, invariant, rule or control ids. The engine's words stay in the reviewer section, glossed (NF-11). **No bare code ever reaches the first screen**, even as a fallback (D-20).
2. **The engine changes only where stated:** PE-9 (list-valued attribute), per-instance review sources (§1.3), and nothing else. Rules change only through the policy file.
3. **Stricter when unsure.** Every "Not sure" maps to the stricter reading and is listed back as an assumption. This now includes Q6, Q7 and Q9 (D-07, D-17).
4. **Honesty.** Provisional stays provisional; attested stays "not verified"; "in place" means machine-verified only; a covered review is never hidden from the reviewer (D-05).
5. **One computation per fact.** Anything the first screen and the existing sections both show is computed once, in one pure module (§4.1, D-02).
6. **Reserved words.** No rendered string contains "approved" or "rejected"; never "immutable" in audit copy; "different histories", never "fork".
7. **Boundaries** (cross-cutting.md §7): the answer→graph mapping is pure engine logic; the verdict view-model is a pure presentation module (no React, no store); components only render.

### 1.1 PE-9: list-valued `system_access_scope`
- Type: `SystemAccessScope | SystemAccessScope[]`. One pure engine helper, `normaliseAccessScope(input) → { ok: true, value } | { ok: false, reason }`, encodes the rule — **non-empty**, every element one of the four known values, **no duplicates**, `none` never together with another value, canonical order — and is the only implementation: the extraction zod gate, the form (Q13), `GraphView`'s correction control, the questionnaire's multi-select and `coerceAnswerValue` all call it (D-65).
- `condition.ts collectFieldValues`: an array value contributes each element. List-valued fields support only the `in` operator; the policy loader rejects `not_in`, `gte`, `lte` on a list-valued field with a CF-5 error (D-40).

### 1.3 Every review has a source (D-04)
`downstream_review_sources` gets one entry per review **instance**, from all four sources, at **every** `evaluate()` return site — including the pack hard-line rejection, which today sets neither `downstream_reviews` nor sources (a current bug: fix it to mirror the base hard-line branch, with a test — D-58): firm rules (`DR-…`), pack rules (the pack rule id, e.g. `SS1-UK-REV-01`), unregistered components (`PV-UNREGISTERED:<component name>`), unregistered models (`MODEL-REGISTRY:<model id>`). The three non-firm producers (`unapprovedComponentReviews`, `modelGovernanceReviews`, pack `addedReviews`) return structured `{ review, rule_id }` instances instead of bare strings. **`downstream_reviews` is derived from the sources** (their `review` strings, de-duplicated) so there is one source of truth (D-57). The **base id** is the part before `:`. `covers_reviews` matches on base id. Deterministic order (sorted by id). Adding sources changes no value the backtest or determinism tests compare (they use named fields / same-run comparisons).

### 1.4 Loader checks (D-05, D-23, D-39, D-60)
One exported pure function, `checkPolicyReferences(policy, packs) → { errors: string[]; warnings: string[] }`, called **at every site that loads policy and packs together or evaluates**: the app start-up gate (App.tsx), both evaluation gates in IntakeFlow (`reviewGateError`), the policy editor's Validate and Save (PolicyEditor — Save is refused on errors, the same "validate first, gate the save" rule it already follows — D-59), the settings panel's policy load, and the three seed scripts (which refuse to seed on errors). Errors refuse evaluation, CF-5-style ("Policy file invalid — CTRL-TPRM-01 covers_reviews: no review with id 'DR-VENDR-01'. Evaluation is disabled until this is resolved."), when a `covers_reviews` id is not a firm review id, a pack review rule id, `PV-UNREGISTERED` or `MODEL-REGISTRY`; or a list-valued field uses a non-`in` operator. It **warns** (shown to the reviewer, not blocking) on unknown placeholders or tokens, and on platforms or suppliers without a `plain_name`. The check is referential — it cannot tell whether a control really satisfies a review it claims to cover; `grounding/PACK-AUTHORING.md` gains a reviewer checklist line: "A `covers_reviews` entry is a claim that this control's action also satisfies that review — check it like any other condition" (D-51).

## 4. Chunk D — the verdict's first screen (VD-9, VD-10)

### 4.1 One view-model (D-02)
A pure module, `src/components/verdict-view-model.ts` (no React, no store calls): `buildVerdictView(verdict, policy | undefined, graph | undefined, ownership, attestations, stage)` returns, once per render:
- per safeguard: id, status (`verified` | `attested` | `outstanding` | `unknown`), plain action, owner text and `yours`, plain reasons (from its tripped invariants, de-duplicated), covered review instances;
- review instances still owed (not covered by a safeguard on this verdict), each with plain name and owner, **de-duplicated by plain name** (so the firm's two information-security rules show once — D-04);
- headline, why-reasons, next steps, could-still-change lines.
The existing **WhatToDo, SignOffChecklist and evidence panel (including its no-policy branch) are refactored to read the per-safeguard status from it** — one computation, four readers. `describesSameObligation` is deleted (replaced by `covers_reviews`); chunk D1 migrates every test fixture that relied on its text matching (starting with TC-RG-9-09) to populate `downstream_review_sources` and `covers_reviews` (D-57).

### 4.2 Layout (in this order)
1. **Headline** — out of appetite: **"No — not as described."** · sign-off needed (stage pre_checked), N outstanding: **"Not yet. You can start once your AI risk team has signed it off and all N safeguards are in place."** (N=1: "…and 1 safeguard is in place."; N=0: "…has signed it off.") · self-service, N>0: **"Nearly. You can start once N safeguard(s) is/are in place — no sign-off needed."**; N=0: **"Yes — you can start."** N counts outstanding = neither machine-verified nor attested.
2. **Why:** distinct plain reasons, binding constraint first, at most two, joined with "; and", then "(Each safeguard below gives its own reason.)" when there are more.
3. **Your next steps** — numbered; a step whose condition is false is omitted; "Then …" appears only after a preceding step (D-38):
   - sign-off: "Send this result to your AI risk team — the independent team that checks how the firm uses AI. They review the use in principle and sign it off; the safeguards can be finished after." When a safeguard lists your AI risk team as a partner, add once: "(Your AI risk team can help you set this up; signing off the use overall is a separate step.)" (D-53)
   - safeguards: all yours → "Put the safeguard(s) below in place — it's/they're yours to arrange (you or your manager)."; some yours → "Ask the team named against each safeguard below to put it in place, and agree a date. K of them is/are yours to arrange — marked \"yours\" and listed first. \"You or your manager\" means your side of the business: agree between you who takes each one."; none → "…None of them is yours to do yourself."
   - other teams' checks: "Also send this result to {teams} — they run their own checks, listed below. Ask each team whether you must wait for theirs before you start."
   - `no_regulatory_basis`: "Tell us which countries it involves, then check again — the answer may change."
   - finish: sign-off + safeguards → "Start only when both are done: it's signed off, and every safeguard below is in place."; sign-off only → "Start once it's signed off."; self-service → "Then you can start. It's saved on your firm's register of AI uses, which your AI risk team can see."
   - with sign-off and safeguards: "Not sure who these teams are? Ask your AI risk team when you send them this result."
4. **Safeguards that must be in place before you start (N)** — outstanding, yours first: plain action; "Who: …" (+ **yours**); "Because …"; "(This also covers {review} — one piece of work.)" when it covers a review on this verdict. Each **yours** safeguard has a "Go to this safeguard" link (D-55) whose click handler opens the reviewer section AND adds the control to the to-do list's expanded set before scrolling to it — the per-control disclosure is React-controlled, so an anchor alone would be closed again on the next render (D-26, D-63); tested. Then "Already in place: … (your firm's records show this)" (machine-verified) and "Reported in place by {name} (name not verified): …" (attested).
5. **Checks other teams run** — owed review instances (plain name — team).
6. **Who signs off:** "your AI risk team. Until they do, this result isn't final." / self-service: "nobody — it's low-stakes enough for you to go ahead once the safeguard is in place."
7. **Could still change** — shown when `isVerdictProvisional(verdict)` (D-19): `unsigned_pack_rules` → "Some country-specific rules it used haven't been formally adopted by your firm yet — your AI risk team can tell you which. If they're adopted as written, this result stays the same."; `unclassified_decision_type` → "You described a decision we don't have a rule for (\"{text}\"), so nothing specific to it was checked — your AI risk team will look at it."; provisional with no named reason (older verdicts) → "This result may still change — your AI risk team can tell you why."; **medium-confidence caveats (RA-11)** → "Some rules it used are worded with less certainty than usual — check this result with your compliance team before relying on it." (D-01).
8. **"Think we got something wrong? Correct your answers and check again."** — on every verdict, wired to the existing correction flow (VD-3, D-01).
9. **The reviewer section** — a fold titled "The full reasoning — every rule checked, the evidence, the sources, and the reviewer's actions": everything that renders today, unchanged and additive (inner folds keep their own behaviour; D-35), collapsed for the submitter, open for 2LoD (existing `reasoningDefaultOpen`). It lists **every** review, marking covered ones "covered by {safeguard}" — nothing is hidden there (D-05). When no model was named: "No model was named — your AI risk team may ask which one it uses." (D-27).
