## Scope

### D1 — VD-7 standing conditions, statically populated [ENGINE]

design-vision decision #2 ("the verdict is a hypothesis — V1 populates
the conditions slots statically") was never implemented:
`VerdictConditions.hypotheses` is always `[]`. New pure engine module
`src/engine/conditions.ts`: `buildStandingConditions(graph, policy,
tier): string[]` — deterministic bounds derived from the policy's
`kri_thresholds` (the six §3.7 dimensions, formatted as green/amber/red
band strings; `override_rate_pct` picks the high_risk band for
High/Critical tiers, low_risk otherwise) plus two graph-derived pins
(processing data zone pinned; max autonomy level as approved).
`KriThresholds` is a loose index type — the formatter reads known keys
defensively and emits nothing for absent/unrecognized shapes (never
guesses). Wired into `evaluate.ts` step 9 for approved /
approved_with_controls verdicts only (a rejection carries no approval
hypothesis). Wording constraint: no hypothesis string may contain the
words "approved"/"rejected" (existing acceptance tests assert
single-match on /approved|rejected/i — "Data zone pinned: …", not
"Approved data zone: …").

### D2 — Verdict screen panels [UI]

`VerdictDisplay.tsx` gains optional `graph?: DataFlowGraph` and
`registerStage?: LifecycleStage` props (passed from `IntakeFlow`, which
already holds both):
- Header meta: short use-case id + evaluated date (from `attested_at`).
- Appetite summary line: "In appetite — N control(s) required, M
  downstream review(s) triggered." / "Out of appetite — no control set
  can bring this use case inside." (No "position: Tolerate" — appetite
  positions don't exist in the policy model; nothing is fabricated.)
- STANDING CONDITIONS (VD-7) panel rendering `conditions.hypotheses`
  with the design's subtitle ("The hypothesis this approval is
  conditional on. V2 monitors these live.").
- RECORD & PROVENANCE panel from the graph prop — same field rows as the
  Confirm screen, via a shared `graphSummaryRows()` helper extracted
  from `ConfirmationStep.tsx` (single source, no duplicated derivation).
- Register status note from `registerStage` — wording avoids the
  "approved/rejected" words: pre_checked → "Saved to register — awaiting
  active 2LoD sign-off (LC-2)."; approved → "Saved to register —
  self-service final."
- NF-2 honesty footer (same one-liner as the register detail view).

### D3 — Questionnaire budget indicator (C2) [UI]

New exported `getQuestionBudget(graph, policy): { budget, provisionalTier }`
in `question-generator.ts` (reusing the existing internal provisional-tier
+ budget logic; `generateQuestions`'s signature unchanged).
`QuestionnaireStep` gains optional `budget?`/`provisionalTier?` props and
renders "{answered} / {total} · budget ≤{budget} (provisional {tier})".
`IntakeFlow` computes them at render via the pure helper.

### D4 — Shell polish (E1/E2) [UI]

- Role switcher options show the design's personas as display text only:
  "1LoD — James · Dev" / "2LoD — Priya · AI Risk" (values unchanged;
  demo personas, same standing as the design's).
- Sidebar Register count badge: App-level effect fetches
  `getUseCases('all').length` keyed on view changes (accepted staleness:
  count refreshes on navigation, not live). Markup keeps "▤ Register" in
  its own span so existing `getByText('▤ Register')` queries still match.

## Known Patterns to Avoid

- BC-V12B-01: `buildStandingConditions` must be deterministic and pure —
  fixed dimension order, no Date/random, engine-island imports only.
- BC-V12B-02: emit only bounds actually present in the policy — a
  missing/unrecognized kri_thresholds entry produces NO line, never an
  invented default.
- BC-V12B-03: hypothesis strings and register-status wording must not
  contain "approved"/"rejected" (single-match regex in existing
  acceptance tests).
- BC-V12B-04: `generateQuestions`' return type and behavior unchanged —
  the budget helper is additive.
