# Build Prompt: P5-C02 — Plain-English Reasoning Trace (VD-8)

## Chunk Summary

`src/llm/reasoning-trace.ts` — a real Anthropic call that turns a
verdict's structured data into plain-English prose an auditor can follow,
grounded strictly in the structured fields (no inference). Stored in the
`verdict_produced`/`verdict_corrected` audit event's `payload.reasoning_trace`
field, which `VerdictDisplay.tsx` (P5-C01) already reads from correctly —
this chunk is the write side, P5-C01 already built the read side.

## Spec Gap Found and Resolved

`VerdictTraceData` (`verdict-audit.md §7`) wants
`tripped_invariants: TrippedInvariant[]` (plural — every tripped
invariant) and `controls_required: ControlDetail[]` (full control
records, not just IDs). But `Verdict`/`EvaluationResult` only exposes a
single `binding_constraint` (the ID of ONE rule/invariant — the one that
determined the outcome) and `controls: string[]` (bare IDs). The full
tripped-invariant list is computed internally by `evaluate()` but
discarded after step 6 — never surfaced on the returned result.

**Resolution (documented simplification, not silently guessed)**:
`tripped_invariants` in the trace prompt is populated as a one-element
array from `binding_constraint`/`binding_path` (the only invariant data
actually available on `Verdict`) rather than the full set. `controls_required`
is populated by looking up each ID in `verdict.controls` against
`policy.controls` to get full `Control` records (name/description/burden).
This means the reasoning trace only narrates the SINGLE binding
constraint plus the full control list, not a complete multi-invariant
breakdown — a real limitation, flagged for a future engine chunk that
would need to extend `EvaluationResult` to expose the full tripped set.

## Deliverables

1. **`src/llm/reasoning-trace.ts`** (new) — `VerdictTraceData` interface,
   `generateReasoningTrace(traceData, apiKey): Promise<Result<string, LlmError>>`.
   System instruction + serialized `VerdictTraceData` + "Write the
   reasoning trace." per §7's exact 3-part prompt structure. No API key →
   `{ ok: false, error: { kind: 'no-api-key' } }` without throwing (§7).
2. **`src/components/IntakeFlow.tsx`** — after assembling `fullVerdict` in
   `runConfirmAndEvaluate()`, call `generateReasoningTrace()` (best-effort:
   failure doesn't block the verdict from being stored — `reasoning_trace: null`
   is a valid, spec-mandated outcome, not an error to propagate).
3. **`src/components/VerdictDisplay.tsx`** — no changes needed to the
   trace-reading logic (P5-C01 already reads `payload.reasoning_trace`
   correctly); only the no-api-key fallback message text needs to match
   §7's exact wording: "Reasoning trace unavailable — configure an
   Anthropic API key to enable plain-English explanations."

## API Boundary Contracts

- `src/llm/*` remains the only Anthropic SDK importer.
- `generateReasoningTrace()` never throws — matches the `Result<T,E>`
  discipline already established by `extractGraph()`/`confirmSemanticDuplicate()`.
- A reasoning-trace failure must not block verdict storage — `verdict_produced`
  is written either way, with `reasoning_trace: undefined`/omitted on failure.
