# Build Prompt: V1.3 — Proof-Carrying Controls (design-gap A7)

## Origin

Fourth chunk of the design-gap plan. design-vision decision #3: "A
required control is not a checkbox. It is either VERIFIED —
machine-provable evidence the control exists — or UNVERIFIED. … V1
implication: the control data model needs a `verification_evidence`
field from the start, even if most V1 controls are manually attested."
The field never made it into V1's schema; the verdict shows bare control
IDs.

## Scope decisions

1. **Schema, additive**: `Control` gains OPTIONAL
   `verification_evidence?: { status: 'verified' | 'unverified';
   detail?: string; attested_by?: string; attested_at?: string }`.
   **Absent evidence = UNVERIFIED** — the honest default; a control is
   never displayed as verified because someone forgot to say otherwise.
2. **No engine changes.** Verification status is policy data resolved at
   display time by control id (same pattern as `findRuleDescription`) —
   the verdict's `controls: string[]` contract is untouched, and
   determinism is unaffected.
3. **Starter YAML**: one worked example on `CTRL-ENC-01` —
   `status: "verified"` with detail referencing the platform TLS pin and
   `attested_by: "[FIRM] — Platform Engineering"` / `attested_at:
   "[DATE]"`. The `[FIRM]`/`[DATE]` markers keep it inside the
   template's existing adoption-required convention (and the NF-10
   banner already brands the file unadopted) — the mechanism is
   demonstrated without fabricating a real attestation. The other two
   controls carry no evidence → UNVERIFIED.
4. **UI**: the verdict's bare "Controls required: …" line becomes the
   design's **MINIMAL CONTROL SET (CS-1)** panel ("smallest set that
   holds the appetite margin"): per control — id, name, what it
   resolves/patches, VERIFIED/UNVERIFIED chip, and the evidence detail +
   attestation line when present. When the `policy` prop is absent
   (legacy render paths/tests), fall back to the plain id list —
   BC-V13-03.
5. **V1 honesty**: these are policy-file-maintained statuses (manual
   attestation), NOT machine-checked evidence — the panel's subtitle
   says so plainly ("V1: statuses are attested in the policy file;
   machine-checked evidence binding is V1.5"). Claiming CI-checked
   evidence would be a lie (BC-V13-01).

## Known Patterns to Avoid

- BC-V13-01: never imply machine verification — the subtitle states the
  V1 manual-attestation reality.
- BC-V13-02: absent `verification_evidence` renders UNVERIFIED, never a
  blank or an implied pass.
- BC-V13-03: verdicts rendered without a policy prop (legacy paths)
  degrade to the current plain id list — no crash, no fabricated chips.
- BC-V13-04: spec sync — `policy-schema.md` (+ `.html`) Control
  interface gains the optional field.
