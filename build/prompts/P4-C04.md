# Build Prompt: P4-C04 — Attestation + Confirmation → Evaluation

## Chunk Summary

Replaces the `PROCEED_TO_EVALUATION_PASSTHROUGH` dead-code path (in place
since P4-C01, explicitly flagged for removal in P4-C03's handover) with
the real `confirmation` state (`intake-flow.md §9`, UC-6): an explicit
"Confirm and evaluate" click that writes a `graph_confirmed` audit event,
runs `evaluate()`, writes a `verdict_produced` audit event with the full
`Verdict` object, then transitions to verdict. This is the gating chunk
for Phase 5+ (P5-C01, P5-C02, P6-C01 all depend on it). User-facing —
**TDD-1 applies.**

## State Threading Fix (found during design, not a late discovery)

`questionnaire`/`contradiction_review` states never carried `corrections`
forward from `graph_review` (a real gap from P4-C03 — corrections made
during graph review were silently dropped once the user moved into the
questionnaire). This chunk fixes it: `corrections: GraphCorrection[]` and
`useCaseId: string` are threaded through
`questionnaire → contradiction_review → confirmation → evaluation_pending → verdict`,
generated once at questionnaire entry, never regenerated.

## Deliverables

1. **`src/store/types.ts`** — tighten `AuditEventPayload`'s
   `verdict_produced`/`verdict_corrected` `verdict`/`new_verdict` fields
   from `unknown` to the real `Verdict` type (`src/types/verdict.ts`,
   landed P3-C01), and `graph_corrected`'s `correction` field from
   `unknown` to `GraphCorrection` (landed P4-C01) — both were flagged as
   overdue in P2-C02's handover "Notes for Downstream Chunks".
2. **`src/components/intake-state.ts`** — remove
   `PROCEED_TO_EVALUATION_PASSTHROUGH` entirely. Add `useCaseId`/
   `corrections` to `questionnaire`/`contradiction_review`/`confirmation`
   state variants; add `useCaseId` to `evaluation_pending` (so
   `VERDICT_READY` no longer needs an external payload — `verdictId` is
   just `state.useCaseId`). New actions: `PROCEED_TO_CONFIRMATION`
   (questionnaire → confirmation, always explicit, even with zero
   questions — UC-6 requires a real human click, not an auto-pass),
   `CONFIRMED` (confirmation → evaluation_pending).
3. **`src/components/ConfirmationStep.tsx`** (new) — final graph summary
   (node list, correction count), "Confirm and evaluate" button.
4. **`src/components/IntakeFlow.tsx`** — `handleConfirmAndEvaluate()`:
   `audit.append({event_type:'graph_confirmed', ...})` →
   `evaluate(graph, policy)` → assemble full `Verdict` envelope (id,
   use_case_id, `living_status: 'approved'`, timestamps, `attested_by`,
   `corrections: []`) → `audit.append({event_type:'verdict_produced', ...})`
   → `addNode()` → transition to verdict. Both audit writes happen before
   the UI transitions (TC-UC-6-01).

## Documented Deviation

**`attested_by` uses a hardcoded `'1LoD'` constant**, same as
`handleCorrectNode`'s existing `corrected_by: '1LoD'` — the spec's
`useRole()` hook doesn't exist (no auth/role system has been built in any
chunk so far). TC-UC-6-03 ("attested_by field matches current role") is
satisfied against this hardcoded placeholder, not a real role system —
flagged, not silently assumed away.

## API Boundary Contracts

- Both audit events (`graph_confirmed`, `verdict_produced`) must be
  written via `await` BEFORE the `VERDICT_READY`/verdict-state dispatch —
  verified by a test asserting write-then-read ordering via
  `audit.getAll(useCaseId)`.
- `src/store/*` still has zero React/LLM imports — importing `Verdict`
  from `src/types/verdict.ts` and `GraphCorrection` from
  `src/engine/types.ts` is fine (pure types).

## TDD Approach

## Review Criteria

**Experts loaded:** Kent Beck (TDD), Alan Cooper (the confirmation step is
the point of no return before an audited attestation — must be
unambiguous, not accidental).

**Known Patterns to Avoid:**
- BC-P4C04-01: `PROCEED_TO_EVALUATION_PASSTHROUGH` must be fully removed
  from `intake-state.ts`, not left as unreachable dead code alongside the
  new actions.
- BC-P4C04-02: the two audit writes must not race — `verdict_produced`
  must never be written before `graph_confirmed` completes, even though
  both are `await`ed sequentially (verify no `Promise.all` shortcut was
  taken).
- BC-P4C04-03: `corrections`/`useCaseId` must be genuinely threaded
  through every intermediate state (not silently dropped again at any
  transition) — verify with a test that makes a correction in
  `graph_review`, then answers a question, then confirms, and asserts the
  final `graph_confirmed` audit event's `corrections_count` reflects the
  earlier correction.
