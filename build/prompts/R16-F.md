## 1. Integrity of the confirm and correction writes

**F-1 (DR7-02, DR7-03) — one confirmation per case, across tabs.** Today two
tabs holding the same draft can both confirm: each writes `graph_confirmed`
and `verdict_produced`, and the second `addNode` throws on the duplicate key
(verified: src/store/register.ts:24-29 `db.add('register_nodes', node)`); the
error lands in the generic catch, `EVALUATION_FAILED` returns to
`graph_review`, and every retry writes another pair. Two tabs correcting the
same verdict both succeed and the last `put` wins silently (verified:
src/store/register.ts:190-217). The write queues only ORDER writes across tabs
(verified: src/store/db.ts:21-40 `createWriteQueue` → `navigator.locks.request`);
nothing checks for a repeat.
- Add to `src/store/db.ts` a `withCaseLock<T>(useCaseId, fn)` that runs `fn`
  under a cross-tab Web Lock named `aigate-case-${useCaseId}` (same
  `navigator.locks` pattern and the same direct-call fallback as
  `createWriteQueue`). It serialises only work on the SAME case, so it may be
  held across the whole confirm sequence (which awaits the optional reasoning
  trace — verified: src/components/IntakeFlow.tsx ~969
  `await generateReasoningTraceForVerdict`) without blocking anything else.
  It must NOT wrap or be wrapped by `withAuditQueue` callbacks: inside it,
  use the normal self-queuing writes (`appendAuditEvent`, `addNode`,
  `updateUseCaseVerdictSummary`, `updateLifecycleStage` — the last one takes
  the audit queue itself, verified: src/store/register.ts:242-290, so calling
  it from inside `withAuditQueue` would deadlock).
- Add a store read `confirmationPrecondition(useCaseId, originalVerdictId?)`
  (src/store/register.ts) returning `'ok' | 'already-decided' |
  'corrected-elsewhere'`: fresh confirm (no `originalVerdictId`) →
  `'already-decided'` when the trail already holds a `verdict_produced` for
  the case OR a register node exists for it; correction → `'corrected-elsewhere'`
  when the register node's `current_verdict_id` is not `originalVerdictId`.
  Reads only (`getAll` from audit.ts:217, `getUseCase` register.ts:336).
- `runConfirmAndEvaluate` (verified: src/components/IntakeFlow.tsx:857) runs
  its whole write sequence inside `withCaseLock(useCaseId, …)`, checking the
  precondition first, before ANY write. On a refusal: write nothing, release
  the confirm guard, stay on the confirmation step and show (role="alert"):
  already decided → *This case already has a result — it was probably
  confirmed in another tab or window. Open it from the register to see it.*;
  corrected elsewhere → *This result was corrected in another tab or window
  while you were working, so your correction wasn't saved. Open the case from
  the register to see the current result.* Disable Confirm after a refusal.
  No `EVALUATION_FAILED` for a refusal.
- An evaluation retry after a genuine failure (no verdict yet) still passes
  the precondition and writes a new `graph_confirmed` — a deliberate second
  attestation, recorded honestly. Say so in the spec.
- Fix the overclaiming text: `src/store/db.ts:9-11` and
  `specs/verdict-audit.md` (~line 809) say a second tab is "locked out too" —
  they are ordered, not locked out; the new case lock is what prevents a
  repeat. Both spec twins.

**F-2 (DR7-04) — an evaluation error never orphans the case.**
`EVALUATION_FAILED` returns every graph to `graph_review` (verified:
src/components/intake-state.ts:601-619), and Back from `graph_review` without
a correction id goes to the duplicate check and drops the case id (verified:
intake-state.ts:264-272) — the next Continue mints a new case while the first
one's `graph_confirmed` stays orphaned.
- `evaluation_pending` carries `plainAnswers?` and `assumptions?` from the
  confirmation state (verified shape: intake-state.ts:127-134).
- `EVALUATION_FAILED`: a form-path graph (`graph.intake_method ===
  'structured_form'`) returns to `graph_extraction` (`method: 'form'`) with
  `useCaseId`, `plainAnswers`, `assumptions` — the filled form, same case; a
  description-path graph returns to `graph_review` as today, plus a new flag
  `afterFailedEvaluation: true`.
- `STEP_BACK` from `graph_review` returns the state unchanged when
  `afterFailedEvaluation` is set (like the correction pass), and `canStepBack`
  (verified: src/components/IntakeFlow.tsx:99-108) is false there.

**F-3 (DR7-05) — the creation record is written at Confirm, once.** The form
path writes `use_case_created` on the first Continue (verified:
src/components/IntakeFlow.tsx ~693-704) and the description path writes it at
extraction; "Start over" before confirming then strands it, and the recorded
description can differ from the one finally confirmed.
- Remove both early writes. Inside the F-1 case lock, at the start of a FRESH
  confirm (not a correction), write `use_case_created` (description = the
  description being confirmed; `intake_method` from the graph) unless the trail
  already holds one for the case (an evaluation retry). Then
  `graph_confirmed`. Order on the trail: `use_case_created` →
  `graph_confirmed` → `verdict_produced`.
- Delete the `isResubmission` / creation-write logic in `handleFormSubmitted`
  (W-4's "one creation event" now holds by construction). Keep the case id
  reused across resubmissions.
- Update TC-R16-W-62 and TC-R16-W-66 to the new timing (exactly one
  `use_case_created`, carrying question 2's final text) and add: "Start over
  after Continue but before Confirm leaves no event on the trail".

**F-4 (DR7-12, part of DR7-16) — a correction keeps what the person typed,
and the register reads it.** On a correction pass the submitter's note, their
contradiction explanations and answer notes are dropped: only the
`graph_confirmed` branch writes them (verified: src/components/IntakeFlow.tsx
873-907), `verdict_corrected` has no fields for them (verified:
src/store/types.ts ~90-97), and the register reads them only from
`graph_confirmed` (verified: src/components/RegisterDetail.tsx ~928-962).
- `verdict_corrected` payload gains optional `submitter_note`,
  `contradiction_resolutions`, `answer_contexts` (same shapes as
  `graph_confirmed`); written spread-if-present on a correction.
- `src/store/handoff.ts` schema for `verdict_corrected` accepts them.
- `RegisterDetail` reads these from whichever event recorded the CURRENT
  verdict: the latest `verdict_corrected` when the current verdict came from a
  correction, else the case's `graph_confirmed`. One helper, used for all three
  fields (D2 will add `assumptions` through the same helper).

**F-5 (DR7-01) — a hand-off file is never wrongly called tampered.** The
import schemas strip unknown keys (plain `z.object`, verified:
src/store/handoff.ts:195-305 payload variants, :308 event, :364 register node,
:376 edge), and the seal and chain are then recomputed over the stripped copy
(verified: handoff.ts:603, 628, 643; audit.ts:79-81 hashes
`JSON.stringify(payload)`), so any field the importing version doesn't know
makes an untouched file fail as "altered after it was exported".
- Add `.passthrough()` to every object schema a hashed or sealed value passes
  through (event, each payload variant, register node, its metadata, edge), so
  unknown fields ride through unchanged and are hashed as sent. Known fields
  stay validated.
- Tests: a bundle whose `graph_confirmed` and `verdict_corrected` carry an
  unknown field imports and verifies, and the unknown field is still present on
  the imported event; a bundle whose KNOWN field is malformed is still
  rejected; a tampered value is still reported as tampered.

**F-6 (DR7-13) — one routing rule, one gate check.** The "questions →
contradiction review → summary" priority exists twice (verified: reducer
src/components/intake-state.ts:359-390 `FORM_SUBMITTED`, and the handler
sequence src/components/IntakeFlow.tsx:608-631), and the policy gate checks are
duplicated (IntakeFlow.tsx:584-588 and :659-663).
- A pure `nextReviewStep(questions, contradictions)` returning
  `'questionnaire' | 'contradiction_review' | 'confirmation'`, used by the
  `FORM_SUBMITTED` reducer case and by `handleProceedFromGraphReview`'s
  dispatch choice; one `checkPolicyGate()` helper in IntakeFlow used by both
  handlers. Behaviour unchanged; a test pins the priority once.

## 2. Description path and form checks

**F-7 (DR7-07) — the "couldn't tell" list survives a refresh.** It is a
`useState` filled only while on `graph_review` (verified:
src/components/IntakeFlow.tsx:170, 751). Carry `uncertainNodeIds?: string[]`
on the `questionnaire`, `contradiction_review` and `confirmation` states, set
from `graph_review`'s `guessedFields` when questions are generated; read it
from state; delete the `useState` and its effect. Test: refresh on
confirmation keeps the list.

**F-8 (DR7-08) — the form's agent-access answer goes through the single
checker.** The Q13 mapping pushes values by hand (verified:
src/engine/plain-intake.ts:502-506) and the form's "answered" check counts raw
ticks (verified: src/components/StructuredForm.tsx:316-318). Route the mapped
list through `normaliseAccessScope` (src/engine/access-scope.ts); a refusal
becomes a validation message on Q13, never "not stated". The required check
reads the normalised result.

**F-9 (DR7-09) — the zone answer is cross-checked and attributed.** The
description-vs-answers plausibility check (verified: src/engine/plausibility.ts
34-36 — "sounds like internal systems" vs an outside zone) runs only on the
field-card screen (verified: src/components/IntakeFlow.tsx:1498), which the
form path no longer visits, so W-9's "Yes — the platform runs the AI on the
firm's own systems" goes unchecked.
- Rewrite every message in `src/engine/plausibility.ts` in plain words — no
  zone letters, field names or "graph"; say what to double-check in the form's
  own terms (e.g. *Your description sounds like the AI runs on your firm's own
  systems, but your answers say your information goes outside the firm. Check
  "Where does the AI come from?" — it affects several rules.*). Engine data
  strings are allowed in the engine; they are plain text.
- Render the warnings on the "Here's what we understood" summary for BOTH
  paths under a heading *Please double-check* (computed at render from the
  description and the graph — pure, no new state). Advisory only, as today.
- When the zone came from the `3platformZone` answer, the destination line
  says so: *Your firm's own systems (you told us your information stays on
  them).* / the Zone B equivalent.
- `build/prompts/R16.md` §0.1 threat model: add rows for W-9's zone answer and
  W-7's evidence scope (a submitter naming a registered platform or supplier to
  turn "to do" into "already in place"), each with its mitigation. Both are
  self-attested; the mitigations are the cross-check above, the summary
  attribution, and (D2) the claimed platform/supplier shown beside any
  "already in place" line.
