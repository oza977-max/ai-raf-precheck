# Build Prompt: V1.2-A — Register Detail + Audit Timeline + 2LoD Actions

## Origin

First chunk of the design-gap plan (`build/design-gap-audit.md`, items
B3/B4/B5/B6), commissioned by the user after the screen-by-screen audit
of their Claude Design demo. The design's register detail view shows an
immutable audit-trail timeline and role-gated Approve/Request-correction
actions — none of which exist in the app, despite every underlying piece
of data already being recorded in IndexedDB and the `twoloD_reviewed`
audit event type having existed unused since P2-C02.

## Scope decisions

1. **Pure UI + wiring chunk — zero store/engine changes needed.**
   `getUseCase()`, `audit.getAll()`, `updateLifecycleStage()` (which
   already appends `lifecycle_stage_changed`), and `audit.append()` cover
   everything. The chunk's whole job is rendering data that exists and
   wiring two buttons to functions that exist.
2. **Action-bar visibility rule**: shown when `role === '2LoD'` AND
   `lifecycle_stage === 'pre_checked'`, for ANY tier. The design shows it
   for Critical ("active 2LoD approval required — LC-2"); Medium-tier
   pre_checked cases are notify-only with a 5-day auto-approve window,
   but an early explicit 2LoD approval of a Medium case is legitimate
   under §6's `Pre-checked → Approved` transition, so the bar shows with
   tier-appropriate wording rather than hiding. Determining
   `requires_twoLoD_action` precisely would need the loaded policy
   threaded into the register — not worth the coupling for wording.
3. **Approve** = append `twoloD_reviewed {action: 'approved'}` (the
   review decision, actor = current role) THEN
   `updateLifecycleStage(useCaseId, 'approved', role)` (which itself
   appends the `lifecycle_stage_changed` event). Two audit events,
   decision before effect — matches the design's timeline ordering.
4. **Request correction** = append `twoloD_reviewed
   {action: 'correction_requested', notes}` only. Lifecycle stays
   `pre_checked` (§6: correction + re-evaluation is a
   Pre-checked → Pre-checked loop driven by the submitter re-running
   intake; V1 records the request, it does not build a notification
   system). Notes field optional, single-line input.
5. **Detail navigation lives inside RegisterView** (selected-id state),
   not App-level routing — no new view plumbing. Returning to the list
   bumps a refresh key so approved stage changes are immediately
   visible.
6. **Timeline detail lines** are derived per event type from the real
   payload union (graph_corrected shows field/original→corrected;
   verdict_produced shows status/tier/track/binding/policy version;
   twoloD_reviewed shows action + notes; etc.) — no generic JSON dumps.
7. **Honesty labels** (design-vision L-3, NF-2): timeline header reads
   "IMMUTABLE AUDIT TRAIL (VD-4 / NF-2) · APPEND-ONLY"; footer carries
   the client-side provisional caveat verbatim from the design.
8. **B6**: the 1LoD list view gains a one-line scope explainer; the
   ride-along stage color chips land in the register table (pre_checked
   amber, approved/in_production/monitored green, retired grey, else
   neutral).

## Deliverables

1. `src/components/RegisterDetail.tsx` (new) — header (label, id,
   submitter, tier/track/status/stage chips), 2LoD action bar per rules
   above with post-action confirmation line ("Approved by 2LoD —
   lifecycle advanced to Approved. Recorded in the audit trail."),
   audit timeline, honesty labels, back link.
2. `src/components/RegisterView.tsx` — clickable rows → detail;
   refresh-on-return; 1LoD scope explainer; stage color chips.
3. `src/App.css` — timeline (dots, rows), action bar, stage chips,
   detail header styles.
4. Tests (TDD-1 first): open detail from a row and see typed timeline
   entries; 2LoD approve advances lifecycle + appends both events in
   order; request-correction appends `twoloD_reviewed` only and stage
   is unchanged; 1LoD sees no action bar and sees the scope explainer;
   immutability label present.

## Known Patterns to Avoid

- BC-V12A-01: the timeline must render from the REAL audit store
  (`getAll(useCaseId)`), never from a re-derived or cached summary — it
  is the product's evidence surface.
- BC-V12A-02: Approve must produce BOTH events (`twoloD_reviewed`, then
  `lifecycle_stage_changed` via the existing store function), not a
  hand-rolled stage write that would bypass the audit append.
- BC-V12A-03: action bar must be gated on role AND stage in the JSX —
  not CSS-hidden.
- BC-V12A-04: no store/engine modifications — if one seems needed, stop
  and re-check, because the audit established everything exists.
