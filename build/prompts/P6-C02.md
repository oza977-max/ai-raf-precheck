# Build Prompt: P6-C02 — Lifecycle Stage + Tier Routing + Policy Re-eval Trigger

## Chunk Summary

`src/engine/workflow-router.ts` (new, pure engine module — real tier→
governance-path routing), wired into `IntakeFlow.tsx`'s verdict-production
path so a use case's `lifecycle_stage` is set for real instead of the
hardcoded `'idea'` P4-C01 shipped. `src/store/policy.ts` gets a real
`onPolicyUpdated()` that queues re-evaluation for every active use case —
this is what makes P6-C01's dormant "Policy updated" banner go live.
User-observable via the register view's stage/status column — **TDD-1
applies.**

## Spec Drift Found and Resolved Before Implementation

1. **`register-lifecycle.md §7`'s `tier_workflows` YAML shape doesn't match
   the real, already-implemented policy schema.** §7 describes a rich
   per-tier object (`governance_path`, `verdict_is_final`,
   `twoLoD_notification`, `twoLoD_approval_required`,
   `twoLoD_review_window_days`). But `policy-schema.md` (what P2-C01
   actually built, Zod-validated, and what `policy/appetite.yaml` actually
   contains) has `tier_workflow: Record<Tier, WorkflowType>` where
   `WorkflowType` is a bare string (`"self-service"` / `"2LoD-notify"` /
   `"2LoD-approve"`) — confirmed by reading `policy/appetite.yaml` lines
   261–265 and `src/engine/types.ts` line 273 (`WorkflowType = string`).
   **Resolution**: `routeToWorkflow()` is built against the REAL schema
   (`policy.tier_workflow[tier]`, a string), not the aspirational richer
   object. The `twoLoD_review_window_days: 5` value from §7's Medium
   example is hardcoded as a module constant (`TWO_LOD_REVIEW_WINDOW_DAYS`)
   since the real schema has no field to carry it — documented, not a
   silent guess.
2. **The wiring matrix (`implementation-guide.md` §4) lists
   `workflow-router.ts`'s "Demanded by" chunk as P6-C01**, which already
   shipped without it — a chunk-ordering inconsistency in the impl guide
   (P6-C01's actual acceptance tests never referenced workflow routing).
   Not fixed retroactively; noted here as a known impl-guide defect.
3. **Apparent contradiction between deliverables and wiring-audit
   sections**: `implementation-guide.md` line 461 lists "`register.
   updateLifecycleStage()` used throughout intake and verdict flows" as a
   P6-C02 deliverable, but line 530 (P7-C03's closure checklist) lists
   "workflow-router.ts output drives lifecycle stage update in
   IntakeFlow.tsx" as something P7-C03 verifies. **Resolution**: read
   line 530 as P7-C03's standard integration-closure re-verification (the
   same pattern already used for P5-C02's reasoning-trace wiring and
   P6-C01's stale_assessment badge, both of which were built in their own
   chunk and re-verified in P7-C03) — not a deferral of the initial
   build. TC-LC-1-01/2-01/2-02 require the wiring to be real now (their
   assertions can't pass against a stubbed router), so this chunk performs
   the actual `IntakeFlow.tsx` wiring; P7-C03 re-audits it later.
4. **Register-node creation timing**: the register node for a use case
   doesn't exist until the FIRST confirm+verdict cycle (established since
   P4-C01/P5-C01 — `addNode()` is called only in the non-correction branch
   of `runConfirmAndEvaluate()`, after the verdict is already produced).
   This means the `Idea → Exploring` transition described in §6 is not a
   separately observable state in this codebase — there is no register
   row to hold it. **Resolution**: the node's initial `lifecycle_stage` is
   set directly to `routeToWorkflow()`'s output at creation time (skipping
   the unobservable Idea/Exploring states), not written as a hardcoded
   `'idea'` followed by a later transition. TC-LC-1-01 is adapted to
   assert the freshly-created node carries the correct routed stage, not
   a live Exploring→Pre-checked transition (same class of adaptation as
   prior chunks' documented deviations).

## Deliverables

1. **`src/engine/workflow-router.ts`** (new) — `routeToWorkflow(tier,
   policy): WorkflowAction` per §7, built against the real
   `tier_workflow: Record<Tier, WorkflowType>` schema (see drift #1
   above). Pure function, zero React/idb/LLM imports (Rule 3,
   cross-cutting.md §7).
2. **`src/components/IntakeFlow.tsx`** — `runConfirmAndEvaluate()`:
   - Fresh path: `addNode()`'s `lifecycle_stage` is now
     `routeToWorkflow(result.tier, policyResult.policy).lifecycle_stage`
     instead of the hardcoded `'idea'`.
   - Correction path: after `updateUseCaseVerdictSummary()`, calls
     `updateLifecycleStage(useCaseId, routedStage, getRole())` so the
     re-evaluation transition is recorded as a real
     `lifecycle_stage_changed` audit event (§6: "Pre-checked →
     Pre-checked (correction + re-evaluation)").
3. **`src/store/policy.ts`** — `onPolicyUpdated(newVersion: string):
   Promise<void>` per §8. Queries `getUseCases('all')`, filters to
   `approved`/`in_production`/`pre_checked`, appends one
   `re_evaluation_queued` event per active use case via `audit.append()`.
   Does NOT change `lifecycle_stage`. **Deviation from the spec's literal
   signature**: takes only `newVersion` and imports `register.ts`/
   `audit.ts` directly (matching this codebase's established
   store-to-store import pattern — `register.ts` already imports
   `audit.ts` the same way) instead of the spec's injected
   `RegisterStore`/`AuditStore` interface parameters, which don't exist as
   types anywhere in this codebase.
4. No caller for `onPolicyUpdated()` yet — `PolicyEditor.tsx` isn't wired
   into the intake flow (same standing deviation since P2-C01). This
   chunk makes the function real and tested; wiring a "Save policy"
   button is out of scope (not in this chunk's deliverable list).

## API Boundary Contracts

- `src/engine/workflow-router.ts` — zero React/idb/LLM imports (Rule 3).
- `src/store/policy.ts` may import `src/store/register.ts` and
  `src/store/audit.ts` (store-to-store imports already established as
  fine — `register.ts` → `audit.ts`).
- `IntakeFlow.tsx` remains presentation-only, calling `routeToWorkflow()`
  and `updateLifecycleStage()`, no business logic inline.

## Review Criteria

**Experts loaded:** Kent Beck (TDD), Fowler (pure routing function,
derived-state discipline — the register node's initial stage must be set
correctly at creation, not patched after), McConnell (defensive default
for an unrecognized `WorkflowType` string).

**Known Patterns to Avoid:**
- BC-P6C02-01: `routeToWorkflow()` must read the REAL
  `policy.tier_workflow[tier]` string schema, not a hallucinated richer
  object shape from §7's YAML example — verify against
  `src/engine/types.ts`'s actual `PolicyFile` interface.
- BC-P6C02-02: `onPolicyUpdated()` must NOT change `lifecycle_stage` —
  only append `re_evaluation_queued` events, per §8's explicit "does NOT
  change on policy save" rule.
- BC-P6C02-03: do not wire a `PolicyEditor.tsx` save button to
  `onPolicyUpdated()` — confirmed out of scope, no such caller exists yet.
- BC-P6C02-04: an unrecognized/future `WorkflowType` string must fail
  SAFE (to the strictest 2LoD-approve-equivalent path), not silently
  default to auto-approval.
