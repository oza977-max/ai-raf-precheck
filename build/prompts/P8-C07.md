# Build Prompt: P8-C07 — The sign-off page shows the verdict

## Chunk Summary

The register detail page is where a 2LoD reviewer approves a High-tier use case
or requests correction. It shows tier, track, status, the sign-off actions and
the audit trail — and **not the verdict**. Charter 004 measured the whole page
at 779 characters. The reviewer is asked to attest to a decision whose basis the
page does not present.

This chunk renders the verdict there: the six decision-bearing elements, the
provisional cause where there is one, and explicit statements for the two states
where a verdict cannot be shown.

## Spec Excerpt

**ADR-RL-R3-1** — read the verdict from the audit trail, do not recompute. "The
verdict a reviewer signs must be the verdict that was produced and attested, not
a fresh one computed against today's policy." Entries with no verdict-bearing
event render the R3-RD-2 statement instead. `graph` is *not* persisted on the
register entry, so any provenance panel depending on it must be omitted here
rather than rendered empty.

**§15.1 — the six decision-bearing elements:** verdict status and tier; binding
constraint id; every triggered invariant id with its citation; every control id
in the minimal set with evidence status (VERIFIED / UNVERIFIED); governance
margin figure and any ids flagged as having no headroom; standing conditions.
TC-R3-RD-1-02 compares id **sets**, not rendered text.

**§15.1a (C-2) — the historical/current split.** The verdict is historical: read
from the persisted payload. Control evidence status is **current**: read from
today's `PolicyFile`, because it is a statement about whether evidence exists
now. Presenting stale evidence status would tell a reviewer evidence exists when
it may since have lapsed. The two are labelled distinctly. Where policy is
unavailable, evidence status renders as **unknown**, not as UNVERIFIED —
absence of a policy is not evidence of absent evidence.

**Prop path:** `PolicyFile` is loaded in `App.tsx` and must be threaded
`App → RegisterView → RegisterDetail`. Neither props interface carries it today
(verified: `src/components/RegisterView.tsx:9`,
`src/components/RegisterDetail.tsx:10`).

**§15.2 (R3-RD-2, I-10) — two distinct empty states.** No verdict-bearing event
at all (the seeded AIGate self-assessment on every install): state plainly that
no verdict is recorded, and leave sign-off available. A verdict persisted before
V1.1-C01 with no `explanation`: state that the record predates explanation
capture and show the elements it does have. "An empty list would read as
'nothing was triggered', which is a stronger and false claim."

**§15.3 (R3-NF-2) — rendering must not write.** Opening the page any number of
times leaves the event count unchanged, asserted over **two** opens because
StrictMode double-invokes mount effects. The existing synchronous `useRef`
in-flight guard on the sign-off actions is unchanged and still required
(verified: `src/components/RegisterDetail.tsx:64`).

**§11.1 constraint (HR3-08):** this chunk writes the first `RegisterDetail`
tests against a page that now renders "Approved with controls". Its queries must
be scoped to a container, a role, or a test id — **never a bare single-match on
verdict text.**

### Known patterns to avoid (build checks)
