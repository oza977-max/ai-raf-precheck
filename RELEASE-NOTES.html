AIGate v0.1.0

The first complete release of AIGate, a pre-check gate that returns a deterministic verdict on whether an AI use case sits inside your firm's risk appetite.

What this is

AIGate turns a bank's Risk Appetite Framework into executable rules. You describe an AI use case in plain language or through a structured form. The engine maps it to a data-flow graph, evaluates it against your firm's machine-readable appetite and relevant regulatory packs (SS1/23, EU AI Act, SR 26-2, DORA), and returns a verdict: approved, approved with these controls, or rejected.

The same inputs produce the same verdict, every time. No AI model sits in the decision path. An optional LLM only reads descriptions in and retells verdicts out; the verdict itself is deterministic and reasoned from your rules, not inferred from data.

Submit a use case

Two intake paths:

  • Guided form. Business questions — "what kind of information does it use?", "how much can it do without a person?" — that map to the data-flow model your firm uses. No API key needed.
  • Plain-language description. If you provide an Anthropic API key, you can describe the use case in prose and the system extracts the same graph. No key: the form is your path in.

Either way, the resulting graph is shown back to you for review and correction before evaluation starts. A duplicate check runs against existing use cases in the register — you can adopt the existing classification or record that yours is genuinely new. Your confirmation is timestamped and recorded in the audit trail.

Read a verdict

A verdict tells you:

  • The outcome: approved, approved with controls, or rejected; the tier and track that produced it; the single binding constraint that set it.
  • The regulatory reasoning. Every rule that fired names the regulation behind it — verbatim source text, the rule derived from it, the basis (whether the rule restates the text, infers from it, or rests on judgment), and the sign-off line for the person accountable for it. In this release those sign-off lines are unfilled placeholders, so the verdict says so and marks itself provisional until your firm adopts the rules.
  • The control set. If controls are required, the engine solves for the smallest set that brings the use case inside appetite. Each control names the invariants it patches and whether the evidence is verified or unverified.
  • Standing conditions. The operating bounds the approval assumes. The verdict holds while the system stays inside them; drift outside voids it.
  • Governance margin. How much headroom the control set leaves, and which invariants rest on a single control (the most at-risk ones if that control fails).
  • A forward path for rejected cases. Not a list of what you did wrong, but what would need to change for approval.

Approve or send it back

A reviewer sees the same verdict the submitter saw. For Low-tier use cases, approval is self-service. For Medium, High and Critical, a 2LoD reviewer must sign off.

A sign-off records the typed name of the approver, their role, and the timestamp. The system labels it "name not verified" — there is no authentication behind it, and the audit trail says so. The record discloses the reviewer's identity and holds them accountable; it does not prevent a submitter from approving their own case, but the record shows it happened. A reviewer can also request corrections and return the case to the submitter.

Configure the firm's appetite

The firm's risk appetite is a YAML file you can read and edit in the application. Validation runs on save. When you change the policy, the engine automatically queues re-evaluation for all affected use cases — so you can track the impact of an appetite change across the entire register.

Regulatory packs (SS1/23, SR 26-2, EU AI Act, DORA) update independently of the main policy file. A policy file missing a required field cannot be used. A pack rule without a regulatory citation is rejected on load.

Every verdict records the policy version and the version of every pack active at the time it was issued. A verdict from last month is not silently rewritten by a policy change today.

Known limits at v0.1.0

Each of these is a boundary, not a defect. They are stated in the product as well.

Table 1 — Honest limits at V0.1.0
LimitWhat it means
No authenticationThe 2LoD role is a dropdown. A sign-off records a typed name and says it is unverified.
No segregation of dutiesNothing stops a submitter approving their own use case. The record discloses it; it does not prevent it.
Client-side storageThe audit trail is append-only by construction but held in your browser — not tamper-evident.
Pack rules unadoptedEvery shipped deck carries [FIRM] sign-off placeholders, so verdicts relying on them are provisional until your CRO adopts them.
Four decks onlySS1/23, SR 26-2, EU AI Act, DORA. Canada, Singapore and Japan are declared with no pack.
No post-deployment monitoringStanding conditions are recorded and checked at re-review, not watched live. That is V2.
No shadow-AI discoveryAIGate cannot see use cases that never come through intake. That is V2.
Condition language cannot scope to a node typeA rule that should apply only to where processing happens cannot yet be written correctly.
No property-based testsFour acceptance criteria specify generative tests that were never written. The behaviour they describe is covered by example tests.

What it will not do

  • It does not write your risk appetite for you. It enforces the one you give it.
  • It does not replace InfoSec review, vendor risk assessment, cloud security approval, or FinOps sign-off. It triggers those as mandatory downstream steps when a use case requires them.
  • It does not monitor AI systems after deployment. That is V2.
  • It does not find AI systems that bypass intake. Shadow-AI discovery is V2.
