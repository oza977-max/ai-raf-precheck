Five themes requiring decisions before build

Theme 1 — The rules themselves have no owner and are already drifted

  • No implementation chunk authors the starter policy and 7 jurisdiction packs
  • 4 material grounding drift points already in specs (missing track rules, missing hard lines, MNPI Zone B, no scale attribute)
  • Placeholder reviewer sign-offs pass CF-5 validation — NF-7 is toothless
  • "Verbatim" citations are almost certainly paraphrased

Theme 2 — Interface contract chaos blocks implementation

  • 4 inconsistent vocabularies already in the repo; tier_workflow vs tier_workflows key mismatch; Confidence capitalisation mismatch; VerdictSummary/UseCaseSummary contradiction; DataClass/DataZone undefined
  • LC-6 seed graph vocabulary crashes the engine on first launch

Theme 3 — Three V1 Musts are unimplementable as written

  • CS-1 safety margin: no metric over boolean conditions
  • TC-PE-1-01 byte-identical determinism: evaluate() returns UUID + timestamps
  • UC-4 question budget: requires a tier that doesn't exist yet at question-generation time

Theme 4 — Two architectural contradictions in the evaluation pipeline

  • Tier semantics: first-match (policy-schema §3.4) vs highest-wins (evaluation-engine §3.5) — a one-line YAML reorder silently changes every verdict
  • track_floor over categorical tracks: supplement vs reclassify unresolved; routes GenAI into MRM-regression regime

Theme 5 — V1 contradicts the product's own credibility definition

  • Design vision: artifact binding is "the irreducible V1 bet." Requirements + specs: zero OB work in V1.
  • LC-6 self-assessment: benign seed + auto-approve = the conduct-matter gaming pattern, applied to the flagship honesty mechanism

C-01 Panel B · 1-B · 2-B
tier_workflow vs tier_workflows: key name, shape, and casing all diverge — LC-2 governance routing completely broken
What's wrong

policy-schema.md:88,433 defines tier_workflow: Record<Tier, WorkflowType> (singular, flat string map, capitalised keys: Critical/High/Medium/Low). register-lifecycle.md:252 references tier_workflows (plural) and describes a rich object with governance_path, verdict_is_final, twoLoD_notification, twoLoD_approval_required, twoLoD_review_window_days. Tier key casing also differs: capitalised vs lowercase. workflow-router.ts receives a PolicyFile and must access policy.tier_workflows — that property doesn't exist on the type as defined. LC-2's approval gate cannot be implemented.

Fix

Define one TierWorkflowConfig interface with all five fields in policy-schema.md §3.4. Update PolicyFile.tier_workflows (plural) to Record<Lowercase<Tier>, TierWorkflowConfig>. Update all YAML examples and every reference in register-lifecycle.md and cross-cutting.md.

C-02 Panel B · 1-A
Confidence capitalised in policy-schema vs lowercase ConfidenceLevel in verdict-audit — RA-11 confidence caveats silently fail
What's wrong

policy-schema.md:416: PackRule.confidence: 'High' | 'Medium' | 'Low' (capitalised). verdict-audit.md:110: ConfidenceCaveat.confidence: 'high' | 'medium' | 'low' (lowercase). The engine reads PackRule.confidence and writes ConfidenceCaveat.confidence — strict TypeScript will produce a compile error or a silent type mismatch. RA-11 confidence display would either fail to compile or silently produce no caveat.

Standardise on lowercase across all specs. Change PackRule.confidence to 'high' | 'medium' | 'low'. Update all YAML examples. One canonical type: type ConfidenceLevel = 'high' | 'medium' | 'low' in cross-cutting.md §4.

C-07 Fable · Task 3
Tier semantics contradiction — first-match (policy-schema) vs highest-wins (evaluation-engine) — a one-line YAML reorder silently changes every verdict
What's wrong

policy-schema.md §3.4: "rules evaluated top-to-bottom, first matching trigger determines the tier." evaluation-engine.md §3.5: "all tier rules are evaluated, the highest tier whose trigger fires is returned." These differ whenever tiers are reordered in the (bank-editable) YAML. A bank listing Low first would down-tier every use case — a one-line edit silently altering the firm's appetite with no error.

Fix

Standardise on highest-tier-wins (order-independent, matches impact-dominance). Delete the first-match sentence from policy-schema.md §3.4. Add a property test: permuting the tiers array never changes any verdict.

C-08 Fable · Task 3
track_floor over categorical tracks is semantically wrong — routes GenAI systems into a traditional MRM regime, losing AI-specific controls; plus a thinking-aloud artifact shipped in the spec
What's wrong

evaluation-engine.md §3.6 applies track_floor using TRACK_ORDER = {I: 3, II: 2, III: 1}. Tracks are governance regimes by model type, not ordered severity. "Upgrading" a GenAI Track III system to Track I (Traditional MRM) loses the AI-specific controls Track III requires. Track II is arguably more demanding than Track I. The grounding's model is supplement (Track III + jurisdictional obligations), not reclassify. Additionally, the spec ships with an unedited "Wait —" thinking-aloud paragraph in §3.6 that should never have been in a committed spec.

Fix

Replace track_floor with a supplement_obligations effect: a pack adds required controls and validation obligations to the assigned track, never changes the track assignment. Update policy-schema.md §4 and evaluation-engine.md §3.6. Delete the "Wait —" paragraph and replace with the decided rule. If track reassignment is genuinely intended, amend raf-extraction.md §C first with regulatory justification.

C-09 Fable · Task 3 · Panel B · 1-G
No canonical attribute vocabulary — four inconsistent vocabularies already in the repo; LC-6 seed graph crashes the engine on first launch
What's wrong

Exact-string conditions with no canonical enum: policy uses "Internal"/"Zone B private"/model_type: "llm"; test cases use "Zone B"; grounding uses A/B/C; the LC-6 seed graph uses 'internal', 'zone_b', 'nlp_text_generation', 'internal_only' (lowercase snake_case). 'nlp_text_generation' matches no track rule → engine throws a no-track-match error on first launch. Every vocabulary mismatch is a silently non-firing rule — deterministic and quietly wrong.

Add §3.0 "Canonical attribute vocabulary" to policy-schema.md defining closed enums for data_class, data_zone, model_type, exposure, decision_bindingness, action_type, decision_type, output_reversibility. Enforce in CF-5 validation. Constrain LLM extractor JSON schema to these enums. Rewrite LC-6 seed graph with canonical values.

C-10 Fable · Task 3
LC-6 self-assessment is engineered to pass — benign seed + auto-approve is the conduct-matter gaming pattern, applied to the flagship honesty mechanism
What's wrong

register-lifecycle.md §9 seeds AIGate's self-assessment with the most benign value on every axis (autonomy 1, internal-only, reversible, advisory) and step 5 auto-sets lifecycle to approved. The design vision explicitly states AIGate "is a High or Critical use case under its own framework." LC-2 requires active 2LoD approval for High/Critical. The product's flagship honesty mechanism is specified as the exact gaming pattern (optimistic self-attestation to dodge oversight) the RAF calls a conduct matter.

Fix

Set the seed graph to honest values (decision_bindingness: material — the verdict drives governance decisions; LLM extraction processes submitter input, so data class is bounded by intake content). Let the engine assign tier. Route through workflow-router.ts like any other use case — if it lands High/Critical, it waits at pre_checked for 2LoD approval. This is the live integration test LC-6 promises.

C-15 Fable · Task 6 · Panel B

I-01 Panel A · P1-01 · Fable · Task 3
CS-1 Must/V1 — safety margin mathematically undefined over boolean conditions; spec already downgraded it but test didn't follow

CS-1 is V1 Must. evaluation-engine.md §4.2 says "full margin-aware solving is V1.5" and only sets a boundary_proximity: true flag. But TC-CS-1-02 requires the solver to choose between sets based on margin. A V1 Must requirement is unimplementable as written and its test will fail against the specced behaviour. "Margin" language on a boolean condition has no underlying metric.

Fix: Rewrite CS-1: "the solver returns the minimal burden-weighted set; the verdict carries boundary_proximity: true when any satisfied invariant has zero redundant coverage." Demote margin-based set selection to V1.5 with a defined metric. Rewrite TC-CS-1-02 against the flag.

I-02 Fable · Task 3
Determinism contract broken — evaluate() returns id: UUID v4, attested_at, and living_status_updated_at; TC-PE-1-01 demands byte-identical verdicts

evaluation-engine.md §7 forbids Date.now()/Math.random() inside evaluate(). But §3.9's Verdict (the function's return value) includes a UUID v4 and timestamps. TC-PE-1-01 demands byte-identical output across 10 runs. Either the engine breaks its own purity rule or the property test can never pass.

Fix: Split the type. evaluate() returns a pure EvaluationResult (status/tier/track/constraints/controls/conditions — byte-identical). The caller wraps it into a Verdict envelope adding id/timestamps/attestation. Point TC-PE-1-01 and TC-NF-1-01 at EvaluationResult.

Fix: Add jurisdictions: string[] to DataFlowGraph in intake-flow.md §4.2. Specify how the LLM extraction path obtains it (extracted with uncertain: true default + mandatory confirmation question, since jurisdiction is rarely inferable from a two-sentence description).

I-08 Panel B · 1-F · 2-E · Fable · Task 3
re_evaluation_queued event missing from AuditEventType — register banner never fires; policy save regresses production use cases to pre_checked

I-09 Fable · Task 6
Multi-node condition semantics unspecified — "reads emails, summarises, second agent drafts replies" is Journey 1 and the engine has no rule for which node's attributes fire

I-10 Fable · Task 6
Three [PROPERTY] tests are repetition tests, not property-based tests — determinism is the headline claim; the strong versions go untested

The property tests verify stability under fixed inputs — this catches Math.random() but not order-dependence, missing-rule coverage, or monotonicity violations. Genuine properties are available and cheap over the closed enum vocabulary (C-09).

Fix: Add fast-check generators over the canonical vocabulary and four genuine properties: (1) jurisdiction monotonicity — adding a jurisdiction never lowers tier; (2) impact dominance — mutating non-trigger fields never demotes a Critical verdict; (3) hard-line supremacy — any graph matching a hard line yields rejected regardless of all other fields; (4) solver soundness — every tripped invariant is resolved by some control in the returned set; plus the tier-order-independence property from C-07.

I-18 Fable · Task 5
AIGate's own model-risk exposure unassessed — the engine + LLM extraction layer is squarely in MRM scope under OSFI E-23 and SS1/23

Under OSFI E-23's broadest definition and SS1/23's technology-agnostic standard, the pre-check engine plus its LLM extraction layer is in MRM scope. LC-6 self-classification doesn't answer the harder challenge: is the engine itself subject to independent validation at the standard it enforces on others? Also: AIGate hardcodes a single vendor (claude-sonnet-4-6) with no self-fingerprinting, while shipping a control library whose marquee control is output fingerprinting.

Fix: Add a feasibility paragraph to risk-assessment.md: AIGate's deterministic engine requires conceptual-soundness validation (the NF-10 attestation — name it as MRM-equivalent); the LLM extraction layer requires Track III behavioural-verification controls (sampling of extracted graphs vs human-built ground truth). LC-6's verdict should list these as its required controls. Add V1.5 item: fixed probe-description set regression-tested on every model version change.
