Design Review 005

App-Wide Narrative Flow. Round 4 (full-depth multi-panel review), STRICT criteria.

Verdict
Build with caveats

The pattern that fixed the verdict screen (Minto-style decision-first structure, the Fold progressive-disclosure component, NF-11's ID-gloss discipline) turns out to be an island: every other screen in the app either never received it, or independently reinvented a worse version of it. The fixes are well-understood and mostly small per-screen, but there is real Critical-severity user confusion on several screens today, and one structural prerequisite (extracting the Fold component so it's reusable) should happen before most of the screen-level fixes, not after.

Executive Summary

Following round 3's verdict-screen rebuild, the owner asked to apply the same "does this tell a clear story to a first-time, non-technical, non-governance-aware reader" lens across every screen in the app. Nine screens/steps were scanned in parallel by Panel G (Audience Hospitality): the 6-step intake flow (Describe, Duplicate check, Graph extraction/review, Questionnaire, Contradiction review, Confirmation+journey spine), the Register list, the Appetite framework/policy editor, and Rule challenges+About. Four holistic panels (A Requirements Coverage, C Structural Soundness, D Implementability, E Security) ran across the whole app, excluding the already-fixed verdict screen.

Three cross-cutting themes emerged, each independently confirmed by multiple panels: (1) NF-11 — the "no bare internal ID without a plain-language gloss" rule written specifically because of a verdict-screen defect — is already being violated on other screens (Panel A found UC-2, UC-5, PE-4, NF-10 all rendered bare, one inside an alert-role banner), meaning the fix from round 3 was never propagated past the screen that prompted it. (2) The Fold component (decision-first, collapse-the-rest) that made the verdict screen work is a private, unexported function trapped inside VerdictDisplay.tsx — Panel C and Panel D independently found it's been reinvented three or four different ways elsewhere (a hand-rolled toggle in PolicyEditor, a bare native <details> in IntakeFlow, an ad hoc show-all toggle in RegisterView), each with subtly different accessibility semantics, and recommend extracting it into a shared, exported component before any further screen work. (3) Several screens have genuine, severe first-time-user comprehension failures independent of the Fold/NF-11 themes — most seriously the intake flow's duplicate-check step, where the on-screen instruction text for non-2LoD users ("contact AI Risk to adopt") is directly contradicted by a fully clickable button next to it that performs the adoption itself with no role gating at all.

Scope & Methodology Note

Panel B (Interface Contracts) did not run: this review focuses on information architecture and audience hospitality for existing screens, not contract changes. Panel F (Quality Attributes / ATAM Utility Tree) did not run: no new quality-attribute scenario is introduced in scope; performance, scalability, and accessibility are already covered by the existing utility tree and nothing in these screen-level fixes changes those tactics. Both gaps are explicitly scoped out per the review's design, matching round 3's methodology.

Critical Findings

Ten critical issues requiring resolution before build:

1. Duplicate-check step: the visible button contradicts the instruction text next to it.
For a non-2LoD submitter, the copy says "Contact AI Risk to adopt its classification" — but the very next element is a live "Adopt this classification" button with zero role gating. A first-time reader has no reason to believe the button does anything different from what the text just told them someone else must do. [Panel G — Intake: Duplicate check]
IntakeFlow.tsx duplicate-check step, handleAdoptClassification
Fix: Either disable/hide the button for non-2LoD roles, or change the copy to match what the button actually does.
2. Duplicate-check step: adopting a classification skips the whole questionnaire and graph review, and nothing says so before the click.
The explanation of what "adopt" really means (no intake questions asked, carries no verdict of its own, differences should become a fresh pre-check) exists in the code — but only renders AFTER the button is clicked. This is a consequence-visibility defect that forces click-and-regret. [Panel G — Intake: Duplicate check]
IntakeFlow.tsx duplicate-check step
Fix: Move that explanation before the button, replacing or supplementing the terse "Adopt this classification" label.
3. Graph review step: "graph" is never defined and appears as the operative word in the loading state, the screen's own h2 title, and the ARIA region label.
"Extracting graph…", "Review extracted graph", aria-label="Data-flow graph" — a first-time reader has no way to connect this vocabulary to what they just typed in plain English one screen earlier. The good explanation exists but is gated behind a specific state. [Panel G — Intake: Graph extraction/review]
GraphReviewStep.tsx, GraphView.tsx
Fix: Rewrite the h2 and loading label to goal-directed language ("Confirm what we understood" / "Reading your description…"), and move the one sentence that explains the task well to always render first, not state-gated.
4. Graph review step: raw engine field names (autonomy_level, decision_bindingness, etc.) render as bare code on every single card.
Deliberate per an existing code comment, but for a first-time reader this undercuts the plain-English framing the rest of the screen works hard to establish, with no explanation of why the codes are there or that they're safe to ignore. [Panel G — Intake: Graph extraction/review]
GraphView.tsx card rendering
Fix: Either remove the raw field names, or add a one-sentence tooltip explaining they are internal labels and safe to ignore.
5. Questionnaire step: the "why this matters" copy for each field is not wired into the questionnaire screen.
The copy (FIELD_CONSEQUENCES in field-copy.ts) exists and is wired into two other screens but is simply missing from QuestionnaireStep.tsx — a first-time user answering a question sees only bare question text and a terse "triggered by RULE-ID" line, never the plain-language reason the question exists. [Panel G — Intake: Questionnaire]
QuestionnaireStep.tsx
Fix: Import FIELD_CONSEQUENCES and render it under every question.
6. Contradiction review: the two conflicting statements are shown as bare bold text with no explanation of source, relationship, or which one to trust — plus a raw internal field name and a bare internal ID tag ("UC-5") both leak onto the screen.
No sentence anywhere says "you said X earlier, but Y here contradicts it." The heading and the raw field: {c.field} label frame this as a technical validation error, not the helpful catch the product intends. The bare "UC-5" tag is a regression of NF-11. [Panel G — Intake: Contradiction review, Panel A confirmed the UC-5 leak independently]
ContradictionReviewStep.tsx
Fix: Rewrite as a plain-language template naming where each statement came from, replace the raw field-name label with a resolved description, remove the bare "UC-5" tag or gloss it.
7. Contradiction review: the instruction asks the user to "correct one of the values above," but there is no editing control on screen — only a free-text box.
The stated option doesn't exist as an affordance; the user has to guess everything must go through prose in the textarea. This is a severe comprehension gap for first-time users. [Panel G — Intake: Contradiction review]
ContradictionReviewStep.tsx
Fix: Either add inline edit controls for the conflicting values, or rewrite the instruction to match what the textarea actually allows.
8. Register list: 1LoD users (first-time submitters) get no "what needs my attention" signal at all.
The entire narrowing mechanism, the plain-language legend explaining Tier/Track/Stage, and the Flags column (the one place stale/attention-needed items are surfaced) are all gated behind is2LoD — a 1LoD user sees a flat, unsorted, unexplained table with the one column engineered to say "look here" invisible to them. [Panel G — Register list]
RegisterView.tsx, narrowing/legend logic
Fix: Extend the is2LoD-gated legend and flags-based narrowing to 1LoD, scoped to "your submissions needing attention."
9. Register list: no default sort or urgency ordering for either role.
Even the 2LoD "awaiting sign-off" view has no ordering by staleness or severity within it — a reviewer must read every row to find what's actually urgent. This fails the basic "don't make me think" principle. [Panel G — Register list]
RegisterView.tsx table rendering
Fix: Add default sort by status urgency (e.g., Correction Requested, then Pending Sign-Off, then Approved); secondary sort by timestamp descending.
10. NF-11 (no bare internal ID without a plain-language gloss) is already violated outside the verdict screen — regression-by-omission.
Bare IDs found: UC-2 and UC-5 (intake flow screen tags), PE-4 (Appetite framework body copy), NF-10 (Appetite framework ACTION REQUIRED alert banner — the highest-visibility instance). The fix pattern this needs already exists and works on RegisterView, RuleImprovementQueue, and AboutPanel — it was simply never propagated past VerdictDisplay after being built. [Panel A, independently corroborated by Panel G finding on UC-5]
IntakeFlow.tsx, PolicyEditor.tsx
Fix: Apply the ID-gloss pattern from RegisterView to all bare instances; document the pattern in CLAUDE.md as a project convention.

22. Implementability: extracting Fold into its own exported component should happen BEFORE any screen-specific narrative-flow fix.

23. Implementability: the intake flow's graph-review step is the riskiest single screen to modify.
It has the most interdependent state, an id-anchored scroll-to-target checklist wired directly into GraphView and the jurisdictions panel, and zero DOM-structure test coverage for that step. A bad reorder could ship silently. [Panel D]

The jurisdictions-confirmation gate and the graph-review "N steps before you can proceed" checklist exist specifically to stop a model-guessed value from silently governing the outcome. Any future streamlining pass must keep both as hard gates in the handler logic, not just visually present. [Panel E]

Observations

Five observations with no severity tag:

  • AboutPanel.tsx has zero internal-ID leaks: It is the cleanest screen in the review with respect to NF-11 and plain language — it should be the reference example alongside the verdict screen when fixing the Critical/Important findings above. [Panel A]
  • RegisterView's Tier/Track/Stage/Verdict legend is a stronger pattern: Explain once, not per-instance gloss. [Panel A]
  • PolicyEditor's YAML editor is honestly gated: A progressive-disclosure toggle with explicit no-auth disclosure copy — a genuine strength, not a defect. [Panel G — Appetite framework, Panel E]
  • GraphView's per-card "why these values matter" toggle: A legitimate, narrower use of progressive disclosure that should NOT be treated as a Fold candidate — the screen's job is to force full review before confirmation, a deliberate, well-documented design choice, not an oversight. [Panel C]
  • RuleImprovementQueue is the easiest screen to retrofit: Flat list, no id-anchored scroll targets, thin state. [Panel D]

What Prevents a Higher Score

Gap statement for each sub-10 panel:

  • Panel A (6/10): The two NF-11 regressions (UC-5, PE-4, NF-10 bare IDs).
  • Panel C (5/10): Fold's lack of reusability; three independent reinventions create drift risk.
  • Panel D (6/10): Graph-review's untested reorder risk with high state interdependency.
  • Panel E (9/10): Only the documentation-discipline note if friction points are accidentally softened in future work; minor.
  • Panel G (4/10): The sheer number of first-time-reader comprehension failures found across 9 screens, and the pattern they reveal: the round-3 fix was a one-screen patch, not a reusable house convention.

Cross-Panel Themes

Theme 1: Independent convergence on Fold's reusability defect — Panels C and D, scanning for different defect classes (structural soundness and implementability), independently found three separate reinventions of the Fold pattern in PolicyEditor, IntakeFlow, and RegisterView. This is the strongest evidence that extracting Fold and documenting the pattern as a project convention should be its own prerequisite chunk, not folded into the first screen-specific fix, because every subsequent screen fix depends on it existing.

Theme 2: Independent convergence on NF-11 regression — Panels A and G independently identified the same phenomenon: the "no bare internal ID without gloss" rule written specifically to fix a verdict-screen defect is already being violated elsewhere (UC-2, UC-5 in intake flow; PE-4, NF-10 in Appetite framework). This is the strongest evidence that the fix pattern from round 3 was built as a one-screen patch, not a reusable house convention, and cannot propagate.

Theme 3: The verdict-screen fix was a one-screen patch, not a reusable house convention — The Minto-style structure, the Fold component, and the NF-11 discipline together made the verdict screen work. All three exist only on that screen, and when the same team faced similar problems on other screens, they locally reinvented answers instead of reusing the proven pattern. Extracting Fold into src/components/Fold.tsx, documenting the NF-11 rule at the point where it's enforced (not just on the verdict screen), and treating both as project conventions (alongside field-copy.ts) is the structural prerequisite before any screen-specific fix — not deferred, not optional.

Implementation Path

From Panel D, a tested sequence before code starts:

  1. Extract Fold from VerdictDisplay.tsx into a shared, exported component (src/components/Fold.tsx): Rename its verdict__fold* CSS classes to something screen-agnostic — small, contained, zero screen-specific risk, unblocks everything else.
  2. Fix the two duplicate-check Criticals (button/text contradiction, missing pre-click consequence): Self-contained, no shared-component dependency.
  3. Fix the Contradiction-review Criticals (bare statements, missing edit affordance) and the UC-5/UC-2 NF-11 leaks: Same file/area, can be fixed together.
  4. Wire FIELD_CONSEQUENCES into QuestionnaireStep.tsx: Small, contained.
  5. Fix the Register-list 1LoD visibility gap: Extend the is2LoD-gated legend/flags/narrowing pattern to 1LoD, scoped to "your submissions needing attention" — contained but touches role-conditional logic, test carefully.
  6. Reorder the Appetite-framework ACTION REQUIRED banner and fix the PE-4/NF-10 leaks: Contained structural fix.
  7. Graph-review step fixes (the "graph" vocabulary, field-name leaks, metaphor narration): Do LAST, after Fold extraction, and re-verify the checklist's scroll-to-target wiring explicitly since there is no test coverage to catch a silent break.

Post-Review Guidance

This review was NOT a liberal-threshold R1 scan with capture-recapture estimation; it was a strict, full-depth pass with 9 named per-screen panels and 4 holistic panels running in parallel. All findings are load-bearing. The verdict "Build with caveats" means the pattern from round 3 is sound and should be propagated, but the structural prerequisite (Fold extraction and NF-11 pattern documentation) should be resolved before most of the screen-level fixes. The implementation path above incorporates this staging. Owner sign-off recommended before code starts; implementer and owner should jointly review this report, confirm the prerequisite extraction and the four highest-severity Critical findings (duplicate-check, graph-review vocabulary, questionnaire FIELD_CONSEQUENCES, contradiction-review statements), and lock the build ticket accordingly.
