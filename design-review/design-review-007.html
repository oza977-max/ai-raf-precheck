Utility Tree — ATAM

Root utility: AIGate verdicts carry the firm's risk appetite, deterministically, verifiably, and without overstating confidence.

High Importance / High Risk

F1. First-time user comprehension and operability (NF-12): A submitter new to the product must understand what they are filling in and what the verdict means, and they must be able to navigate to correct their answers. High risk: keyboard and screen-reader users today cannot reach controls (DR7-10); the summary and correction flow need integration work (DR7-23). Panels: F1C and F1B; findings: DR7-10, DR7-23.

F2. Audit-trail integrity of new writes: Every write must be atomic and happen at most once per confirmed action, across tabs, retries, and crashes. High risk: the confirmation-double-write path is live (DR7-02); corrections can be silently clobbered across tabs (DR7-03); evaluation errors leave orphaned records (DR7-04); the description path's disclosure is unpersisted (DR7-07). Panels: F2C and F2B; findings: DR7-01 to DR7-05, DR7-07, DR7-12, DR7-16, DR7-22.

High Importance / Medium Risk

Determinism (NF-1): Same inputs always produce byte-identical verdicts. Medium risk: the issue is architectural (not new with D2 or E) and covered by existing tests (TC-PE-1-01). Panels: C; findings: none new.

Honesty (NF-7): The verdict never claims more than it can prove. Medium risk: false claims are rare (jargon on fallback paths, claims about fields never extracted). Panels: C and E; findings: DR7-06, DR7-25, DR7-30.

Security: The engine and forms resist tampering and misuse. Medium risk: identified by panels C and E; findings: DR7-01 (false tamper alarm), DR7-05 to DR7-07 (data leakage paths), DR7-09 (unchecked self-attestation), DR7-21 (policy tampering).

Findings — Built Code (R16-W and Earlier)

DR7-01 — Hand-off import calls an untouched file "tampered" when a record carries an unknown field

The import schema's record types are plain zod objects that strip unknown keys, and the seal and chain are then recomputed over the stripped copy. Any new optional field reaching an app version that doesn't recognize it triggers a false tamper alarm. D2's assumptions field will cause this the moment the schema lands.

Sources: F2C-1, F2B-6† (BC-7 corrected). Pre-existing schema design, made live by D2.

Fix: Let unknown record fields ride through (passthrough on the payload variants) so verification hashes what was sent; add D2's fields to the schema explicitly; test a bundle with an unknown field.

DR7-02 — Two tabs confirming the same draft both write a verdict; the second fails and every retry writes another duplicate pair

The cross-tab lock only orders writes, it does not detect repeats. The register write then fails ("Evaluation failed"), and the retry loop writes another duplicate audit pair.

Sources: F2B-7†, F2C-3. Pre-existing; register.ts:27 db.add; IntakeFlow.tsx confirm path; db.ts:9-36.

Fix: Refuse a second confirmation inside the locked write ("this case was already confirmed in another tab — reload"), no retry loop; correct the overclaiming comment and spec line.

DR7-03 — Two tabs correcting the same verdict: the later write silently replaces the earlier

The register's read-modify-write lets one person's correction stop being current without anyone being told.

Source: F2B-8†. Pre-existing; D2 widens the path (register.ts:190-217).

Fix: An expected-current-verdict check (the pattern replaceWithBundle already uses), refusing with a clear message.

DR7-04 — An evaluation error followed by Back leaves a creation + confirmation record with no case behind it

Confirmation is written before evaluate(), so a graph-review Back after an error creates an orphaned record. The retry starts a second case. Form-path users also land on the old field-card screen after an engine error (EVALUATION_FAILED).

Sources: F2C-2, CB-7†. Pre-existing; graph_review Back → duplicate check drops the case id (intake-state.ts:264-272), confirmation written before evaluate() (intake-state.ts:601-619).

Fix: Graph review Back and retry keep the same case; form-path graphs return to the filled form.

DR7-05 — "Start over" after a first form submit strands that submit's creation record

The recorded description can also differ from the one finally evaluated, since it is written at first Continue and edits come later.

Sources: F2B-1†, F2B-2†. Pre-existing.

Fix: On the form path write the creation record at Confirm — once, with the final description — instead of at first Continue. Simplifies W-4 and D2 §2.

DR7-06 — The engine imports from the screen layer, breaking the architecture's first rule

src/engine/plain-intake.ts imports question text helpers and types from src/components/plain-copy.ts. No lint rule catches it; D2 would deepen it.

Sources: CC-1 (rated Critical), CB-1†. Cross-cutting.md §7 prohibits engine → UI.

Fix: Move question ids and assumption keys to the engine side; screens resolve the words.

DR7-07 — Description path: "Things we couldn't tell" lives in temporary memory, not the saved draft

A refresh before Confirm silently drops it — the bug W-4 fixed for the form path.

Source: CC-2 (rated Critical). IntakeFlow.tsx:170, 751.

Fix: Carry it in the saved state.

DR7-08 — The form's agent-access question (Q13) maps ticks by hand instead of through the single access-scope checker

A mismatched saved answer would silently become "not stated" and skip the agent safeguards.

Source: EB-1†. plain-intake.ts:502-506; the "answered" check counts raw ticks.

Fix: One checker; check the result.

DR7-09 — The zone question (W-9) is unchecked self-attestation

The description-vs-answer plausibility check now runs only on the field-card screen the form path skips; nothing records which answer set the zone; after D2 answers can be re-tried freely.

Sources: EB-3†, EC-2. plausibility.ts:34-36; IntakeFlow.tsx:1498.

Fix: Run the plausibility check on the form path and show any warning on the summary; record how the zone was set; add the lever to the threat model (R16.md §0.1).

DR7-10 — Keyboard and screen-reader use: accessibility requirements never revisited for newcomers

Requirements still say "Consumer accessibility requirements (WCAG) do not apply to MVP"; sidebar items including "+ New pre-check" are clickable divs no keyboard can reach; no screen change moves focus; "Go to this safeguard" scrolls but doesn't move focus.

Sources: F1C-1..4, F1B-4†, F1B-5†. App.tsx:273-313; VerdictDisplay.tsx:1241; requirements.md:616.

Fix: An owner decision on the requirement, then real buttons, focus on each step's heading, focus on the target safeguard.

DR7-11 — The review/correction screen edits agent access with a single dropdown; cannot record more than one kind

Editing a correct multi-value answer silently narrows it with no check. The R16 plan says a tick-all editor exists (R16.md:42, D-22) — it was never built.

Sources: F1C-5, EB-5†, BC-5. GraphView.tsx:98-104, 413-423; IntakeFlow.tsx:529-560.

Fix: Build the tick-all editor through the single checker (in E); correct R16.md.

DR7-12 — A correction already drops the submitter's note and answer notes

These are written only on a first confirmation, not on corrections.

Source: F2B-5†. IntakeFlow.tsx:873-907.

Fix: Keep them on the correction record (D2 touches this branch).

DR7-13 — The "questions → contradictions → summary" routing rule is written twice

Once in form submit and once in the review screen. So are the policy gate checks.

Sources: CB-2†, CC-5. intake-state.ts:359-362 vs IntakeFlow.tsx:608-631.

Fix: One shared function.

DR7-14 — Minor batch: five observations

Two summary tables restate value lists instead of importing them; "UC-6b" used as if a requirement; "check" used for six different actions; the noun-phrase rule for review names is documentation-only; no authoring-checklist line for evidence scope.

Sources: BB-5†, AC-4, F1C-10, EB-6†, EC-7.

Fix: Import the lists; remove UC-6b references; pick one term for "verify"; document the noun-phrase rule in code; add evidence scope line to the checklist.

Findings — The "No" Screen Plan (R16-D2), Not Yet Built

DR7-15 — The "No" screen's "answers you weren't sure about" line would always be empty on a first result

The only carrier of the assumptions is gone by the result step, and the result screen is never given them. The plan frames the choice as correction-only and as an open "pick one".

Sources: DB-1†, BC-1, DC-1, CB-3†, CC-3. IntakeFlow.tsx:161; intake-state.ts:135.

Fix: Keep the confirmed answers and assumptions for the session (taken before Confirm, like the reviewer note), pass them to the result screen; state plainly that this lasts until a reload.

DR7-16 — Where assumptions live after a correction, and how the register reads them, is undefined

Corrections write no confirmation record; the register's existing lookup reads only confirmation records for notes and its current-verdict accessor excludes them.

Sources: DC-2, BB-2b†, F2C-4, F2B-4†, BC-2. register.ts:94-99, RegisterDetail.tsx:948-951.

Fix: Pin it — first confirmation → confirmation record; correction → the correction record; the register reads whichever matches the current verdict; tests for both.

DR7-17 — Correcting through the form must carry the original verdict id and description through the form state

If not carried, the correction is treated as a new case and the register write fails.

Source: DB-3†. intake-state.ts:12-25, 352-358; IntakeFlow.tsx:871, 1052.

Fix: Thread the verdict id and original description through the form state and submit action.

DR7-18 — The "No" sentence needs short question labels and a pointer clause

The full question text makes a run-on sentence. It should point to the full list of guesses so fixing one isn't mistaken for fixing all.

Sources: F1B-2† (rated Critical), F1C-8.

Fix: A short label per question; a pointer clause that explains this is a partial list.

DR7-19 — The "which guesses contributed" table must cover every question and be validated as a closed set

Must include 6a, 6b, the supplier sub-questions, and 4a. Must be checked against the mapping, validated as a closed set in hand-off imports, and not be keyed across the layer boundary.

Sources: DB-2†, BB-4†, EB-2†, EC-5, CB-1†.

Fix: Complete the table; add schema validation; test hand-off imports with the closed set.

DR7-20 — A "No" from a country rule pack gets a generic reason and no "contributed" line

Packs have no plain text for hard lines; the result view has no packs.

Sources: AB-3†, F1C-7. No shipped pack uses pack hard lines today.

Fix: State it as a known v1.0.0 limitation, or extend packs to carry plain text for hard lines.

DR7-21 — The plan adds a third "correct your answers" button; two already show on every result

This creates visual redundancy and unclear prioritization.

Source: DC-3. VerdictDisplay.tsx:1200, 2140.

Fix: The new text replaces the first-screen one; the lower one is hidden on a "No".

DR7-22 — Form-path correction records must keep the original node ids and cover every field including cleared ones

The rebuilt graph mints new ids. A removed model name is a missing key, not a changed one. The record must say "0 corrections — reviewed, nothing changed" and record that the correction came from the form.

Sources: BB-3†, BC-8, F2C-5, F2B-3†, F2C-6, CB-4†, CC-6.

Fix: Preserve node ids from the original graph; include cleared fields in the diff; add the form-origin flag; test all cases.

DR7-23 — The newcomer release test (NF-12) must include a "No" result, a correction, and a tick-all question

Today it only asks the three "can I start" questions.

Sources: AC-3, AB-4†. requirements.md NF-12.

Fix: Amend NF-12 to require: a "No" result, a correction, a tick-all question, and the three questions "why, what would change it, whom to ask" (owner decision).

Cross-Panel Themes

Theme A: Contracts Asserting Things About Existing Code That Were Never True

Findings: DR7-11, DR7-15, DR7-25, DR7-26.

The R16 build plan refers to code that does not exist or has never done what the plan claims: a tick-all editor in GraphView (DR7-11), session storage of assumptions (DR7-15), fields in the graph extractor (DR7-25), and named export SUMMARY_VALUES (DR7-26). These create builder confusion and will cause test failures when the code lands. All four require the plan to match reality — either build what the plan promises or rewrite the plan to match what exists.

Theme B: One Rule Implemented Twice or Not at All on One Path

Findings: DR7-08, DR7-09, DR7-13, DR7-27.

The form and description paths split the logic for agent access (DR7-08 does not use the shared checker; DR7-27's questionnaire does not support tick-all), plausibility checking (DR7-09 runs only on one path), and routing logic (DR7-13 is duplicated). These split implementations are a source of bugs (silent narrowing of access values, silent loss of zone attestation, different routing behavior) and maintenance cost. Each has a single-source-of-truth fix.

Theme C: Write-Once Integrity Broken Across Tabs, Retries, and Abandonment

Findings: DR7-01 to DR7-05.

Five findings (false tamper alarm, duplicate writes on confirm, silent overwrites on correction, orphaned records after error, stranded description) are all variations on the same architectural pattern: audit writes are not guarded against repeats, dropped values are not persisted, and error cleanup is incomplete. All are fixable within the existing architecture but require attention to atomicity, state lifecycle, and error handling. This is the F2 (audit-trail integrity) panel's core concern.

Theme D: Parallel D2/E Build Has No Owner for Shared Files and Shared Data

Findings: DR7-24, DR7-32.

D2 and E run in parallel and both touch IntakeFlow.tsx, the question list, and the result-screen assumptions. D2 specifies the assumptions as a correction-only feature (DR7-15), but E's questionnaire would generate assumptions that need to flow into D2's "No" screen. Without a named owner for the handoff, silent conflicts are guaranteed. The fix is explicit: build D2 first (in order from R16.md §6), then E as the owner of the shared screens.
