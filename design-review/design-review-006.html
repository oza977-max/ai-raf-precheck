Design Review 006 — plain-language intake and verdict (R16)

Review of build/prompts/R16.md against the round-16 requirements · 2026-09-28 · Round 1, liberal criterion

1. Summary

Six panels (A requirements coverage, B interface contracts, C structural soundness, D implementability, E security, F comprehension by a first-time user — the utility tree's one high-importance, high-risk leaf, NF-12) reviewed the build contract for the plain-language redesign before any code is written. All six returned. Code was read as committed (HEAD 2c05776) because other agents were editing the working tree.

47 findings after de-duplication: 15 Critical, 19 Important, 13 Minor. Every one is a gap or error in the contract — nothing has been built. The three themes: (1) the contract specifies the happy path and leaves identity, fallbacks and old data undefined (D-04, D-09–D-13, D-19, D-20); (2) three new surfaces were checked only for well-meaning use — a typed supplier name, “Not sure” on reversibility, and the policy's “covers” list (D-05–D-07, D-21); (3) the first screen and the form would re-derive facts that already exist elsewhere (D-02, D-03, D-28).

What held up: the question table's overall design, the PE-9 list matching (consistent with the engine's existing any-node rule), the “No” screen, the stricter-when-unsure principle where it is applied, the draft-versioning rule, and the chunk ordering (no circular dependencies).

2. Critical findings

D-01 — The first screen drops two things the submitter has today

Panels: A (C6 related) · R16.md §4 intro and content list; VerdictDisplay.tsx medium-confidence caveat, “Correct this classification?”

Everything that renders today moves into a fold titled for the AI risk team and collapsed for the submitter. That fold would now hold the medium-confidence caveat (RA-11: “verify this reasoning with your compliance team”) and the correction button (VD-3) — both addressed to the submitter, and both visible above the fold today by spec (verdict-audit §5.1, §5.3). The plain reasoning trace (VD-8) and the audit-trail honesty line (NF-2) go the same way.

Fix: Add to the first screen: the medium-confidence caveat, in plain words, under “Could still change”; and “Think we got something wrong? Correct your answers and check again.” wired to the existing correction flow, on every verdict (not only the “No” screen).

D-02 — The verdict screen's key facts would be worked out in four separate places

Panels: C, A, B · R16.md §4; VerdictDisplay.tsx WhatToDo, SignOffChecklist, controlEvidenceStates

What counts as outstanding, attested or machine-verified — and which reviews a safeguard covers — is already computed three separate times on today's screen (one mismatch was a Critical in code review 005). The plan names no shared module for the first screen, so it would become a fourth.

Fix: One pure module (no React) computes, once per verdict: each safeguard's status, owner text and “yours” flag, its plain reasons, the reviews it covers, and the reviews still owed. The first screen, the to-do list, the sign-off checklist and the evidence panel all read from it.

D-03 — With several kinds of information ticked, the confirmation grid shows only the first

Panels: C, B · graph-summary.ts (input_nodes[0]); condition.ts describeGraphPath

The tick-all question creates one input per kind of information, but the shared summary behind the attestation grid and the verdict's detail grid reads only the first input. A submitter would attest to a grid that silently leaves out price-sensitive information they ticked second. The graph-path sentence has the same blind spot.

Fix: graph-summary lists every input (or the most sensitive, using one exported ranking shared with envelope.ts); the graph-path description names the input that actually matched where it can; tests with two and three ticked kinds.

D-04 — Reviews have no reliable identity for “this safeguard also covers that review”

Panels: B, D · R16.md §1.2–1.4, §4; evaluate.ts downstream_review_sources; jurisdiction.ts

Only the firm's own review rules carry an id today; pack reviews and the two reviews the engine writes itself do not. The plan's single literal ids would merge two different unlisted suppliers into one line, while the firm's two information-security rules (different ids, same review) would show twice. The worked example uses a description instead of the real pack rule id (SS1-UK-REV-01).

Fix: Every review on a verdict carries a source entry — firm rules, pack rules and engine reviews — with a per-instance id (e.g. PV-UNREGISTERED:<component>). “Covers” matches by id; the “checks other teams run” list then de-duplicates by plain name. Fix the SS1/23 example.

D-05 — A typo in the policy's “covers” list could hide a required review from everyone

Panels: E · R16.md §1.2; src/store/policy.ts (no cross-reference checks)

One firm-edited list would decide what disappears from both the submitter's screen and the reviewer's section, and nothing checks the ids when the policy loads.

Fix: Check every “covers” id when the policy loads and refuse to start with a clear error if one doesn't exist (as CF-5 does). Covered reviews leave the submitter's list only; the reviewer's section always lists every review, marked “covered by …”.

D-06 — Typing a supplier's name could borrow an assessed supplier's record

Panels: E, B, A · R16.md §2 row 3+; evaluate.ts resolveInheritance (exact-id match inherits the supplier's envelope)

The plan matches a typed supplier name to the firm's list. Typing the name of an approved supplier would make an unassessed tool inherit that supplier's approved limits and skip the supplier checks — exactly what a submitter wanting a lighter verdict would try. The matching rule itself was also unspecified.

Fix: Pick the supplier from the firm's list (by its plain name), or choose “Not on this list — type its name”, which always counts as not yet assessed. Never match typed text to the list.

D-07 — “Not sure” about undoing mistakes is treated more leniently than “No”

Panels: E · R16.md §2 Q9; policy HL-001, INV-IRREV-01 (match only “irreversible”)

The plan maps “Not sure” to “unknown”, which neither the hard line nor the undo-window rule matches — so “Not sure” can clear a line the firm never crosses, while “No” would not. That breaks the approved “Not sure takes the stricter reading” rule.

Fix: “Not sure” → can't be undone (listed as an assumption). Add a worked case: acts entirely by itself + clients see it + “Not sure”.

D-08 — The describe-it-in-words path can't record what an agent can reach

Panels: B, E · R16.md §5; src/llm/graph-extractor.ts (field not extracted); types.ts IntakeQuestion (no multi-select); QuestionnaireStep (single choice)

The field is never extracted from a description, so no follow-up question is ever asked about it, and the question machinery has no tick-all type. UC-10 and UC-12 require both paths to capture it.

Fix: Chunk E adds the field to the extraction schema, a tick-all question type with an array-aware answer check, and a tick-all control in the questionnaire and the graph review screen.

D-09 — How the firm's own AI service maps to a supplier is undefined

Panels: D · R16.md §2 Q3(d); RegistryEntry has no vendor field

Whether supplier checks apply to a platform-based use depends entirely on the vendor value, and the plan gives no source for it.

Fix: Platforms gain an optional supplier id (the supplier behind the service); absent means built in-house. Starter policy: the cloud AI assistant names the firm's registered AI supplier.

D-10 — “The company AI-assistant account” can't be picked out once a firm lists a second supplier

Panels: D, B · R16.md §2 Q3a; vendor registry has no kind field

“Exactly one registered company-assistant vendor” works today only because there is one supplier in the starter file; the fallback question has no wording.

Fix: Suppliers gain an optional kind (company assistant / other). Q3a picks the one company assistant; with several, a follow-up lists them by plain name (exact wording specified); with none, not yet assessed.

D-11 — Where the AI processes the information is never stated

Panels: D · R16.md §2; StructuredFormValues.processingDataZone (required)

The processing node's zone is required today and the plan never says what fills it.

Fix: Processing zone = the destination zone from Q3/Q3a; state it in the mapping table and test it.

D-12 — The same-answers-same-verdicts check could prove nothing

Panels: D, C · R16.md §2 parity test; backtest-predictions.test.ts; backtest-corpus.test.ts

The same builder would write the mapping and the answers that “prove” it; the comparison fields aren't named (ids and timestamps differ every run); and one worked case (the regulatory-reporting drafter) is already unreachable because Q8 is now required.

Fix: Answers for each worked case are written from the case's narrative only — never from its recorded form values or prediction — by a different agent from the builder, stored as a fixture file, and compared on a named subset (status, tier, track, binding constraint, controls, reviews, tripped rules). Each difference is listed for the owner; UC-8 vs UC-8b resolved up front.

D-13 — The form's answer format is unspecified

Panels: D · R16.md §2 plainAnswersToFormValues(answers, policy)

The one new function the chunk exists for has no input shape, which forces the builder to invent the form's state model.

Fix: answers: a record keyed by question id ('1', '3', '3a', …, '14') holding a string or a list of strings; plus the typed shapes of Assumption and the result.

D-14 — Three different names for IT on one screen

Panels: F · R16.md §1.4 owner table

“Your IT or platform team”, “your IT security team” and “IT, or whoever sets the tool up” would appear side by side on an agent case — the same confusion testers raised about “security” versus “information-security”.

Fix: Owner decision (see triage): two names — “your IT team (or whoever sets the tool up)” for building and running the tool, and “your information-security team” for anything about security — used everywhere.

D-15 — Country-rule reviews would show raw regulatory titles on the first screen

Panels: F · R16.md §1.4 (pack names drafted, not approved); §4 fallbacks

The plain names for the reviews that come from country rules are drafts awaiting approval, and the fallback shows the formal title (e.g. “ICT third-party concentration review (DORA Art. 28/29)”) — engine vocabulary on the first screen.

Fix: Owner approves the drafted names (see triage). A review with no plain name shows “a regulatory review required for this kind of use — ask your AI risk team which” instead of its citation.

3. Important findings

D-16 — “Stricter” zone ordering isn't defined

Panels: D · R16.md §2 Q3(d)

A builder could read “stricter” as the more locked-down zone — the opposite — and silently switch off the data rules for platform cases.

Fix: State once: zones run most exposed → most contained as A, B, C; “stricter” always means the earlier letter.

D-17 — Questions 6 and 7 have no “Not sure”

Panels: D · R16.md §2 Q6, Q7

Every other closed question offers it; these two gate autonomy, weight and audience.

Fix: Owner decision (see triage). Recommended: no “Not sure” — the submitter knows what their tool does and who gets the result — and the form says so.

D-18 — The form and the “what we understood” screen must ship together

Panels: D · R16.md §6 order

If chunk B lands before chunk C, the live site briefly takes new answers without showing what it understood.

Fix: B and C are one release unit: built in order, committed together.

D-19 — Old saved verdicts need safe fallbacks

Panels: D, C, B · R16.md §4 fallbacks; provisional.ts legacy branch; RegisterDetail reuses VerdictDisplay

Verdicts saved before this change lack review source ids and may lack provisional reasons; the plan only covers “no policy loaded”.

Fix: Old verdict without source ids → list every review separately, never fold one away. “Could still change” is gated on isVerdictProvisional, with a generic line when no specific reason is recorded.

D-20 — A bare rule code could still reach the screen

Panels: E, B · R16.md §4 fallbacks; VerdictDisplay.tsx `control?.name ?? id`

With no policy loaded, or a control since renamed, today's fallback prints the code (e.g. CTRL-ENC-01) — which NF-11 forbids.

Fix: Never print a bare code on the first screen: “Safeguard 1, 2, …” with “ask your AI risk team what this involves”; the reviewer section keeps the code beside its gloss.

D-21 — No threat model

Panels: E · R16.md (whole)

The plan never names who could misuse the new surfaces — which is how D-05, D-06 and D-07 were missed.

Fix: Add a short threat model: a submitter optimising for a lighter verdict; a careless or malformed policy or pack file; a hand-off bundle carrying old or crafted verdicts. State what each new surface does against each.

D-22 — The graph review screen can't edit a list of access kinds

Panels: B · GraphView.tsx PROCESSING_FIELDS (single select)

The screen where a submitter or reviewer corrects the graph can show and edit only one value.

Fix: Tick-all control for this field in GraphView; its corrections recorded as today (UC-7).

D-23 — A platform or supplier without a plain name would break the no-jargon rule on the form

Panels: B · R16.md §1.2, Q3(d)

Unlike the verdict, the form has no acceptable “formal text” fallback.

Fix: Platforms and suppliers without a plain name show “Your firm's AI service 1, 2, …” on the form, and the policy check warns at load.

D-24 — Nothing guarantees the access list is sorted in the form path

Panels: C · R16.md §1.1 vs Q13 option order

The canonical order and the question's display order differ, and no test ticks boxes in a different order.

Fix: buildGraphFromForm sorts; a test ticks the same boxes in two orders and gets byte-identical graphs.

D-25 — Two parallel chunks share the one stylesheet

Panels: C · R16.md §6; src/App.css

Chunks B and D run in parallel and both will need new styles in the single stylesheet.

Fix: Each chunk adds its styles in its own clearly-marked block; the second to finish merges.

D-26 — “Yours” safeguards have no action on the first screen

Panels: C (A-01 related) · R16.md §4

The owner-assignment and attest actions live in a fold labelled for another team.

Fix: Each “yours” safeguard on the first screen links to its action in the detailed section (opens and scrolls to it).

D-27 — “No model was named” is promised but unassigned

Panels: A · UC-11 fit criterion

Making the model name optional is the first time it can be blank; nothing states it.

Fix: The reviewer section says “No model was named — your AI risk team may ask which one it uses.”

D-28 — Shared labels still carry codes such as “(LLM)”

Panels: A, C · field-copy.ts label maps; QuestionnaireStep

The describe-it-in-words path would inherit the codes; stripping them would break the reviewer grid that needs them.

Fix: One shared, code-free set of question and option texts used by both paths; the code-bearing labels stay for the reviewer grid.

D-29 — Requirement UC-3a now contradicts UC-8

Panels: A · requirements.md UC-3a

Its fit criterion still describes labelled engine fields.

Fix: Amend UC-3a: the surviving obligations are no API key needed, the same graph shape, and marked as form intake.

D-30 — “(name not verified)” would mean two different things

Panels: F · R16.md §1.2 vs §4

On an owner assignment it would suggest the safeguard is claimed done; on an attestation it means “only as good as this person's word”.

Fix: Assignment line: “{name} (assigned on your firm's register), due {date}”. Keep “(name not verified)” for attestations only.

D-31 — Question 4 has no example for translation

Panels: F · R16.md §2 Q4

Q3 names translation websites; Q4 then leaves the reader to guess.

Fix: “Reads, summarises, translates, writes or answers questions in words”.

D-32 — “What to charge a client” doesn't cover valuation models

Panels: F · R16.md §2 Q8

A quant's pricing or valuation model has no clear option.

Fix: “What to charge a client, or how something is priced or valued”.

D-33 — Question 7 assumes a person reads the output

Panels: F · R16.md §2 Q7

An agent that changes code or systems produces nothing people “receive”.

Fix: Help text: “If it changes code, records or systems instead, think about who is affected by those changes.”

D-34 — Chunks A and D each bundle two different jobs

Panels: A · R16.md §6

A mixes engine plumbing with owner-approved content; D bundles the “No” screen with the main screen.

Fix: Split A into A1 (schema and engine) and A2 (policy text); build the “No” screen as its own slice of D.

4. Minor findings

D-35 — The reviewer fold must wrap today's content unchanged

Panels: D · R16.md §4

D-36 — Q11 “required” means an option picked

Panels: D · R16.md §2

Fix: Required = an option selected, not a non-empty list.

D-37 — Which Q3 answers show the name fields

Panels: D · R16.md §2 row 3+

Fix: Name fields show for the outside-assistant, software-feature and specialist-product answers only.

D-38 — Empty next-step bullets

Panels: D · R16.md §4 item 3

Fix: Omit empty bullets; “Then …” only follows a preceding step.

D-39 — Unknown placeholders and owner tokens

Panels: E · R16.md §1.2

D-40 — “Not in” under list-valued fields

Panels: B · condition.ts matchesOperator

“Any value matches” semantics would make a not-in test pass when an excluded value is present.

Fix: Document that list-valued fields support “in” only; the policy check rejects “not in” on them.

D-41 — Old form drafts need an actual notice

Panels: B · intake-draft.ts

A renamed key alone hides the old draft silently.

Fix: Probe the old key, clear it and show the one-line notice.

D-42 — VD-2 needs the same amendment note as VD-1

Panels: A · requirements.md VD-2

Fix: One-line amendment: the binding rule's plain reason is on the first screen; its formal text and graph path are in the reviewer section.

D-43 — The summary component must not write

Panels: A · R16.md §3

This codebase has twice needed guards against double audit writes.

Fix: State the summary only navigates (“Change an answer”); the one write stays on the existing Confirm button.

D-44 — “Provisional tier” shows on the questionnaire

Panels: A · QuestionnaireStep progress line

Fix: Replace with “Question X of Y”.

D-45 — The worked-case document's “form values” go stale

D-46 — Q4's “pick the lowest” needs an example

Panels: F · R16.md §2 Q4

An interview note-taker transcribes and summarises; readers stop at the first match.

Fix: Add: “for example, something that turns speech into text and writes a summary of it”.

D-47 — Fallback text gives no next step

Panels: F · R16.md §4 fallbacks

Fix: Every fallback line ends “Ask your AI risk team what this means for you.”

5. Owner disposition

Owner disposition (2026-10-02): "Fix all 47 in the plan, then re-check." None deferred, none dismissed. Three findings needed an owner decision and got one:

  • D-14 team names: two names — "your IT team (or whoever sets the tool up)" and "your information-security team"; the model list goes to "your AI risk team".
  • D-15 review names: the drafted plain names for the pack and engine reviews are approved as written.
  • D-17 questions 6 and 7: they offer "Not sure", which takes the strictest answer (acts entirely by itself; the public or the market) — not the recommended option. The contract adds a line to the "No" screen naming the assumed answers when they contributed.

The contract was rewritten as v2 (build/prompts/R16.md, 2026-10-02), citing the finding id each change closes, and two requirement amendments were added (UC-3a, VD-2). Round 2 (strict) re-checks v2.

6. Round 2 (strict, 2026-10-02)

Three combined panels (A+D, B+C, E+F) re-checked contract v2. Of the 47 round-1 findings, 42 were confirmed closed and 5 only partly (D-03 graph-path sentence, D-04 review sources at every return site, D-07 missing worked case, D-26 link vs a controlled disclosure, D-47 one fallback without a pointer). 19 new findings (D-48 … D-66), of which 4 Critical: "Not sure" on the kind of AI mapped below the strictest reading (D-48); the threat model promised hand-off validation for data that never travels (D-52); the pack hard-line rejection returns no downstream reviews at all — a live engine bug (D-58); and the new policy check had no single function or named call sites (D-60). All were written into contract v2.1, each citing its id.

Owner disposition (2026-10-02): "Start building from v2.1." The "Not sure" → AI agent change (D-48) was put to the owner explicitly and accepted.

Verdict: Build with caveats. Caveat: the round-2 fixes are in the contract but were not re-reviewed by a third plan round; each lands with its own tests in the build, and the code review after the build is the next independent check.
