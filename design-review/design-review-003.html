Executive Summary

This screen has been through 5 prior redesign rounds (R9, R12, R13, R14, R15-C2) without resolving a recurring "too much going on, confusing" complaint from the owner. A real exploratory-test session (explore-006, practitioner-classified, not LLM-self-graded) found 3 Critical UX defects for a non-technical reader. This design review, triggered by that session, confirms and substantially extends those findings — 6 Critical and 8 Important issues total after cross-panel deduplication (from ~25 raw panel findings).

Panel A's key structural insight: no requirement in this project currently forbids internal spec-ID leaks into rendered text, or specifies fold-state-by-audience — that gap in the requirements, not a coding mistake, is why 5 prior rounds never caught this class of defect. Three independent panels (C, D, G) converged on the identical concrete fix mechanism for the review's core finding.

Critical Findings

Six critical issues, all with traced locations and specified fixes:

1. Internal spec-IDs leak into rendered text
Panels A, D, G converged. NF-7 rendered in VerdictDisplay.tsx (provisional-only); NF-2, VD-4, and LC-2 rendered in RegisterDetail.tsx headings and text (every visit, not provisional). Users see "(NF-7)", "(NF-2)", "(VD-4)", "(LC-2)" parenthetical codes throughout the screen.
VerdictDisplay.tsx:56, :1353; engine/jurisdiction.ts:93; RegisterDetail.tsx:716, :909, :919
Fix: One-line string edits stripping the parenthetical codes. NF-7's source is engine/jurisdiction.ts:93 where jurisdiction name is concatenated with spec-ID.
2. Sign-off checklist leads with bare rule ID before gloss
Panels A, B, D, G converged. Structural, fires for every verdict. Section reads "Decided by {verdict.binding_constraint}" with no plain-language description of what that constraint means, leaving non-technical readers in the dark.
VerdictDisplay.tsx:576-582
Fix: Call the already-imported findRuleDescription(policy, verdict.binding_constraint) and render the description first, ID demoted to quiet code — an identical pattern already exists at VerdictDisplay.tsx:927.
3. "Why this verdict" has no fold/collapse mechanism
Panels A, C, D, G — four independent panels — all identified this as the core defect. VerdictDisplay.tsx:897 renders "Why this verdict" reasoning as a bare <div> while every sibling analytical panel (fragility, inheritance, regulatory reasoning, control set, expiry conditions, "what you told us") uses the existing Fold component with defaultOpen={false}. This is THE reason 5 prior rounds never fixed the "too much going on" complaint — the page renders permanently dense.
VerdictDisplay.tsx:897
Fix (independently converged by 3 panels): Thread the role prop RegisterDetail.tsx already holds (already used for showSignOffChecklist at line 672) into VerdictDisplay as a new prop; wrap WhyThisVerdict in <Fold defaultOpen={role === '2LoD'}>, matching the existing Fold summary-gist pattern used elsewhere in the same file.
4. Audit trail literally renders the word "rejected"
Panel B independently verified against source. RegisterDetail.tsx:71-73 renders p.action.replace('_', ' ') where action: 'approved' | 'rejected' | 'correction_requested' (confirmed in src/store/types.ts:93). Direct live violation of this project's own explicit reserved-word rule (HR3-08, the /approved|rejected/i acceptance-test collision rule documented in verdict-audit.md §13.3).
RegisterDetail.tsx:71-73; src/store/types.ts:93
Fix: Add an ACTION_LABEL map (e.g., approved→"signed off", rejected→"sign-off rejected — correction not requested") mirroring the existing STAGE_LABELS precedent, render through it instead of the raw enum.
5. Audit-trail timeline shows raw enum where the same field shows label elsewhere
Panel B. RegisterDetail.tsx:62-63 renders ${p.from_stage} → ${p.to_stage} raw, while RegisterDetail.tsx:573 correctly uses STAGE_LABELS for the same field on the same page. Direct self-contradiction.
RegisterDetail.tsx:62-63 vs :573
Fix: Replace raw enum with ${STAGE_LABELS[p.from_stage]} → ${STAGE_LABELS[p.to_stage]}.
6. STATUS_LABEL lookup table defined twice, independently
Panels B and C found this separately. VerdictDisplay.tsx:82-86 and RegisterDetail.tsx:33-37 are verbatim duplicates; neither imports from the shared field-copy.ts both files already import from. Drift risk: a future status value added to one copy and not the other would make the verdict heading and register chip disagree silently.
VerdictDisplay.tsx:82-86 and RegisterDetail.tsx:33-37 (duplicates)
Fix: Hoist one export into field-copy.ts, both components import it.

Cross-Panel Themes

Theme 1: ID-before-gloss pattern (findings 1, 2, 7, 8, 9, 10) — six separate instances where internal-only identifiers appear on-screen before or without adjacent plain-language gloss. This is a systemic defect class, not an isolated mistake. Root cause: no requirement exists forbidding it. Recommendation: Add a new non-functional requirement (e.g., NF-11: "no internal-only identifier renders on a user-facing screen without an adjacent plain-language gloss") and add it to pre-submission review checklist.

Theme 2: Fold-mechanism gap (finding 3) — the review's central and most-converged finding. Four independent panels identified this as the single thing preventing the screen from serving non-technical readers. All other analytical panels use Fold with sensible defaults; WhyThisVerdict was built without one. Recommendation: Thread role prop and wrap in Fold.

Theme 3: Duplication and shared-source gaps (findings 6, 12) — STATUS_LABEL defined twice, "sign-off still required" logic derived in three places. The codebase has proven shared-source patterns (field-copy.ts, STAGE_LABELS, findRuleDescription) that work correctly where used. These are implementation discipline issues, not missing mechanisms.
