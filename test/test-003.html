The pattern worth naming

7. Findings

CS-3: no InfoSec review binding exists (MUST, V1 scope)

CS-3 requires the verdict to list downstream reviews triggered by the use case's characteristics, naming InfoSec review as an example. grep -rn 'InfoSec' policy/ src/ returns nothing. downstream_reviews is populated only from jurisdiction-pack required_review rules and the unapproved-component path. An MNPI-handling use case triggers no InfoSec review because no such rule exists in the policy or the engine.

TC-CS-3-01 · requirements.md CS-3 · evaluate.ts:246-248
PE-6: "most demanding standard governs" is half implemented (MUST, V1 scope)

PE-6 says "Track and tier assignments shall never be reduced below the jurisdictional minimum." Tier floors work and are tested. Track floors do not exist — and their absence is deliberate: engine/types.ts:198-200 records that track_floor is "intentionally absent — the supplement model was decided instead". So the requirement's own fit criterion (a UK Track II overriding a US Track III) cannot be produced by the engine. Found independently by two reviewers as TC-PE-6-01 and TC-RA-2-01.

TC-PE-6-01, TC-RA-2-01 · engine/types.ts:198-200 · jurisdiction.test.ts:86
UC-2: the submitter cannot adopt an existing classification (MUST, V1 scope)

UC-2's fit criterion says the submitter "may adopt the existing classification or confirm their use case is genuinely new". Only the second action exists. The UI instead directs the user to "Contact AI Risk to adopt its classification" — an out-of-band human step. Honest in what it claims, but the in-product action the requirement describes was never built. The dismissal also writes no audit event.

TC-UC-2-02, TC-UC-2-03 · IntakeFlow.tsx:511-548, 172-187
NF-10: the translation-fidelity label is a static banner, not a computed one

NF-10 requires that a policy file without a current attestation "produces verdicts marked translation fidelity unattested". The attestation block exists in the schema and is validated. Nothing reads it: the header string at App.tsx:83 is unconditional, and no verdict carries the label. Today it happens to be true — the shipped policy is unattested — so the product under-claims rather than over-claims. But if someone attested, the UI would still say unattested. This is the computed-but-never-consumed pattern CLAUDE.md warns about, in its milder direction.

TC-NF-10-01 · App.tsx:83 · engine/types.ts:381
UC-1: the submitted description is discarded

The description is captured and used for extraction, then never shown back to the submitter. This is charter 004's D-001, still unrouted — now confirmed by an independent walk of TC-UC-1-01.

TC-UC-1-01 · IntakeFlow.tsx:496-508 · charter 004 D-001

12. What this verdict does and does not say

Demo-ready means the product does what it claims, end to end, and states its limits honestly on screen. A reviewer can drive a use case from description to verdict to sign-off, and every screen tells them what it knows and what it does not.

It is not Ship-ready, and the reason is specific rather than vague: one MUST requirement in V1 scope has no implementation at all (CS-3), one is half built (PE-6), one in-product action was never built (UC-2 adopt), and nine behaviours that are true today are defended by no test. None of these is hidden; all are now named.

The honest reading: this remains proof-of-concept grade for audit purposes, which is exactly what the product says about itself in its own audit-trail caveat. That self-description is accurate — which is itself the strongest signal in this report.

13. Method note

The 81 untraced cases were walked by four independent agents working in parallel, each instructed that a status without a command and an observed result would be rejected, and that NOT-WALKED was an acceptable answer where PASS could not be evidenced. Every finding they classed as serious was then re-verified directly before entering this report — two were re-framed as a result: RA-8 and PE-6 were reported as unbuilt requirements and are in fact recorded deliberate decisions.

Deviation from the skill: the HTML was written directly rather than dispatched to a Haiku subagent, because the finding set is large and passing it through another agent adds a transcription step to evidence that must stay exact.
