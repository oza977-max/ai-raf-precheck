Critical findings

CRITICAL · C-1 — platform_satisfies references platform ids that do not exist

Location: policy/appetite.yaml:337,338,391
Found by: Panel A · Hunt & Thomas (The Pragmatic Programmer)

Issue: CTRL-ENC-01 lists azure-openai-internal and azure-openai-eu; CTRL-LOG-01 lists azure-openai-internal. The registry defines PLAT-INTERNAL-ML and PLAT-CLOUD-LLM. Verified mechanically: the referenced ids appear nowhere else in the repository.

Fix: Delete the stale entries, or rename to the registry ids. But see C-2 — the field has no consumer, which is why this could never fail at runtime.

CRITICAL · C-2 — Control.platform_satisfies still has zero production consumers — the defect I claimed to have fixed INTRODUCED THIS SESSION

Location: src/engine/types.ts:432
Found by: Panels A and B, independently → severity elevated

Issue: PV-A built inheritance on platforms[].satisfies_controls (the inverse relation, keyed by platform id). The original controls[].platform_satisfies is still declared, still populated, still read by nothing. A second working mechanism was added alongside the dead one rather than replacing it. Two panels found this independently.

Fix: Either wire it into envelope.ts, or delete it from the schema, appetite.yaml and fixtures. Leaving both is what makes C-1 silent.

CRITICAL · C-3 — resolved conflates platform and vendor, masking an unapproved component INTRODUCED THIS SESSION

Location: src/engine/evaluate.ts:302
Found by: Panel C · Michael Fagan (formal inspection)

Issue: resolved: entries.length > 0 is true if either matched. A use case declaring an approved platform and an unapproved vendor emits zero unapproved-component reviews. PV-5 exists precisely to prevent this.

Fix: Track platformResolved and vendorResolved independently; fire a review per declared-but-unmatched component.

CRITICAL · C-4 — Asymmetric guards drop the declared-but-unrecognised vendor case entirely INTRODUCED THIS SESSION

Location: src/engine/evaluate.ts:274-275
Found by: Panel C · Boris Beizer (Software Testing Techniques)

Issue: Guard 1 tests !platformId && !vendor — a pre-lookup id paired with a post-lookup object. When only a vendor is declared and it is absent from a non-empty registry, the function returns undefined before guard 2 can distinguish 'no registry' from 'registry does not recognise this'. The caller never learns a vendor was declared.

Fix: Short-circuit only when nothing was declared (!platformId && !vendorId). Any declared-but-unresolved id must produce a chain with resolved: false.

CRITICAL · C-5 — Check-then-act race on an append-only audit trail INTRODUCED THIS SESSION

Location: src/seeds/sample-register.ts:151
Found by: Panel C · Kent Beck / the project's own CLAUDE.md

Issue: if (await getUseCase(id)) continue is TOCTOU across an async boundary. Two concurrent calls both see 'absent' and both write, producing duplicate audit events — which by design cannot be cleaned up. aigate-self-assessment.ts sitting beside it does this correctly with a synchronous in-flight promise, and CLAUDE.md documents the lesson explicitly.

Fix: Wrap the body in the same synchronous in-flight promise guard used by aigate-self-assessment.ts.

CRITICAL · C-6 — PV-6 inheritance copy reintroduces the banned word "approved" INTRODUCED THIS SESSION

Location: src/components/VerdictDisplay.tsx:241,253,259
Found by: Panel D · McConnell / project convention

Issue: Acceptance tests use a single-match getByText(/approved|rejected/i). The new inheritance block renders 'ON THE APPROVED REGISTRY', 'approved envelope', 'approved registry'. Currently latent — WalkingSkeleton declares no platform, so the block never renders there. It breaks the moment anyone tests a use case with a platform.

Fix: Reword to 'covered' / 'registered'. A landmine, not a live failure — which is worse, because it detonates for the next person.

CRITICAL · C-7 — Spec HTML silently stale against its own .md INTRODUCED THIS SESSION

Location: specs/verdict-audit.html
Found by: Panel D · project convention

Issue: The V2-D reword landed in verdict-audit.md and never in verdict-audit.html. Verified: the new string appears once in .md, zero times in .html. spec-parity-check.py reads only .md by design, so it cannot see this.

IMPORTANT · SR-1 — PV-2 and PV-5 are unreachable from the product's own intake

Status: deferred — awaiting triage (promotion route to requirements.md not yet chosen)

Found: while fixing C-3. build-graph-from-form.ts:58 hardcodes vendor: 'internal' and StructuredForm.tsx never asks for a vendor or a platform (zero mentions). Every use case submitted through the app therefore declares the same vendor and no platform.

Consequence: PV-2 (Must — an unregistered model is treated as a new vendor) can never fire, and PV-5 (Must — unapproved-component routing) is reachable for platforms only. Both are specified, implemented in the engine, and now test-covered, with no path from the UI. Testers cannot exercise inheritance at all.

Not fixed in this pass — it is a requirements question (PV-4's neighbour), and adding a feature during a fix pass is the scope confusion that produced HR-12 earlier the same day. Narrow mitigation applied instead: 'internal' is treated as a reserved sentinel meaning "no third-party vendor", since it is not user input. Any other value remains a real registry claim.

Promotion route pending: acceptance criterion on PV-2/PV-5, a new requirement in the PV domain, or Round 2.
