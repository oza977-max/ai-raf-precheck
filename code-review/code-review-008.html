2. Headline

The CR7 fixes held where they were aimed; the defects found are in the edges of the new mechanisms. The "Not sure" assumptions now survive every way back to the review screen (CR7-02) — but editing that field’s card on the revisited screen does not remove the now-false assumption, so the signed record says "we assumed…" about a value the person set (four panels). The non-permissive "no sign-off on record" headline (CR7-09) is contradicted by the next-steps list on the same screen ("You can start"). The Back guard after a failed evaluation (CR7-03) survives the questions but not a trip through the confirmation and "Change an answer" — Back can then orphan a case that already has a signed attestation. And the audit-trail wording added overnight ("a later change … would show as a break") is not true for deleting the newest entries, which leave a chain that still verifies.

4. Important findings (CR8-01 – CR8-05), all verified

CR8-01 — Important
Editing an assumed field on a revisited review screen keeps the "we assumed…" line.

File: src/components/intake-state.ts ~870-935 (CORRECTION_APPLIED), ~945-955 (JURISDICTIONS_SET); written at IntakeFlow.tsx ~1245, ~1461.

Impact: after "Change an answer", a failed result or a correction from the result, a person who edits the card for a field they had answered "Not sure" still sees "we assumed the strictest case" for it on the confirmation and the result, and the permanent graph_confirmed / verdict_corrected record carries it. The "No" screen can blame that assumption. A false claim on append-only evidence (BC-005). New with CR7-02.

Found by: C blind, A blind, B calibrated, C calibrated, D calibrated. Verified: V8-1 (probe).

Fix: in CORRECTION_APPLIED drop assumptions whose fields include the corrected field; same in JURISDICTIONS_SET for jurisdictions. Test per re-entry path, asserting the graph_confirmed payload.

Recommend: fix. Disposition: fix — owner decision, 2026-10-04.

CR8-02 — Important
"No sign-off on record" headline, but the next steps say "You can start".

File: src/components/verdict-view-model.ts ~939 (signOffMissing), ~1057 (buildNextSteps call), ~700-704.

Impact: for a case that needed sign-off and has none on record at a later stage, the headline says "confirm with them before you start" and the list directly under it says "You can start. It’s saved on your firm’s register…." Two opposite instructions on one screen; the permissive one is the actionable one.

Found by: A calibrated. Verified: V8-2 (probe with the shipped policy).

Fix: pass signOffMissing into buildNextSteps; a non-permissive step and finish line; assert "you can start" is absent from every next step.

Recommend: fix. Disposition: fix — owner decision, 2026-10-04.

CR8-03 — Important
After a failed result, confirmation → "Change an answer" → Back can orphan the case.

File: src/components/intake-state.ts ~1176-1197 (PROCEED_TO_CONFIRMATION drops the flag), ~1199-1245 (CHANGE_ANSWER), ~681 (STEP_BACK guard); IntakeFlow.tsx ~228-247.

Impact: the Back guard set after a failed evaluation is lost through the confirmation step, so Back walks out to the duplicate check and the next Continue mints a new case id — the first case’s use_case_created and graph_confirmed stay on the append-only trail with no verdict. The CR7-03 fix covered Back from the questions only (RF-9 / BC-004 again).

Found by: A calibrated, D calibrated (C calibrated as an observation). Verified: V8-2 (reducer probe; UI route by code).

Fix: carry afterFailedEvaluation on confirmation (and evaluation_pending); CHANGE_ANSWER restores it. Reducer and UI test for the five-step sequence.

Recommend: fix. Disposition: fix — owner decision, 2026-10-04.

CR8-04 — Important
The audit-trail wording claims more than the chain check proves.

File: src/components/RegisterDetail.tsx ~1403-1416 ("a single altered or deleted event breaks the chain"; "Chain integrity verified … unbroken"); src/components/ConfirmationStep.tsx ~88-91 (the confirm notice, written overnight); src/store/audit.ts ~410-413 (comment).

Impact: deleting the NEWEST entries (e.g. a trailing sign-off or correction request) leaves a chain that still verifies — proved: append 3, delete the last, verifyChain ok. A reviewer reading "verified … unbroken" or a submitter reading "a later change would show as a break" is told more than the check can prove (NF-2 / BC-005).

Found by: G blind. Verified: V8-1 (probe) — Important for the register banner, Minor for the confirm notice.

Fix (wording only — no tail anchor exists): "an edited event, or a deleted event with later events after it, breaks the chain; removing the newest events can’t be detected from inside this browser"; banner "No break found in the N events present"; confirm notice "a later edit to an earlier entry would show as a break…"; spec twins.

Recommend: fix. Disposition: fix — owner decision, 2026-10-04.
