2. Cross-cutting themes

1. The hand-off import trusts the file too much

A file that travels between people is untrusted input, but import validates only its outer shape: timestamps, register metadata, event types and payload fields pass unchecked, and one bad value can freeze the register list or break every later write (F3, F4, F13, F20).

2. The hand-off's safety promises are stronger than the mechanism

"Any change in transit is detected" and "a backup was downloaded first" are both stated unconditionally; the seal is an unkeyed hash anyone can recompute, and the backup is never checked (F1, F2, F14).

3. Multi-step writes are not atomic and not serialised

Import checks the chain outside the write queue, writes two databases without rollback, and swallows failures (F5, F6, F15, F16, F17, F18).

4. The new "attested" tier did not reach every surface

The evidence panel still says UNVERIFIED, the checklist reuses "in place", and the policy-not-loaded case disagrees with itself (F8, F11, F12, F19).

5. Traceability of the new features themselves

Both features were labelled with requirement ids that already mean something else, have no requirement or test-case entry, and (hand-off) no spec; the audit spec and its guard test still claim nothing can clear the trail (F7, F9, F10, F21, F22).

3. Critical findings (F1–F8)

F1 — Critical
Replace proceeds even when the backup failed; the message says a backup was downloaded

File: src/components/RegisterView.tsx:65-122 (handleExportBundle / handleReplaceWithBundle); src/store/handoff.ts:229-233

Panels: B calibrated, B blind, C calibrated, C blind, G calibrated, G blind (6)

Issue: handleExportBundle catches its own errors and always resolves; handleReplaceWithBundle awaits it and then unconditionally wipes and replaces the register and audit trail. A browser can also block or cancel a programmatic download silently, which JavaScript cannot observe.

Consumer impact: A reviewer whose backup fails loses their register and audit trail for good, while the screen, README and tester guide say a backup was taken first.

Fix: Make the backup step return success/failure and abort the replace on failure; because download completion is unobservable, word it honestly ("a backup file was created — make sure it saved") and ask the user to confirm they have it before anything is deleted.

F2 — Critical
"Sealed: any change in transit is detected" overclaims what an unkeyed hash proves

File: src/components/RegisterView.tsx:280-284; src/store/handoff.ts:6-28, 122-126; README.md (loop step 4, honest limits); docs/tester-guide.md

Panels: G calibrated, G blind (2)

Issue: The seal and the chain are plain SHA-256 over public, open-source logic — no key, no secret. They catch accidental corruption and naive edits; anyone holding the file can edit it and recompute every hash, and import will accept it.

Consumer impact: A reviewer would treat a clean import as proof the history is authentic and sign off on a fabricated audit trail.

Fix: Say exactly what it catches everywhere it is claimed (UI hint, export message, README, tester guide, code comments), matching the app's existing "tamper-evident, not tamper-proof" language for the local trail, and tell users to confirm the sender directly. Add a test showing a fully re-hashed forgery is accepted, so the limit is pinned, not hidden.

F3 — Critical
One malformed register entry in a bundle freezes the whole register list, permanently

File: src/store/handoff.ts:53-59 (metadata passthrough); src/store/register.ts:99-101, 250-255; src/components/RegisterView.tsx:136-152

Panels: B blind, C calibrated, G blind (3)

Issue: Register-node metadata is accepted with no shape check; toSummary throws on a mismatched node inside Promise.all, and the register's load() has no catch, so the list stays on "Loading…" — and the bad node stays in IndexedDB.

Consumer impact: After importing a corrupt or version-skewed bundle, a user sees every case disappear behind a permanent spinner, with no error and no in-app recovery.

Fix: Validate register nodes against the real metadata schema at import and reject before writing; make the list load per-row resilient and show an error instead of spinning.

F4 — Critical
One malformed timestamp in a bundle breaks every later write in the session

File: src/store/handoff.ts:46; src/store/audit.ts:17-22, 152, 172

Panels: C calibrated, C blind (2)

Issue: occurred_at is accepted as any string; an unparseable value makes the monotonic clock NaN, and the next local append throws "Invalid time value".

Consumer impact: After such an import, every sign-off, attestation or new submission fails until the page is reloaded.

Fix: Require a valid ISO timestamp at import; guard the clock against non-finite values.

F5 — Critical
Import checks the chain outside the write queue, so a write in between can fork it

File: src/store/handoff.ts:242, 269-271; src/store/audit.ts:156-175

Panels: E calibrated, E blind (2)

Issue: importBundle reads the local chain and computes the tail outside the serialised write queue, then writes that tail without re-checking the current tip; the import button has no in-flight guard, and the queue does not coordinate across tabs.

Consumer impact: A second quick import, a local action, or a second tab can leave two events claiming the same predecessor — and the case then shows "chain integrity check FAILED" for a record nobody tampered with.

Fix: Do read + check + write as one queued step, re-verify the tail joins the current tip immediately before inserting, add an import in-flight guard, and take a cross-tab lock (navigator.locks) around import/replace/append.

F6 — Critical
Register and audit trail are written in two steps with no rollback, and failures are silent

File: src/store/handoff.ts:227-228, 244-247, 269-272; src/components/RegisterView.tsx:95, 108-122

Panels: C calibrated, C blind, E calibrated, E blind (4)

Issue: The register (derived view) is written first, then the audit trail (source of truth), as separate databases with no compensation; neither UI handler catches a failure.

Consumer impact: A mid-way failure leaves a case showing a stage or verdict its own audit trail cannot justify, and the user sees nothing at all.

Fix: Write the audit trail first, then the register; catch failures in both handlers and show them; keep the pending replace available after a failure.

F7 — Critical
The audit spec and its guard test still say nothing can clear the trail

File: specs/verdict-audit.md:63, 257-263 (and .html twin); src/store/register.test.ts:493-507; src/store/audit.ts:144-154

Panels: A blind, D blind, G blind (3 — blind-only)

Issue: The spec says the audit store has no delete/update/clear; replaceAllRawEvents now clears and rewrites it, and the guard test ("no update or delete path") uses a keyword blocklist the new name evades.

Consumer impact: Anyone trusting the spec or the passing test believes the append-only guarantee is unconditional, when a UI-reachable path now replaces the whole trail.

Fix: Document the bounded exception in the spec (both twins) — verified bundle, user-confirmed, backup first — and replace the keyword test with an explicit allowlist of audit.ts exports, so any new write path must be added on purpose.

F8 — Critical
The "control set, with evidence status" panel ignores attestations

File: src/components/VerdictDisplay.tsx:1300-1376 (lines 1329, 1342)

Panels: B calibrated (Critical), D calibrated (Important), G blind (Minor) — elevated: 3 independent panels

Issue: This older panel still renders only VERIFIED/UNVERIFIED, so an attested control shows UNVERIFIED next to the "attested" chip and the checklist's count on the same screen.

Consumer impact: A reviewer sees two answers to "is this control done?" on one verdict — the direct self-contradiction the product rules out.

Fix: Add the third state ("attested — not verified") to this panel, with the same precedence as the to-do list.

F14 — Important

F15 — Important
Clock differences between machines plus a reload can raise a false "chain integrity FAILED" alarm

File: src/store/audit.ts:15, 51-62, 120-124, 156-174, 203-216

Panels: C calibrated, C blind, E calibrated (Critical), E blind (4)

Issue: Chain order is taken from sorting timestamps; after a reload the monotonic clock restarts at zero instead of the stored maximum, so on a machine whose clock is behind the sender's a new event can sort before events it follows.

Consumer impact: A legitimate record is flagged "treat as compromised". Likelihood is low (needs clock skew larger than the time between the two machines' actions) but the harm is a false tamper alarm.

Fix: Restore the clock floor from the stored trail on first write after load; verify by following hash links rather than time order.

F16 — Important
