Purpose

  • Define how verdicts are displayed to risk officers with clarity on confidence and key decision drivers
  • Specify an append-only audit trail that captures all verdict changes, reasoning, and corrections for regulatory compliance
  • Detail the correction flow for adjusting verdicts post-issuance without destroying audit history
  • Provide templates for plain-English reasoning traces that explain model decisions to non-technical users
  • Ensure integration with Policy Schema and Evaluation Engine while maintaining data integrity across the system

Design Decisions

ADR-006 Event-Sourced Audit Trail with Hash Chain Approved

Context

Regulatory compliance requires tamper-proof, append-only verdict records. Overwriting fields erases history; corrections must be traceable. A simple "update verdict" table fails audit and legal discovery.

Decision

Use event sourcing: each verdict, correction, and state change is an immutable AuditEvent. Events chain via cryptographic hash (SHA-256 of prior event + current data). Corrections link to the original verdict by parentVerdictId and include amendmentReason.

Rationale

  • Audit trail is queryable, searchable, and legally defensible.
  • Hash chain prevents silent tampering—any change to an old event breaks the chain.
  • Supports both "show full history" (compliance) and "latest state" (user-facing) queries.
  • Enables correction flow without destroying original verdict.

Consequences

  • Storage cost increases (every verdict + all corrections stored); requires TTL or archive strategy for old events.
  • Verdict display must compute "current state" from event log (latest non-superseded event).
  • Performance: indexed timestamp + intake-id queries keep retrieval sub-2s for large ranges.
ADR-007 Inline Reasoning Trace Generation During Evaluation Approved

Context

Risk officers need to understand why the engine approved or rejected a deal. Post-hoc explanation is opaque and expensive; tracing the decision path in real-time is feasible but adds latency.

Decision

Evaluation engine captures reasoning as it executes: which controls fired, which policies matched, which confidence factors applied. A ReasoningTrace object annotates each control result with plain-English templates (e.g., "Control X applied because [Factor Y met threshold Z]"). Templates are authored separately from model logic and can be updated without code changes.

Rationale

  • Reasoning is authoritative—generated from actual decision path, not guessed afterward.
  • Plain-English templates make output understandable to non-technical users.
  • Separating templates from logic enables non-engineers to refine explanations.
  • Reasoning trace is captured in audit trail, supporting historical queries ("why was this approved on June 1?").

Consequences

  • Evaluation engine must instrument control callbacks; modest CPU overhead (~5–10%).
  • Template authoring is a new operational task; changes to templates require coordination with risk team.
  • Storage: reasoning trace can be 2–5x verdict size; needs compression or separate storage tier.

Data Models

4.1 VerdictConditions

interface VerdictConditions {
  intakeId: string;                    // Link to Policy Schema intake
  caseId: string;                      // Associated case/application ID
  evaluationTimestamp: number;         // Unix ms when evaluation ran
  evaluationEngineVersion: string;     // Version of Evaluation Engine
  evaluationInputHash: string;         // SHA-256(intake data + policy rules)
  verdictType: 'in-appetite' | 'out-of-appetite' | 'review-required';
  confidenceInterval: {
    lower: number;                     // e.g., 0.82
    upper: number;                     // e.g., 0.91
    methodology: string;               // 'bootstrap' | 'bayesian' | ...
  };
  violatedControls: string[];          // Control IDs that failed
  appliedControls: string[];           // Control IDs that passed
  minimalControlSet: string[];         // Recommended additions to bring in-appetite
  suspiciousFactors: Array<{
    factor: string;                    // e.g., "Negative news sentiment"
    severity: 'low' | 'medium' | 'high';
    evidence: string;                  // Brief explanation
  }>;
}

interface ConfidenceCaveat {
  caveats: string[];                   // Array of caveat messages
  generatedAt: number;                 // Timestamp when caveat text was generated

    confidenceScore: number;           // 0–1
    intervalWidth: number;             // upper - lower
    dataFreshness: number;             // Days since intake data refreshed

  caveatRules: Array<{
    rule: string;                      // Rule ID (e.g., "CAVEAT_WIDE_INTERVAL")
    triggered: boolean;
    message: string;                   // Template text if triggered
  }>;
}

interface AuditEvent {
  eventId: string;                     // UUID
  eventType: 'verdict-issued' | 'verdict-corrected' | 'audit-query' | 'audit-export';
  timestamp: number;                   // Unix ms
  actor: {
    userId: string;
    role: string;                      // 'system' | 'risk-officer' | 'compliance-admin'
  };
  verdict?: VerdictConditions;         // Set for 'verdict-issued'
  correction?: {
    parentVerdictId: string;           // ID of verdict being amended
    oldVerdictType: string;
    newVerdictType: string;
    amendmentReason: string;
    supportingDoc: string;             // e.g., URL to amendment request
  };
  reasoningTrace?: ReasoningTrace;     // Explanation of decision
  priorEventHash: string;              // SHA-256 of prior event (hash chain)
  eventHash: string;                   // SHA-256(eventType + verdict + correction + timestamp + priorEventHash)
  metadata: {
    policyVersionId: string;           // Policy rules version
    intakeVersionId: string;           // Intake schema version
  };
}

4.4 AuditStore Interface

interface AuditStore {
  // Append: insert new audit event (auto-compute eventHash)
  append(event: Omit<AuditEvent, 'eventId' | 'eventHash'>): Promise<AuditEvent>;

  // Retrieve: get latest verdict state for intake
  getLatestVerdict(intakeId: string): Promise<VerdictConditions | null>;

  // History: retrieve all events for an intake
  getVerdictHistory(intakeId: string): Promise<AuditEvent[]>;

  queryByTimeRange(
    startMs: number,

}

5.2 Verdict Badge

A large, color-coded badge displays the verdict type:

  • In-Appetite: Green checkmark, "IN-APPETITE"
  • Out-of-Appetite: Red X, "OUT-OF-APPETITE", lists violated controls
  • Review Required: Yellow triangle, "REVIEW REQUIRED", lists suspicious factors

5.3 Confidence Display

Confidence is shown as a percentage (e.g., 87%) with an interval below (0.82–0.91). The percentage is the midpoint of the interval. A horizontal bar chart shows the interval visually, with shading for the inner quartile.

5.4 Reasoning Expander

Clicking "Expand Reasoning" shows the plain-English trace of each control and decision step. Steps are hierarchical; users can collapse/expand each section. Timestamps and policy versions are shown in a footer.

Correction Flow

6.1 Correction Initiation

A risk officer clicks "Correct Verdict" on a verdict card. A modal opens asking for:

  • New verdict type (in-appetite / out-of-appetite / review-required)
  • Amendment reason (free text, max 500 chars)
  • Supporting document link (optional)

6.2 Correction Processing

async function correctVerdict(
  originalVerdictId: string,
  newVerdictType: 'in-appetite' | 'out-of-appetite' | 'review-required',
  amendmentReason: string,
  supportingDoc?: string,
  actor: Actor
): Promise<AuditEvent> {
  // 1. Retrieve original verdict from audit log
  const originalEvent = await auditStore.getVerdictById(originalVerdictId);
  if (!originalEvent) throw new Error('Verdict not found');

  // 2. Create correction event
  const correctionEvent: Omit<AuditEvent, 'eventId' | 'eventHash'> = {
    eventType: 'verdict-corrected',
    timestamp: Date.now(),
    actor,
    correction: {
      parentVerdictId: originalVerdictId,
      oldVerdictType: originalEvent.verdict!.verdictType,
      newVerdictType,
      amendmentReason,
      supportingDoc: supportingDoc || '',
    },
    priorEventHash: originalEvent.eventHash,
    metadata: {
      policyVersionId: originalEvent.metadata.policyVersionId,
      intakeVersionId: originalEvent.metadata.intakeVersionId,
    },
  };

  // 3. Append to audit store (auto-generates eventHash and eventId)
  const newEvent = await auditStore.append(correctionEvent);

  // 4. Emit audit log event for compliance monitoring
  await emitAuditNotification({
    type: 'verdict-corrected',
    intakeId: originalEvent.verdict!.intakeId,
    originalVerdictId,
    correctionId: newEvent.eventId,
    actor: actor.userId,
  });

  return newEvent;
}

6.3 Correction Display

Once corrected, the verdict card shows a "Corrected" badge with a link to view the amendment reason and prior history. The audit trail shows both the original and correction events, with the correction appearing as a child of the original in the event hierarchy.

Reasoning Trace Generator

7.1 ReasoningTrace Interface

interface ReasoningTrace {
  traceId: string;                      // UUID
  steps: ReasoningStep[];
  summary: string;                      // One-paragraph executive summary
  generatedAt: number;                  // Unix ms
}

interface ReasoningStep {
  stepId: string;
  stepType: 'control-evaluation' | 'policy-check' | 'factor-assessment';
  title: string;                        // e.g., "Debt Ratio Control"
  status: 'pass' | 'fail' | 'neutral';
  narrative: string;                    // Plain-English explanation
  evidence: Array<{
    key: string;                        // e.g., "debt_ratio_value"
    value: any;
    unit?: string;                      // e.g., "%"
    threshold?: string;                 // e.g., "< 0.40"
  }>;
  childSteps?: ReasoningStep[];         // Nested steps
}

7.2 Reasoning Generation

During evaluation, the engine instruments each control and policy check with a callback that populates ReasoningStep objects. The callback receives the control name, input data, and result. A template engine translates this into plain English using pre-authored rules (e.g., "If debt ratio < 0.40, output 'Debt ratio is acceptable at {{value}}%'").

7.3 Code Snippet: Template Engine

function generateNarrative(
  stepType: string,
  controlName: string,
  evidence: Record<string, any>,
  result: 'pass' | 'fail'
): string {
  const templates = REASONING_TEMPLATES[controlName] || REASONING_TEMPLATES['default'];
  const template = templates[result];

  // Simple interpolation: replace {{key}} with evidence[key]
  return template.replace(/\{\{(\w+)\}\}/g, (_, key) => {
    return evidence[key]?.toString() || 'N/A';
  });
}

const REASONING_TEMPLATES: Record<string, Record<'pass' | 'fail', string>> = {
  'debt-ratio': {
    pass: 'Debt ratio is {{debtRatio}}%, which is below the threshold of {{threshold}}%.',
    fail: 'Debt ratio is {{debtRatio}}%, exceeding the threshold of {{threshold}}%.',
  },
  'sentiment-check': {
    pass: 'Sentiment analysis shows {{sentiment}} score; no red flags detected.',
    fail: 'Sentiment analysis flagged negative sentiment ({{sentiment}} score). {{flaggedTopics}}',
  },
  'default': {
    pass: 'Control {{name}} evaluated successfully.',
    fail: 'Control {{name}} triggered a violation.',
  },
};

13. Round 3 — Stating What Was Not Checked (R3-JU-3, R3-JU-6)

The verdict must carry two distinct things when no regulatory basis was applied. They are separate because they address separate readers, and an implementation providing one has met one requirement, not both.

R3-JU-3 — the consequenceR3-JU-6 — the cause
ReaderThe submitter, nowA later reader of the record
FormProse, in the verdict bodyA labelled reason on the verdict
Says“No regulatory rules were applied, so there are no citations”no_regulatory_basis
SourceRendered from provisional_reasonsprovisional_reasons itself

13.1 Absence is never communicated by absence

Before round 3, a verdict with no active packs simply had no REGULATORY REASONING CHAIN panel. A reader could not distinguish “no regulation applies here” from “we did not check” from “the panel failed to render”. All three look identical: nothing. R3-JU-3 requires the explanation to be present, not the panel to be absent.

13.2 Rendering the reasons

Where provisional_reasons is non-empty, the verdict states each reason it contains. Where both are present, both are stated (TC-R3-JU-6-03). The two must be textually distinguishable, not merely both present under one “Provisional” banner — a reader must be able to tell, without opening the policy, whether rules were applied and not yet adopted, or not applied at all.

13.2a Policy-authored content is rendered as text, never as markup (I-6)

Design review round 1, I-6. R3-RD-1 puts policy-authored strings — source_text, control evidence detail, invariant descriptions, standing conditions — onto a second rendering surface. Pack content is human-authored and partly external in origin; eu-ai-act.yaml says in its own header that its text has not been verified by a lawyer.

Today nothing is interpreted as markup, because JSX interpolates children as text and dangerouslySetInnerHTML appears nowhere in src/. But that is a framework default, not a stated rule, and TC-R3-RD-5-01 is a single test — a test is not a control.

Invariant: all content sourced from PolicyFile or a JurisdictionPack is rendered as plain text through JSX child interpolation. dangerouslySetInnerHTML and any markdown or HTML renderer are prohibited on those fields. A future change adding markdown rendering for quoted source_text — plausible, since it already renders inside a blockquote — must not apply it to pack-sourced fields.

13.3 Constraint — the verdict-query collision (HR3-08)

Existing UI tests assert the verdict screen with a single-match /approved|rejected/i query. Round 3 adds rendered strings here and, via register-lifecycle.md §15, puts the verdict status on a second screen for the first time. Any new string must avoid the words “approved” and “rejected”, and the register-side queries must be tightened before that change lands.

13.4 The sign-off event must name the verdict it attests to (R3-RD-3)

Design review round 1, C-1. The twoloD_reviewed payload is { type, action, notes? } — it carries no reference to the verdict being signed off. R3-RD-3's fit criterion ("the audit event written on sign-off refers to that same verdict") is therefore unimplementable as the schema stands, and TC-R3-RD-3-02 could only be written vacuously.

The payload gains verdict_id: string, following the pattern the schema already uses — verdict_corrected.original_verdict_id and reasoning_trace_generated.verdict_id. The value is the id of the verdict the page actually rendered, threaded from the render, not re-derived by a second "latest event" lookup at write time. A second lookup would reintroduce precisely the race this closes.

The race it closes. Without the id, a verdict_corrected event landing between the page's load and the reviewer's click means the attestation is recorded against whatever is current, with nothing recording what the reviewer saw. It could never afterwards be established — for or against — which verdict was attested. For an attestation this product frames as carrying legal weight, that is the defect, not an edge case.

Where the rendered verdict's id no longer matches the latest verdict-bearing event at write time, the write is refused and the reviewer is told the verdict changed while they were reading, rather than silently attesting to the new one.
