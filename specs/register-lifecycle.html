AIGate — Register & Lifecycle Specification

Graph-based AI inventory register, lifecycle stage machine, tier-to-workflow routing, and AIGate self-assessment (RG-1–5, LC-1–4, LC-6)
June 2026

Purpose

  • Inventory: Maintain a queryable graph of AI systems, their properties, relationships, and data flows within a bank.
  • Lifecycle: Track each AI system through defined stages (draft, active, deprecated, archived) with automatic and manual transitions.
  • Tier Routing: Map systems to risk tiers (1–4) and route them to appropriate approval workflows based on appetite.
  • Self-Assessment: Allow banks to input their own AIGate appetite and receive deterministic, auditable in/out verdicts.
  • Traceability: Link every register entry to source data, appetite rules, and control decisions for regulatory reporting.

Design Decisions

ADR-008 Use adjacency list representation for graph storage Accepted

Context

The register must efficiently store AI systems as a directed graph (nodes = systems, edges = data flows) and support frequent queries: find all downstream dependents, detect cycles, compute blast-radius impact.

Decision

Represent the graph as an adjacency list (node ID → Set of outbound edge IDs) rather than an adjacency matrix or edge-list-only store. Pair with a separate edge table (edge ID → {source, target, type, metadata}).

Rationale

  • Sparse graphs: Banks' AI inventories are sparse; adjacency matrix wastes memory.
  • Traversal speed: Outbound neighbors are O(1) lookup; DFS/BFS without scanning all edges.
  • IndexedDB fit: Two tables (nodes, edges) with a Set of edge references maps naturally to index stores.
  • Scalability: Easy to add reverse-index (inbound edges) if needed for "impact-to-me" queries.

Consequences

  • Must keep adjacency list synchronized when edges are added/deleted.
  • Cycle detection and blast-radius queries become standard graph algorithms (DFS, BFS).
  • Schema requires denormalization: every node stores its edge references.
ADR-009 Use localStorage role toggle for field masking Accepted

Context

Three stakeholder roles (bank, regulator, auditor) need different field visibility: bank sees all; regulator sees asset + risk fields only; auditor sees audit trail + approval fields only. Role is set once per session and changes infrequently.

Decision

Store the active role in localStorage under key aigate-role. Compute a field-visibility map at app load, apply CSS classes to the DOM for masking (not removing from DOM). Provide a simple toggle UI in the header.

Rationale

  • Persistence: User's choice is remembered across browser sessions without a backend call.
  • Simplicity: No server-side session state needed; toggle is instant.
  • Auditability: Role is client-side, so audit trail must still log who viewed what (captured at backend on data fetch).
  • Offline: Supports offline register viewing in the chosen role.

Consequences

  • Field masking is cosmetic (CSS display: none) — sensitive data is still in the DOM. Do not rely on this for security; always enforce role checks at the backend.
  • Role toggle is per-browser, not per-user account — if multiple users share a device, they see each other's role choice.
  • Register must be fetched with full payload; filtering on the server would be cleaner for high-security use cases.

IndexedDB Schema

The browser's IndexedDB database (aigate-register) has three object stores:

  • nodes: keyPath = id; indexes on type, tier, lifecycle_stage, owner, updated_at.
  • edges: keyPath = id; indexes on source_id, target_id, type.
  • audit_trail: keyPath = id; indexes on node_id, timestamp, user_id. Each entry logs {user_id, timestamp, action: 'create'|'update'|'delete', node_id, old_value, new_value, diff}.

Graph Traversal: Blast-Radius Query

// Compute all nodes downstream of a given node (transitive closure of 'produces' edges)
// Returns the impact radius: which systems are affected if source_id goes offline.

async function computeBlastRadius(
  source_id: string,
  db: IDBDatabase
): Promise<BlastRadiusResult> {
  const visited = new Set<string>();
  const queue: string[] = [source_id];
  const directDependents = new Set<string>();

  while (queue.length > 0) {
    const current = queue.shift()!;
    if (visited.has(current)) continue;
    visited.add(current);

    const tx = db.transaction('edges', 'readonly');
    const edgeIndex = tx.objectStore('edges').index('source_id');
    const outgoing = await new Promise<GraphEdge[]>((resolve, reject) => {
      const req = edgeIndex.getAll(current);
      req.onsuccess = () => resolve(req.result);
      req.onerror = () => reject(req.error);
    });

    for (const edge of outgoing) {
      if (!visited.has(edge.target_id)) {
        queue.push(edge.target_id);
        directDependents.add(edge.target_id);
      }
    }
  }

  return {
    source_id,
    blast_radius: Array.from(visited),
    impact_count: visited.size - 1,
    high_risk_downstream: Array.from(directDependents)
      .filter(id => {
        // Filter by tier or other risk signals
        return true; // Placeholder
      })
  };
}

interface BlastRadiusResult {
  source_id: string;
  blast_radius: string[];
  impact_count: number;
  high_risk_downstream: string[];
}

Lifecycle Stage Machine

Each AI system moves through four stages: draft → active → deprecated → archived. Transitions are triggered manually (via approval workflow) or automatically (via time-based rules or change events).

draft ──[manual approval]──> active ──[deprecation approval]──> deprecated ──[archive approval]──> archived
  ↓                                        ↓                           ↓
  └────────[age > 180d, no activity]─────┤                           │
                                          └─────[age > 2y]────────────┘

Transitions:
  draft → active:     Manual (approval workflow) or auto (immediate if low-tier)
  active → deprecated: Manual (deprecation notice + 30d grace period)
  deprecated → archived: Auto (30d after deprecation, no active data flows)
  active → draft:     Rollback (only if approval withdrawn within grace period)
    
type LifecycleStage = 'draft' | 'active' | 'deprecated' | 'archived';

interface LifecycleTransition {
  from: LifecycleStage;
  to: LifecycleStage;
  trigger: 'manual' | 'time_based' | 'event_based';
  condition?: string; // e.g., "age > 180 days and no activity"
  requires_approval: boolean;
  grace_period_days?: number;
}

Risk tiers (1–4) determine approval workflows. Banks configure tier rules; the engine computes a system's tier deterministically and routes it to the appropriate workflow. Tier assignment is rule-driven, not human guess.

Scoring formula:

function computeTierScore(node: GraphNode): number {
  let score = 0;

  // Data sensitivity
  const sensitivity = node.attributes.sensitivity as string;
  if (sensitivity === 'restricted') score += 30;
  else if (sensitivity === 'confidential') score += 20;
  else if (sensitivity === 'internal') score += 10;

  // Downstream impact
  const downstreamCount = node.outbound_edges.length;
  score += Math.min(downstreamCount * 10, 25);

  // System age (draft penalty)
  const ageMs = Date.now() - new Date(node.created_at).getTime();
  const ageDays = ageMs / (1000 * 60 * 60 * 24);
  if (ageDays < 30) score += 15; // New, untested

  // Approval required flag
  if (node.attributes.approval_required) score += 20;

  // Critical business function
  if (node.attributes.critical_path) score += 25;

  return Math.min(score, 100);
}

interface TierRouting {
  tier: 1 | 2 | 3 | 4;
  approval_path: string;
  sla_days: number;
  re_evaluation_interval_days: number;
  required_controls: Record<string, boolean>;
}

Re-evaluation Trigger

When a system's properties or data flows change, the register must re-run tier scoring and lifecycle checks. Triggers include data mutations, time thresholds, and manual requests.

// Re-evaluation event handler
interface ReEvalTrigger {
  node_id: string;
  reason: 'data_change' | 'time_threshold' | 'manual_request' | 'dependency_change';
  changed_fields?: string[];
  timestamp: string;
}

async function handleReEvalTrigger(trigger: ReEvalTrigger, store: RegisterStore): Promise<void> {
  const node = await store.getNode(trigger.node_id);
  if (!node) return;

  // Recompute tier
  const newTier = computeTierScore(node) as 1 | 2 | 3 | 4;
  if (newTier !== node.tier) {
    await store.assignTier(node.id, newTier);
    console.log(`Tier changed for ${node.id}: ${node.tier} → ${newTier}`);
  }

  // Check if lifecycle transition is required
  const now = new Date();
  const createdAt = new Date(node.created_at);
  const daysSinceCreation = (now.getTime() - createdAt.getTime()) / (1000 * 60 * 60 * 24);

  if (node.lifecycle_stage === 'draft' && daysSinceCreation > 180 && newTier === 4) {
    // Auto-promote low-risk draft systems
    await store.transitionLifecycle(node.id, 'active');
    console.log(`Auto-promoted ${node.id} to active`);
  }

  // Check if deprecated systems should be archived
  if (node.lifecycle_stage === 'deprecated') {
    const deprecatedAt = new Date(node.updated_at);
    const daysSinceDeprecation = (now.getTime() - deprecatedAt.getTime()) / (1000 * 60 * 60 * 24);

    const outgoingEdges = await store.queryEdges({ source_id: node.id });
    if (daysSinceDeprecation > 30 && outgoingEdges.length === 0) {
      await store.transitionLifecycle(node.id, 'archived');
      console.log(`Auto-archived ${node.id}`);
    }
  }

  // Emit event for downstream listeners (workflows, dashboards)
  window.dispatchEvent(new CustomEvent('register:re-evaluated', {
    detail: { node_id: trigger.node_id, old_tier: node.tier, new_tier: newTier }
  }));
}

// Listen for changes and queue re-evaluations
function setupReEvalListener(store: RegisterStore): void {
  window.addEventListener('register:node-updated', async (evt: any) => {
    const trigger: ReEvalTrigger = {
      node_id: evt.detail.node_id,
      reason: 'data_change',
      changed_fields: evt.detail.changed_fields,
      timestamp: new Date().toISOString()
    };
    await handleReEvalTrigger(trigger, store);
  });

  // Periodic time-based re-evaluation (e.g., every 6 hours)
  setInterval(async () => {
    const allNodes = await store.queryNodes({});
    for (const node of allNodes) {
      const routing = getTierRouting(node.tier);
      const lastEval = new Date(node.updated_at);
      const daysSinceEval = (Date.now() - lastEval.getTime()) / (1000 * 60 * 60 * 24);

      if (daysSinceEval > routing.re_evaluation_interval_days) {
        const trigger: ReEvalTrigger = {
          node_id: node.id,
          reason: 'time_threshold',
          timestamp: new Date().toISOString()
        };
        await handleReEvalTrigger(trigger, store);
      }
    }
  }, 6 * 60 * 60 * 1000); // 6 hours
}

AIGate Self-Assessment

Banks upload their risk appetite rules (a policy document); AIGate checks the register against those rules and returns deterministic verdicts. Self-assessment is the bridge between the register and the evaluation engine.

// Bank uploads appetite rules; AIGate evaluates register
interface BankAppetite {
  bank_id: string;
  max_tier_1_systems: number;
  tier_1_required_controls: string[];
  tier_2_approval_sla_days: number;
  prohibit_data_flows: Array<{from: string; to: string}>;
  max_blast_radius: number;
  data_classification_required: boolean;
}

interface SelfAssessmentVerdict {
  compliant: boolean;
  timestamp: string;
  summary: {
    total_systems: number;
    by_tier: Record<1 | 2 | 3 | 4, number>;
    violations: Violation[];
    recommendations: string[];
  };
  control_gaps: ControlGap[];
}

interface Violation {
  type: 'tier_limit_exceeded' | 'prohibited_flow' | 'control_missing' | 'blast_radius_exceeds_limit';
  node_id?: string;
  message: string;
  severity: 'critical' | 'high' | 'medium' | 'low';
}

interface ControlGap {
  node_id: string;
  control: string;
  required_by: string; // e.g., "tier_1_required_controls"
  remediation: string;
}

async function runSelfAssessment(
  appetite: BankAppetite,
  store: RegisterStore
): Promise<SelfAssessmentVerdict> {
  const nodes = await store.queryNodes({});
  const violations: Violation[] = [];
  const controlGaps: ControlGap[] = [];

  // Check tier limits
  const byTier = { 1: 0, 2: 0, 3: 0, 4: 0 };
  for (const node of nodes) {
    byTier[node.tier]++;
  }

  if (byTier[1] > appetite.max_tier_1_systems) {
    violations.push({
      type: 'tier_limit_exceeded',
      message: `Tier-1 systems (${byTier[1]}) exceed appetite limit (${appetite.max_tier_1_systems})`,
      severity: 'critical'
    });
  }

  // Check prohibited data flows
  const edges = await store.queryEdges({});
  for (const edge of edges) {
    const prohibited = appetite.prohibit_data_flows.some(
      p => p.from === edge.source_id && p.to === edge.target_id
    );
    if (prohibited) {
      violations.push({
        type: 'prohibited_flow',
        message: `Data flow from ${edge.source_id} to ${edge.target_id} is prohibited`,
        severity: 'critical'
      });
    }
  }

  // Check required controls
  const tier1Systems = nodes.filter(n => n.tier === 1);
  for (const system of tier1Systems) {
    for (const requiredControl of appetite.tier_1_required_controls) {
      if (!system.attributes[requiredControl]) {
        controlGaps.push({
          node_id: system.id,
          control: requiredControl,
          required_by: 'tier_1_required_controls',
          remediation: `Implement ${requiredControl} for ${system.name}`
        });
      }
    }
  }

  // Check blast radius
  for (const system of nodes.filter(n => n.tier === 1)) {
    const radius = await store.blastRadius(system.id);
    if (radius.impact_count > appetite.max_blast_radius) {
      violations.push({
        type: 'blast_radius_exceeds_limit',
        node_id: system.id,
        message: `System ${system.id} has blast radius of ${radius.impact_count}, exceeds limit of ${appetite.max_blast_radius}`,
        severity: 'high'
      });
    }
  }

  return {
    compliant: violations.length === 0,
    timestamp: new Date().toISOString(),
    summary: {
      total_systems: nodes.length,
      by_tier: byTier as Record<1 | 2 | 3 | 4, number>,
      violations,
      recommendations: [
        violations.length > 0 ? 'Address critical violations before proceeding' : 'System is compliant',
        controlGaps.length > 0 ? `Remediate ${controlGaps.length} control gaps` : 'All required controls are in place'
      ]
    },
    control_gaps: controlGaps
  };
}

Register View

The register is viewed through a filterable, sortable table. Role-based field masking (via CSS) controls visibility. Users can toggle between bank, regulator, and auditor perspectives using the localStorage role toggle.

Columns

  • ID: System identifier (immutable).
  • Name: Human-readable label.
  • Type: Node type (ai_system, data_source, etc.).
  • Tier: Risk tier (1–4), color-coded.
  • Lifecycle: Current stage (draft, active, deprecated, archived).
  • Owner: Responsible team/department.
  • Data Sensitivity: (Role-masked) public, internal, confidential, restricted.
  • Approval Status: (Regulator only) in-progress, approved, rejected.
  • Last Updated: ISO timestamp.
  • Actions: Edit, view audit trail, run re-evaluation, transition lifecycle.

Filtering & Querying

  • By Tier: Checkbox filters for tiers 1–4.
  • By Lifecycle: Toggles for draft, active, deprecated, archived.
  • By Type: Multi-select for ai_system, data_source, control, etc.
  • By Owner: Autocomplete search.
  • Full-Text Search: Searches name + description across all systems.
  • Impact Blast Radius: Filter for systems with downstream impact > N.

User Interaction

  • Click a row: Opens detail panel with full node data, related edges, audit trail, and actions.
  • Drag to reorder: Sort by any column (sorts persist in localStorage).
  • Role toggle (header): Switches between bank, regulator, auditor views; updates stored role and re-renders masked fields.
  • Export: Download register as CSV (respects current role masking).
  • Sync indicator: Shows last sync timestamp and allows manual sync trigger.

Error Handling & Edge Cases

Scenario Handling Strategy User Feedback
Cycle detected in graph computeCycles() returns cycle list. Block transition or edge creation if it would create a cycle. Toast: "Cannot add edge; would create a cycle: [node1 → node2 → node1]"
Node deletion with active edges Require cascade deletion or reassign edges. Check blast_radius first. Confirmation: "Deleting this system will orphan X downstream systems. Proceed?"
IndexedDB quota exceeded Log warning, sync to backend, clear old audit entries locally. Disable offline mode if necessary. Alert: "Storage quota full. Recent audit entries removed. Enable sync."
Network unreachable during sync Queue mutations locally, retry exponential backoff. Warn user that register is stale. Badge: "Offline; changes will sync when connection restored"
Concurrent edits (optimistic lock) Use versioning (updated_at). On conflict, show diff and let user choose keep/discard/merge. Conflict dialog with old/new/merged options
Invalid tier score (e.g., all attributes missing) Default to tier 4 (low risk) conservatively. Log warning. Flag node as needing manual review. Yellow badge: "Tier assigned by default; review recommended"
Lifecycle transition violates policy (e.g., cannot archive if active edges) Reject transition. Show list of blocking edges. Error: "Cannot archive while data flows exist: [edges listed]"
Role toggle in shared device (localStorage collision) Role is per-browser. Recommend using private browsing or separate browsers for different roles. Info: "Role is stored per-browser. Use private mode or separate browser for different roles."

15. Round 3 — The Sign-Off Page Shows the Verdict (R3-RD)

Exploratory charter 004 found that the register detail page — where a 2LoD reviewer approves a High-tier use case or requests correction — shows the tier, the status, the sign-off actions and the audit trail, and does not show the verdict. The whole page measured 779 characters. The reviewer is asked to attest to a decision whose basis the page does not present.

ADR-RL-R3-1 Read the verdict from the audit trail; do not recompute Accepted

Context

The register entry (UseCaseSummary) stores only a summary: tier, track, status, last-evaluated timestamp, policy version. The full Verdict object is already persisted in the verdict_produced audit event payload. RegisterDetail already loads all audit events for the use case.

Options Considered

  1. Re-run evaluate() on open. Rejected outright. The verdict a reviewer signs must be the verdict that was produced and attested, not a fresh one computed against today’s policy. Re-running would silently show a different verdict after any policy change — the opposite of an audit record.
  2. Widen UseCaseSummary to carry the full verdict. Duplicates data already persisted, and the copy could drift from the audit trail after a correction.
  3. Read the latest verdict-bearing payload from the audit trail the page already loads. Chosen.

Decision

The page renders the verdict from the latest verdict-bearing audit event. No recomputation, no new persistence.

Consequences

R3-RD-3 follows directly: the latest event is by construction the verdict the sign-off attaches to. Entries with no such event render the R3-RD-2 statement instead. graph is not persisted on the register entry, so any provenance panel depending on it degrades and must be omitted rather than rendered empty.

15.1 The six decision-bearing elements

  1. verdict status and tier
  2. binding constraint id
  3. every triggered invariant id, with its citation
  4. every control id in the minimal set, with evidence status (VERIFIED / UNVERIFIED)
  5. governance margin figure, and any ids flagged as having no headroom
  6. standing conditions

Content outside this list may differ from the intake rendering without failing (TC-R3-RD-1-02 compares id sets, not rendered text). The intake verdict’s reclassification affordance and reasoning trace are deliberately not carried over. Control evidence status is called out separately (TC-R3-RD-1-03) because an UNVERIFIED control rendered without its status would let a reviewer sign off believing evidence exists.

15.1a Control evidence status comes from current policy (C-2)

Design review round 1, C-2. Element 4 asks for each control's evidence status. That status is not carried on the Verdict — it lives on PolicyFile.controls[].verification_evidence, which VerdictDisplay reads live. So element 4 requires today's policy, while ADR-RL-R3-1 requires the verdict itself to be historical. As first written the two contradicted each other.

They are reconciled by scope, and the split is deliberate:

ShownSourced fromWhy
The verdict — status, tier, binding constraint, invariants, citations, margin, standing conditionsThe persisted verdict_produced / verdict_corrected payloadIt is the record of what was decided and attested. Recomputing it would change history.
Control evidence status (VERIFIED / UNVERIFIED)The current PolicyFileIt is a statement about the world now — whether evidence exists today, not whether it existed at evaluation time. A reviewer signing off today needs today's answer.

Presenting stale evidence status would be the dishonest option: it would tell a reviewer that evidence exists when it may since have lapsed. The two are labelled distinctly on the page so a reader can tell which is historical record and which is current state.

Prop path. PolicyFile is loaded in App.tsx and must be threaded App → RegisterView → RegisterDetail. Neither RegisterViewProps nor RegisterDetailProps carries it today; both gain it in P8-C06. Where policy is unavailable, evidence status renders as unknown rather than as UNVERIFIED — absence of a policy is not evidence of absent evidence.

15.1b Reusing VerdictDisplay on a reviewer's page (I-1, I-2)

Design review round 1, I-1. VerdictDisplay's onCorrect prop is required, and its "Correct this classification?" button renders unconditionally. §15.1's statement that the reclassification affordance is "not carried over" is therefore unbuildable by reuse alone — reuse would either put the affordance on the sign-off page or force a no-op handler behind a button that still invites the click.

onCorrect becomes optional. The button, and the reasoning-trace disclosure, render only when it is supplied. RegisterDetail supplies neither, so neither appears — correction is a submitter action (verdict-audit.md §6.1), not a reviewer one.

Design review round 1, I-2. R3-JU-6 requires a Provisional verdict to state which condition caused it, and it is not scoped to one screen. The sign-off page is now a place a verdict is rendered, so the requirement reaches it. The six-element list is extended: where the verdict is Provisional, its provisional_reasons are stated here too. A Provisional badge with no cause is the defect TC-R3-JU-6-01 rejects, and it would be worse on the page where someone signs their name.

Design review round 1, I-4. findLatestVerdictEvent already exists in store/register.ts but is not exported. P8-C06 exports and reuses it rather than writing a third copy of the same scan — the duplication ADR-EE-R3-1 was written to close.

15.2 No verdict recorded (R3-RD-2)

Where no verdict-bearing event exists — the seeded AIGate self-assessment is the real case on every install — the page states plainly that no verdict is recorded and leaves sign-off available. An empty panel presented as a verdict is the same class of defect as the missing panel it replaces.

**Design review round 1, I-10.** A second legacy state exists and is distinct: a verdict persisted before V1.1-C01 has no `explanation`, so elements 2 and 3 (binding constraint, triggered invariants with citations) have no source. The page states that the recorded verdict predates explanation capture and shows the elements it does have, rather than rendering an empty invariant list. An empty list would read as "nothing was triggered", which is a stronger and false claim. It does not render an empty panel, and it does not hide the section. An empty panel presented as a verdict is the same class of defect as the missing panel it replaces.

15.3 Rendering must not write (R3-NF-2)

The audit trail is append-only evidence, so a write triggered by a render is a data-integrity defect, not a performance one. Opening the page any number of times leaves the event count unchanged (TC-R3-NF-2-01, stated over two opens because React StrictMode double-invokes mount effects). The existing synchronous in-flight guard on the sign-off actions is unchanged and still required.

15.4 Constraint — the verdict-query collision (HR3-08)

Rendering the verdict here puts its status — commonly “Approved with controls” — onto the register detail page for the first time. Existing tests query verdict text with a single-match /approved|rejected/i pattern. Those queries must be tightened before this section lands. The implementation guide sequences this as its own chunk ahead of the rendering work.
