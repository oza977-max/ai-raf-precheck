Approved Platform & Vendor Envelope
Requirements Addendum

Version: 0.1 — Draft
Date: May 2026
Status: Proposed addition to AIGate Requirements v1.0
New domain: PV — Platform & Vendor Envelope

Rationale

The bulk of a typical AI intake form running to hundreds of questions is not asking about the use case. It is asking about the platform and infrastructure the use case runs on — data residency, encryption, access control, network zone, logging. These questions have the same answer for every use case running on the same approved platform. Asking them per use case is redundant work that inflates assessment time without adding governance value.

The fix is control inheritance: a platform and a vendor/model are each approved once, for a defined envelope — a specific class of data, exposure, and autonomy. A use case that sits inside an approved platform's envelope inherits that platform's cleared controls automatically. Only the residual — where the use case exceeds the envelope, or touches genuinely use-case-specific risk (purpose, data class, output exposure, fairness, explainability) — needs to be assessed at intake.

The disciplined claim — not the magic one

This is not "those questions never get asked." It is "those questions are answered once, at platform-approval time, and reused only while the use case stays inside the proven envelope." Inheritance is conditional, not unconditional. A platform approved for internal productivity data does not clear a use case touching MNPI or client PII. The moment a use case exceeds its platform's envelope, the inherited controls fall away and the relevant questions return. The tool's job is to check fit against the envelope, inherit only what fits, surface the residual, and record the full inheritance chain so a regulator can trace it.

What Breaks This (Precondition)

Inheritance requires that platform approvals specify their envelope. If a firm holds "Azure OpenAI is approved" as a bare fact with no recorded statement of approved for what data class, what exposure, what autonomy, there is nothing to check fit against, and nothing can be safely inherited. For such firms the tool's first job is to force platforms to be approved with an explicit envelope. This is valuable but is a precondition the tool imposes, not a feature that works out of the box. Firms with mature, envelope-scoped platform approvals get the full question-reduction benefit; firms without get the appetite and consistency benefits but a smaller reduction until they define their envelopes.

Functional Requirements — PV Domain

PV-1 Must

The policy file shall support an approved-platform registry. Each platform entry shall record its approved envelope: the maximum data class, exposure level, autonomy level, jurisdiction set, and network zone for which the platform is cleared, together with the set of controls the platform approval already satisfies.

A platform entry expresses, for example: Azure OpenAI (internal zone) — approved for data class ≤ Internal, exposure ≤ internal-only, autonomy ≤ L2, UK/EU; satisfies controls C-ENC-1, C-ACC-2, C-LOG-1, C-RES-3. The registry is part of the versioned policy structure.
PV-2 Must

The policy file shall support an approved-vendor/model registry, structured the same way as the platform registry. Each entry records the vendor or model's approved envelope and the controls its approval satisfies.

A use case using a model on the approved registry, within that model's envelope, inherits the model's cleared controls. A use case using a model not on the registry is treated as a new vendor (see PV-5).
PV-3 Must

During evaluation, the system shall determine whether the use case's risk envelope (data class, exposure, autonomy, jurisdiction, zone — drawn from the confirmed data-flow graph) sits inside the envelope of its declared platform and vendor/model. Controls satisfied by the platform or vendor approval shall be inherited only where the use case fits inside the corresponding envelope.

If a use case runs on a platform approved for data class ≤ Internal but the use case touches MNPI, the platform's data-handling controls are not inherited for that dimension; the relevant invariants are evaluated as if no platform clearance existed for them. Inheritance is per-dimension, not all-or-nothing.
PV-4 Must

The system shall ask intake questions only for the residual — risk dimensions not covered by an inherited platform or vendor envelope, plus genuinely use-case-specific dimensions (purpose, data class confirmation, output exposure, human oversight, fairness, explainability obligations). Questions whose answers are determined by an inherited envelope shall not be asked.

A low-risk use case on a fully covering approved platform, using an approved model, within envelope, is asked only the use-case-intrinsic questions — not the platform/infra questions the approval already answers. The number of questions asked is a function of residual risk, not a fixed list. This refines UC-4: the question budget is reduced by whatever the envelope covers.
PV-5 Must

When a use case declares a platform or vendor/model not present in the approved registry, the system shall route it to the full vendor/platform risk process as a triggered downstream review, and shall not inherit any controls for the unapproved component.

A net-new vendor produces a verdict that includes "full vendor risk assessment required" as a mandatory downstream step (consistent with CS-3), and the pre-check proceeds with no inherited vendor controls. The verdict names the unapproved component explicitly.
PV-6 Must

The verdict and audit trail shall record the full inheritance chain: which platform and vendor/model were declared, which envelope each was approved for, which controls were inherited from each, and which dimensions fell outside the envelope and were therefore evaluated directly.

If a regulator asks "was data residency assessed for this use case?", the audit trail answers: "inherited from Platform X approval, version N, which is cleared for UK/EU residency; use case is within that envelope." Inheritance is never asserted without the chain that justifies it. This extends VD-4 and VD-5.
PV-7 Must

When a platform or vendor approval changes — its envelope narrows, or its approval is withdrawn — the system shall re-evaluate all use cases that inherited from it and flag any whose inherited controls are no longer valid.

If Platform X's approval is narrowed to exclude EU jurisdictions, every use case that inherited EU coverage from Platform X is flagged for re-evaluation, with the affected dimension named. This extends the re-evaluation triggers in LC-4 and the diff mechanics in RG-4.
PV-8 Should

The starter policy file shall ship with a small set of example platform and vendor envelope entries, illustrating the envelope structure and at least one over-envelope case, so a bank can see the inheritance mechanics working before defining its own registry.

A bank installing the tool can run a sample use case that demonstrates inheritance (fits envelope, questions reduced) and a sample that demonstrates the envelope breaking (exceeds envelope, questions return), without first building its own registry.

Open Questions

OQ-PV-1

How is an envelope expressed for ordinal dimensions (data class, autonomy) versus set dimensions (jurisdiction)? Ordinal dimensions need a "≤ ceiling" semantics; set dimensions need subset semantics. The policy schema must support both. Deferred to tech spec.

OQ-PV-2

When a use case fits a platform envelope on most dimensions but exceeds it on one, is the correct behaviour partial inheritance (inherit the fitting dimensions, evaluate the exceeded one) or full fallback (evaluate everything)? PV-3 currently specifies per-dimension partial inheritance; this needs validation against a real bank's control dependencies, since some controls may be coupled.

OQ-PV-3

For firms without envelope-scoped platform approvals, should the tool offer a lightweight "define your platform envelope" flow, or simply degrade to asking the full question set? Affects time-to-value for less mature firms. Deferred to user confirmation.
