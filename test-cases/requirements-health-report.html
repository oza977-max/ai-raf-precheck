Issues

HR-01 Medium
"Substantially similar" undefined — UC-2

UC-2 requires duplicate detection above "a configurable threshold" but neither the default threshold nor the algorithm (semantic vs keyword, per OQ-4) is specified. Tests cannot have concrete pass/fail criteria until OQ-4 is resolved.

Suggestion: Add to UC-2: "Default threshold: 0.80. Algorithm: LLM-based semantic comparison if API key present; keyword/tag match otherwise."

HR-02 Low
"Standard laptop" undefined — NF-5

The 30-second verdict target is measurable, but "standard laptop" lacks a hardware definition. Performance tests cannot be written against an undefined baseline.

Suggestion: Define as MacBook Air M-series or equivalent (8GB RAM), or state that the test machine is the baseline.

HR-03 Low
CF-1 / PE-7 near-duplicate — policy file requirement

Both require a human-readable versioned YAML policy file. Intentional — PE-7 frames it as engine behaviour; CF-1 frames it as configuration. Tests written once, cross-traced to both IDs.

HR-04 Low
PE-5/6 / RA-1/2 near-duplicate — jurisdiction logic

PE-5 and PE-6 specify jurisdiction override logic from the engine's perspective; RA-1 and RA-2 cover the same from the regulatory compliance frame. Intentional dual-frame. Tests cross-traced.

HR-05 High Fix Recommended
Missing requirement: fallback form intake (no API key path)

UC-3 describes only the LLM extraction path. The handoff document, CLAUDE.md, and NF-3 all reference a fallback to structured form intake when no API key is configured — but no requirement covers what the form contains, which fields are mandatory, or how the output maps to a data-flow graph.

Suggestion: Add UC-3a: "When no LLM API key is configured, the system shall present a structured intake form covering the minimum graph attributes required for evaluation. The form output shall produce a data-flow graph equivalent to LLM extraction."

HR-06 High Fix Recommended
Missing requirement: policy file validation and load failure handling

RA-7 states invalid packs are "rejected on load" — but no requirement specifies what happens: does the application refuse to start? Show an error screen? Which field is named in the error? NF-1 requires deterministic evaluation, which depends on the policy file being in a known-valid state.

Suggestion: Add CF-5: "The system shall validate the policy file on load. If validation fails, it shall display an explicit error identifying the invalid rule or field and prevent evaluation until resolved."

HR-07 Medium
Missing requirement: API key configuration UX

NF-3 says the user supplies their own key but no requirement describes the configuration mechanism, storage location, or what is shown when the key is absent or invalid. Affects UC-3, UC-2 semantic path, and the fallback path.

Suggestion: Add NF-11: "The system shall provide a configuration screen for the LLM API key, stored in localStorage, displayed masked. If absent or invalid, fall back to structured intake (UC-3a) and keyword duplicate detection."

HR-08 High
Inconsistency: NF-2 provisional audit trail vs VD-4 absolute claim

NF-2 honestly states V1 audit trail is "provisional / proof-of-concept grade." VD-4 states audit records "cannot be deleted or modified after the fact" — an absolute claim unachievable in a client-side deployment. Tests will verify application-layer immutability only; the inconsistency is known and documented.

Disposition: Acknowledge. VD-4 tests pass if the application has no delete/edit function. V1 verdicts are labelled "Provisional audit trail."

HR-09 Low
Missing performance criterion — RG-1 graph queries

RG-1 requires graph queries to be "answerable without full-table scans" but sets no latency target. Assumed default for tests: under 2 seconds on a register of 500 use cases.

HR-10 Medium
Missing failure behaviour — LC-6 self-assessment

LC-6 requires AIGate to pass its own pre-check, stating "if it cannot satisfy its own gates, the gates are reconsidered." The process for "reconsidering the gates" is unspecified. Tests will verify: self-assessment use case exists in register, and that a Rejected result triggers a visible warning to the 2LoD role.

Health Report — Run 2 (2026-07-26)

Triggered by /gvm-status, which flagged test-cases as stale and PV as uncovered. Both flags needed correcting. Findings below supersede the /gvm-status reading where they conflict.

HR-11 — Staleness alarm was a FALSE POSITIVE (methodology finding)

/gvm-status reported requirements.md (mtime 2026-07-12) newer than test-cases.md (mtime 2026-06-13) — a 29-day drift implying the test cases were derived from superseded requirements.

Not true. Git shows both files were last changed in the same commit: c6f1892 (2026-06-13), which touched requirements.md (24 lines) and test-cases.md (95 lines) together.

The 2026-07-12 mtime came from the git filter-repo history rewrite performed that day, which rewrites every file and resets mtimes without changing content. Content-wise the two artefacts are in sync.

GVM gap worth recording: shared rule 19 specifies mtime comparison for staleness detection. In any repository that has had git filter-repo (or rebase, or a fresh clone) run, mtimes are unreliable and the check produces false positives across the whole pipeline at once. The commit date of the last content change is the sound signal. This project has had two history rewrites, so every mtime-based staleness reading here is suspect.

Disposition: no test-case regeneration required for staleness.

HR-12 — PV was built despite being a recorded V2+ deferral

/gvm-status reported PV-1..PV-8 as having zero test coverage, which is literally true. But the traceability matrix records why: PV is marked V2+ scope, out of MVP and OB is marked V1.5/V2+ scope, deferred. PV was deliberately deferred, not overlooked. Zero coverage was the correct state for the MVP.

Implementation for PV-1/2/3/5/6/8 was nonetheless written (commit f640005), on the mistaken basis that PV was an unbuilt V1 gap. It works and is tested (9 tests, 236 passing), but it is out-of-scope work against the recorded plan, and two artefacts now disagree with reality: the traceability matrix still says PV is not built, and earlier completion reporting produced a "75% of Round 1" figure by counting PV and OB as shortfalls. Excluding the 13 deliberately-deferred requirements, V1's MVP scope is 67 requirements and is complete. The 75% figure was wrong and is withdrawn.

Disposition required from the practitioner — this is a scope decision, not a test-design one.

HR-13 — TC-CS-1-02 denotes three different tests

ArtefactMeaning
test-cases/test-cases.mdSafety margin maintained — control set keeps use case inside margin
specs/implementation-guide.md (line 286)Inherited platform controls reduce required controls
src/engine/greedy-solver.test.tsTie-breaks equal-coverage candidates by lowest burden

Three definitions of one ID across requirements, spec and code. The implementation-guide meaning describes PV inheritance — behaviour the matrix says was deferred — so the guide referenced a test for out-of-scope functionality under an ID already in use.

Per shared rule 24 (fix-propagation), resolving this requires edits to all three artefacts in one pass, not just test-cases.md.

Disposition required from the practitioner.

HR-14 — CS-1 (Must) is half implemented, and the ID collision was hiding it

Resolving HR-13 surfaced a larger problem. CS-1 requires the solver to compute the smallest control set while maintaining a configurable safety margin from the appetite boundary, and states explicitly that "minimal" means smallest set that achieves the required margin — not closest to the line. It names the failure mode directly: "Optimising for minimum controls without margin optimises for developer convenience at the cost of governance resilience."

CS-1 elementStatus
Smallest set satisfying all tripped invariantsBuilt
Safety margin honoured during selectionNot built
Boundary-proximity warningBuilt

safety_margin is declared in the policy schema, validated to 0.0–1.0, and threaded through evaluate.ts into solvControls — where the parameter is named _margin. The underscore is the TypeScript convention for deliberately unused. The value is read, validated, passed, and discarded. The engine performs exactly the optimisation CS-1 names as wrong.

Why nobody noticed: the traceability matrix records CS-1 as covered by TC-CS-1-01 and TC-CS-1-02. The first is genuinely covered. The second was supposed to cover the margin — but its ID had been reused in code for a burden tie-break test, so the suite passed and coverage looked complete. The duplicate ID was concealing an unimplemented Must requirement.

This is the third instance of the same defect class here: regulatory citations computed and dropped at verdict assembly (V1), platform_satisfies declared and never read (fixed today), and now safety_margin. CLAUDE.md already warns about it — the warning exists because it keeps happening.

Disposition required from the practitioner — this is a build gap, not a test-design one, and per shared rule 25 it must not be silently skipped.
